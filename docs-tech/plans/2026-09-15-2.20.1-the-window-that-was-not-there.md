# 2.20.1 — The window that was not there

Two defects found by rolling 2.20.0 onto a real host, both by reading rather than
by an outage, plus two wording fixes the same rollout asked for. Neither defect
is reachable without opting into something: one needs a config that names
`duration` and omits `enabled`, the other needs `published_ports = "filtered"`.

## Finding A — the acceptance window was configured off, and nothing said so

`AcceptanceConfig.Enabled` is a plain `bool`: absent reads as false, with no
default and no warning. `Duration` in the same struct is refused at `<= 0` and
clamped out of range **with a log line** (`config.go:114-126`), so a file naming
only `duration` reads like one that configures a window and configures the
length of a window that never opens.

The first apply on the reporting host ran with no undo — the case 2.20 was
released to make safe.

And `restore.go:100-105` prints, at every start of a never-configured host:

> the first apply is what starts filtering, and it has the acceptance window to
> undo it

gated on `!everConfigured(state)` alone. It never consults `Acceptance.Enabled`.
The daemon promises an undo it will not perform.

**Not fixed here:** defaulting absent to true. That changes behaviour on
upgrade — every installation whose config omits the key would begin blocking
applies for its duration — and automation that applies and moves on would sit
through a window it does not know to confirm. It needs its own release and its
own acceptance round.

## Finding B — `filtered` drops container-to-container across bridges

The per-bridge deny is `ip daddr <bridge> ip saddr != <bridge> drop`, rendered
once per network, before the exceptions. Its own comment says:

> container-to-container has both ends inside, so neither matches

True within **one** bridge. A container in bridge B reaching a service published
on bridge A's gateway — DNAT'd to an address in A — arrives with its destination
in A and its source in B, so the deny matches and the exceptions that would have
accepted it never run.

On the reporting host this killed every container's DNS while all fifteen
external probes stayed green: the resolver was published on `172.17.0.1:53`, not
`0.0.0.0`. It was found by reading the drop rule's own packet counter.

## What 2.20.1 changes

| | |
|---|---|
| 1 | Warn once at start when the acceptance window is off, and stop printing the "undo it" half of that sentence when there is no window to undo with |
| 2 | `acceptance_enabled` in `FirewallStatus`, so a caller can tell "no window configured" from "no window open right now" |
| 3 | At apply, with filtering on, name the published ports that have no forwarded rule — and correct the comment that says container-to-container cannot match the deny |
| 4 | `health`'s selftest line says the proof is unavailable here rather than never recorded, when the capability it needs is absent |
| 5 | The documentation for all four, plus the UDP counter technique the rollout invented |

## Tasks

### Task 1 — the acceptance window says whether it exists

**Files:** `internal/core/restore.go`, `internal/core/config.go`, `internal/core/firewall.go`, `internal/shared/models.go`, `docs-tech/protocol.md`, `internal/web/democlient.go`

- A `slog.Warn` at start when `Acceptance.Enabled` is false, once, saying what it
  means: applies take effect immediately and nothing will undo them. Beside the
  `Duration` validation, which is where an operator already looks.
- `restore.go:100-105`'s sentence loses its final clause when the window is off.
  The first half stays true either way.
- `FirewallStatus` gains `AcceptanceEnabled bool json:"acceptance_enabled"`, set
  from the same config the apply path reads. The demo mock sets it too.
- `docs-tech/protocol.md`'s `GET_STATUS` row names the new field.

**Proven by:** a test that a status built with the window off reports
`acceptance_enabled: false` while `Acceptance` is still `idle` — the two states
the reporting host's script could not tell apart. Mutate by hard-coding the
field true and watch it go red.

### Task 2 — a published port with no rule is named

**Files:** `internal/core/nftables.go`, `internal/core/docker.go`

- At apply, when `docker.published_ports` is `"filtered"`, compare the published
  ports the daemon can already see against the forwarded port rules, and
  `slog.Warn` each one that has none, naming the port and the address it is
  published on — `53 published on 172.17.0.1 with no forwarded rule`.
- Correct the deny loop's comment. "Container-to-container has both ends inside"
  is true within one bridge and false across two, and the sentence is the
  justification for the ordering.

**Proven by:** a test over a fixture with two bridges and a published port that
has no forwarded rule, asserting the warning names it. Mutate by removing the
comparison and watch it go red. The Docker inspection is the same one that
already yields the CIDRs — do not add a second source of truth.

### Task 3 — the selftest line describes a capability, not a history

**Files:** `cmd/easywall-core/subcommands.go`, `internal/core/selftest.go` or a small helper

`describeProof` returns `"never recorded"` for an empty result. In the container
deployment that state is permanent by design: the image asks for `CAP_NET_ADMIN`
and the namespace harness needs `CAP_SYS_ADMIN`. "Never recorded" describes a
history and reads like a chore; "unavailable here" describes a capability and
tells an operator to stop looking.

Probe the capability by reading `CapEff` from `/proc/self/status` — a file read,
no fork, no clone. `health` runs on a 30-second Docker healthcheck and must stay
cheap.

**Proven by:** a test driving both branches with a fake capability reader.
Mutate by making the probe always report the capability present and watch the
container case go red.

### Task 4 — the documentation, and the changelog

**Files:** `docs/_docs/features/docker.md` or `filters.md`, `docs/_docs/features/health.md`, `CHANGELOG.md`, `docs/_docs/changelog.md`

- Under `published_ports`: a service published on a bridge gateway rather than
  `0.0.0.0` is reached by other containers **through the forward chain**, so it
  needs its own forwarded rule. This is the line that would have saved the
  reporting host.
- The UDP counter technique, which that rollout invented and which belongs
  beside the health page's own *fail* versus *unprovable* distinction: send
  datagrams from outside, then read the packet counters on the accept rules. It
  answers the question no reply-based probe can, for a service that answers
  nothing.
- The container selftest, and why it is unavailable there by design.
- `CHANGELOG.md` and its rendered twin.
