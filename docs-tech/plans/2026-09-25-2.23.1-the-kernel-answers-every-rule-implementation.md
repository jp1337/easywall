# 2.23.1 — The kernel answers every rule · Implementation Plan

> **For agentic workers:** one task, TDD. Every test is seen red by breaking the code it covers, in a throwaway worktree.

**Goal:** an apply with a realistic rule set and the curated feeds succeeds on a stock host (`rmem_max` = `wmem_max` = 212 992), and a failed flush never claims "nothing was written" when the kernel committed.

**Found by:** the wdk-ansible rollout of 2.23.0 on root01xvp — 9 × `apply_failed`: `apply nftables rules: netlink receive: recvmsg: no buffer space available (nothing was written to the kernel)` with 4 feeds (27 736 prefixes) and ~107 kernel rules.

## Root cause, with evidence

| Fact | Source |
|---|---|
| Every rule add carries `NLM_F_ACK` and `NLM_F_ECHO`; every set, chain, table and set-element message carries `NLM_F_ACK` | `google/nftables@v0.3.0/rule.go:159-163`, `set.go:388,659,674,715`, `chain.go:146`, `table.go:63-109` |
| The kernel queues every ack in `err_list` and delivers them **after** `ss->commit()`; rule echoes are unicast at commit | `net/netfilter/nfnetlink.c` `nfnetlink_rcv_batch` @ v6.12 (`done:` → `commit` → `nfnl_err_deliver`) |
| The core raises the **send** buffer only when feed elements are in the batch, and never the **receive** buffer (stock 212 992) | `internal/core/nftables_feeds.go` `feedSockOption` (`if m.sndbuf == 0 { return nil }`), `flushLarge` |
| Reproduced rootless (`unshare -rn`, rmem_default 212 992), modules on, N port rules with two sources each: | probe `TestProbeReceiveBuffer` (kept in the planning scratchpad) |

| Port rules (kernel rules) | v2.22.0 | 2.23.0 no feeds | 2.23.0 + 4 feeds at real sizes |
|---|---|---|---|
| 1 (74) | ok | ok | ok |
| 16 (104) | ok | ok | **ENOBUFS** ← caused by 2.23 |
| 40 (151) | ENOBUFS | ENOBUFS | ENOBUFS |
| 160 (391) | EMSGSIZE | EMSGSIZE | ENOBUFS |

So the limit **predates** the branch (proven at `v2.22.0`): any host with more than about a hundred kernel rules (≈107, from the measured line below; 151 is the first failing point in the table) cannot apply. 2.23's feed messages moved the threshold to ≈96 rules with root01xvp's four feeds (104 is a failing point, not the threshold), and root01xvp sits at ≈107. A release fixes what it caused; the root cause is one function, so both are fixed here.

A second defect 2.23.0 caused: `ApplyWithFeeds` tags every flush error `errNothingWritten` (`nftables.go:910-912`). A receive-side `ENOBUFS` arrives **after** the commit, so the table *was* written; the rollback then skips resetting the usage baselines (`firewall.go:755`) and the audit log says something false. (The Task 3 review listed this as a minor; the rollout proved it.)

## The fix — one place

1. **Size both buffers for every flush the manager makes**, from what the batch holds: the rules built for this transaction (`len(m.built)` at flush time), the set-element bytes already passed as `batch`, and a margin. `SO_SNDBUFFORCE` / `SO_RCVBUFFORCE` (need `CAP_NET_ADMIN` in the initial userns; the core has it), falling back to `SO_SNDBUF` / `SO_RCVBUF` on `EPERM` (capped at `wmem_max` / `rmem_max`), and the error then says which sysctl caps it — the existing `EMSGSIZE` sentence, plus one for `ENOBUFS` naming `net.core.rmem_max`.
   - **Measure** the per-rule send bytes and the per-reply receive cost (find the smallest buffer that passes for N rules, at two N, fit a line) and derive the constants from the measurement with a 2× margin — never from arithmetic. Put the numbers in the constants' comments.
   - `CapAcknowledge` stays on every socket (it keeps a refused message's echo out of its error ack).
   - The same sizing covers `ReplaceFeedSet`, the final-log flush and `Reset`.
2. **`errNothingWritten` only when the kernel cannot have committed**: a send-side failure (serialisation, dial, sockopt, `SendMessages`) or error acks (the kernel aborts the whole batch). A receive-side `ENOBUFS` is **not** tagged. The apply's error path then runs the panic check and a rollback that resets baselines, as for any post-commit failure.

## Measured (2026-09-25, rootless `unshare -rn`, Linux 7.2.3, rmem_max = wmem_max = 4 194 304)

Smallest `SO_SNDBUF` / `SO_RCVBUF` value (what `setsockopt` is passed; the kernel doubles it) that lets the apply through, every protection module on, port rules with two sources, binary search per cell:

| Port rules | Feeds | Kernel rules | min SO_SNDBUF | min SO_RCVBUF |
|---|---|---|---|---|
| 1 | — | 73 | 13 332 | 75 232 |
| 16 | — | 103 | 22 362 | 102 688 |
| 40 | — | 151 | 36 810 | 146 336 |
| 80 | — | 231 | 60 890 | 219 552 |
| 160 | — | 391 | 109 050 | 365 984 |
| 320 | — | 711 | 205 370 | 658 848 |
| 1 | 4 root01xvp | 89 | 572 144 | 100 192 |
| 40 | 4 root01xvp | 167 | 595 622 | 171 808 |
| 160 | 4 root01xvp | 407 | 667 862 | 391 456 |

Line through 151 and 391 rules: **301 bytes a rule sent, 915 received** (ack + echo), per setsockopt unit. The constants are twice that (`sndBytesPerRule = 602`, `rcvBytesPerRule = 1 830`) on top of the stock 212 992; the element acks cost ≈ 1/100 of the element bytes (≈ 10.7 k for 1.1 MB), taken as `batch/50`. The stock `rmem_default` is `sk_rcvbuf` itself, undoubled: 2 × 102 688 < 212 992 < 2 × 146 336, i.e. the stock buffer is 106 496 in setsockopt units, and the fitted line crosses it at ≈107 kernel rules without feeds and ≈96 with the four root01xvp feeds (review correction: 104 and 151 are the first failing points of the reproduction table, not the thresholds).
