# 2.25.2 — The live tail sends what is new

/blocked asks for the rows it does not have yet, and gets nothing when there are
none. New rows are marked, the tail can be paused with a button, and the page
says when it is paused and why.

**Why now.** Two reports from the live server on 2026-10-13:

1. **Every poll resends the whole view.** Measured in demo mode: 190 271 bytes
   for 103 rows, uncompressed, every five seconds — ≈137 MB an hour for one
   open tab. A row is ≈1.8 KB, mostly its three action forms.
2. **The tail stopped.** The maintainer kept /blocked open for minutes and saw
   no new row, while the core logged 6 entries in 10 minutes (seq 311 at
   19:24 UTC). The browser sent `GET /blocked/rows` every five seconds. Not
   reproduced yet. Ruled out: the server path, because demo mode returned
   seq 40 → 56 over two minutes. The client in Chromium and Firefox, because
   Playwright saw seq 62 → 69. A row falling off the 200-row limit with
   `hx-preserve`, because that swaps cleanly in both browsers. The proxy path
   (traefik → socat → WireGuard), because it holds no cache, no buffering and
   no compression (read by the wdk-ansible session). §3 says what settles it.

## 0 · Decisions, and what decided them

| # | Decision | Evidence |
|---|---|---|
| D1 | **The poll carries `after=<seq>`**, the highest `Seq` on the page; the answer holds only newer rows. | `PacketLogEntry.Seq` is assigned by the core, strictly increasing, and survives a restart through the spill file (`shared/packetlog.go`). |
| D2 | **The server picks the swap**: `after` absent or 0 → the whole view (`HX-Reswap: innerHTML`); newer rows → only those (`HX-Reswap: afterbegin`); none → `204 No Content`. | htmx 2.0.11 swaps nothing on 204, and honours `HX-Reswap`. The empty-state sentences stay where they are now: the `{{else}}` of `blocked_rows`, reached by a whole-view answer. |
| D3 | **A ring that went backwards gets the whole view.** If the newest matching `Seq` is below `after`, the core restarted without a spill file, and the answer is `innerHTML`. | Without persistence `seq` restarts at 1 (`PacketLog.Add`). A delta would then show nothing until the new count passed the old one. |
| D4 | **HTML, not JSON.** The same `blocked_rows` template renders the new rows. | Maintainer's choice. JSON would need a second renderer in app.js for the drop reasons, the remedies, the feed names and every locale string. |
| D5 | **The core protocol does not change.** The web process filters `Seq > after` from the `GET_PACKET_LOG` answer it already gets. | The cost is browser ↔ web; core ↔ web is a Unix socket on the same host. `rulesNow` (two more socket calls) then runs only when a *new* default-drop row arrives. |
| D6 | **The client keeps at most `limit` rows** (200, `packetLogDefaultLimit`), dropping from the bottom after each insert. | Without that, a page left open grows without bound. The limit reaches the page as `data-limit` on the tbody. |
| D7 | **`after` is added in `htmx:configRequest`** by app.js, read from `data-seq` on the first row. | `hx-vals="js:…"` evaluates code, which `script-src 'self'` without `unsafe-eval` refuses. |
| D8 | **A pause button**, `aria-pressed`, beside the live hint. Paused, the poll is skipped. On resume, the next poll catches up through D1 (up to `limit` rows). | Maintainer's request. The state is per tab and not stored: a reload is live again. |
| D9 | **The implicit pause stays and becomes visible.** While the pointer or the focus is in the table, the hint reads *Paused while you point at the table* (or *…work in the table*). | An insert at the top still moves the row under the cursor, which is why 2.21.1 added the pause. That pause is silent today, and a large table under a resting mouse pauses it for as long as the mouse rests there. That is the leading explanation for report 2 (§3). |
| D10 | **New rows are marked until the next batch arrives**, with a 2 px inset rule on the left in `ink` (not a state colour) and a 200 ms fade-in. Under `prefers-reduced-motion` the rule stays and the fade goes. A polite live region says *3 new entries*. | DESIGN.md § Motion: at most 200 ms, information never only in the animation, and colour is reserved for firewall state. DESIGN.md is amended to name the marker (`.pkt-new`). |
| D11 | **No response compression.** | After D1–D2 a poll is 0 bytes (204) or a few KB. Compressing pages that echo the filter fields (`src`, `dst` …) invites BREACH; static assets are already served `immutable` with a version query. |
| D12 | **An older row keeps its drop reason and remedies as rendered.** | They are read against the rules in force when the row arrived. Any staged action ends in a full page load (`handleBlockedStage` redirects). A change made in another tab shows up at the next load, and staging twice is refused (`blocked_refused_already`). |

## 1 · Server

`handleBlockedRows` reads `after` (uint64, an invalid value counts as 0). It
filters the core's entries to `Seq > after`, chooses the swap (D2/D3), and fills
`FeedNames` and `rulesNow` from the rows it will render, and no others. The
tbody gains `data-limit`, and every `<tr>` gains `data-seq`.

## 2 · Client (app.js, blocked.html, app.css)

- `initBlockedTail` grows three things:
  - It adds `after` on `htmx:configRequest`.
  - On `htmx:afterSwap` it moves the `.pkt-new` mark to the inserted rows, trims to `data-limit`, and updates the live region.
  - It owns the pause state: the button press, plus pointer and focus. It sets the hint text from that state.
- New locale keys in en, de and fr (fr gaps allowed): `blocked_live_on`, `blocked_live_paused`, `blocked_live_paused_pointer`, `blocked_live_paused_focus`, `blocked_live_pause`, `blocked_live_resume`, `blocked_live_new` (plural via the existing one/many pair). `blocked_live_hint` goes.

## 3 · The stalled tail: what settles it

The plan's first task reproduces report 2 before anything changes. It needs
one reading from the maintainer's browser, taken in Firefox DevTools → Network
on root01xvp's /blocked. For two `/blocked/rows` responses a minute apart, note:

- the status code
- the first `pkt-` id in the response
- whether the pointer was resting on the table or a *Details* row was open

Here is what each reading means:

- **Status 200 and the id rises:** the client did not apply the answer, and D9's visible state is the fix.
- **Status 200 and the id stays:** the server's answer is stale, and the plan adds a test shaped like the server (311 entries held, more than the limit).
- **Any other status:** that status is the finding.

The proof table carries the matching test either way.

## 5 · Proof

Every test is seen red by breaking the code it covers.

| Test | Proves |
|---|---|
| unit, handler | no `after` → whole view + `innerHTML`; newer rows → only those + `afterbegin`; none → 204 with an empty body; `after` above the newest → whole view; a filter combined with `after` filters both |
| unit, handler | `rulesNow` is not called when no new default-drop row is in the answer |
| `check:ui` | rows arrive and are marked; the page never holds more than `data-limit` rows; the pause button stops requests (none sent while paused) and resume catches up; pointer and focus pause and say so; a signed-out tail still navigates to /login |
| `check:ui` | the bytes of a poll with nothing new: 0 |
| Chrome | /blocked in both themes at 1600 / 900 / 390, live and paused |

## 6 · Out of scope

- A pending count while paused (*3 new — show*). Resume shows them.
- Server-sent events or WebSockets: a poll of 0 bytes costs nothing worth a
  second transport.
- A `GET_PACKET_LOG` filter `after` in the core protocol (D5).
