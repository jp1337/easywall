# Research — /options is complicated for a non-expert

German ask, verbatim: *"Auf der Optionen Seite ist bisher für Leute, die nicht so
viel Ahnung haben die Liste der Optionen ziemlich kompliziert... z.B. 'Drop
multicast' — dort steht keine Beschreibung dabei, keine Hilfe und nichts."*

**Correction against source, first:** every option already has a one-line
`module-desc` in both locales (`web/templates/options.html:41,65,...`; every
`opt_*_desc` key exists in `locales/en.json` and `locales/de.json`, verified
below). `opt_drop_multicast_desc` = "Discards traffic sent to a multicast
group" / DE "Verwirft Verkehr an eine Multicast-Gruppe" — present since the
i18n migration (`git log --follow -S"opt_drop_multicast_desc" -- locales/en.json`
finds exactly one commit, `643becc` "Graphite design system, full translation,
and a language switch" — the string has never been touched since, and was not
added recently). So the report is not "no
description exists", it is "the description that exists doesn't tell a
non-expert what breaks, why they'd want it, or where to read more" — no docs
link, no disclosure, no consequence stated. `docs-tech/plans/2026-09-23-2.21.1-what-it-offers-it-can-do-implementation.md:37`
independently names this same work item ("the Options page rewrite asked for
on 2026-09-23") and explicitly excludes it from the 2.21.1 patch — confirms
this is understood as a separate feature, not a bug in 2.21.1.

## 3. Per-option facts a non-expert needs

Verified against `internal/core/nftables.go` unless marked UNVERIFIED.

### Drop multicast — the user's own example

- **Protects against:** nothing offensive by itself; it removes an entire
  traffic class. `addMulticastDrop` (`internal/core/nftables.go:1923-1931`) is
  an unconditional `pkttype multicast drop` — no rate limit, no source check.
  It exists to *reduce noise/attack surface on a host with no LAN peers*, not
  to stop an attack.
- **What it breaks, concretely:**
  - **mDNS/Avahi and SSDP/DLNA discovery are dropped.** mDNS uses UDP 5353 to
    224.0.0.251 / ff02::fb, SSDP/DLNA uses UDP 1900 to 239.255.255.250 — both
    are link-layer multicast (`pkttype multicast`) and neither is ICMP, so
    neither is covered by the one exemption that exists (below). **Verified**
    by reading `addMulticastDrop`: it matches on `expr.MetaKeyPKTTYPE` alone,
    no protocol/port condition, so any UDP multicast destination is dropped
    once this module is on.
  - **IPv6 neighbour discovery and router advertisement are exempt, but only
    because `addICMPRules` runs earlier in the chain and accepts first.**
    `internal/core/nftables.go:721` calls `addICMPRules` before the optional
    modules are added at `internal/core/nftables.go:739-775` (`DropMulticast`
    is applied at line 770-772). `addICMPRules`
    (`internal/core/nftables.go:1157-1204`) accepts ICMPv6 types 133/134
    (Router Solicitation/Advertisement, gated by
    `ipv6.icmp_allow_router_advertisement`, default `true` —
    `config/easywall.toml:41`) and 135/136 (Neighbor
    Solicitation/Advertisement, gated by
    `ipv6.icmp_allow_neighbor_advertisement`, default `true`). Both ND/RA use
    multicast destination addresses (ff02::1/2) but are **ICMPv6**, and
    nftables evaluates rules top-to-bottom with first-match-wins for a verdict
    — an ACCEPT at line 721 stops the packet before the DROP added at line
    770 is ever reached for that packet. **Verified: exempt, and the reason is
    chain order, not a special case in `addMulticastDrop` itself.**
  - IPv6 SLAAC (which rides on the same RA/NA multicast traffic) therefore
    keeps working; anything else multicast (mDNS, SSDP, multicast video/audio
    streaming, some VoIP discovery) does not.
- **Recommended setting:**
  - Home server on a LAN, wanting Avahi/DLNA/Chromecast-style discovery to
    keep working: **off**.
  - VPS / public host with a static address and no LAN peers to discover:
    **on** is safe — matches `filters.md:25` ("Behind NAT, or on a LAN...
    Leave off: Broadcast/multicast/anycast") and `filters.md:159`.
- **Shipped default:** `drop_multicast = false` (`config/easywall.toml:129`).
  Matches the recommendation for the common case (a LAN-attached host);
  operators who need it on for a VPS have to turn it on themselves, and the
  UI gives them no signal that this is the right VPS move.

### Drop broadcast

- **Protects against:** broadcast amplification/noise; same "blunt instrument"
  shape as multicast — `addBroadcastDrop` (`internal/core/nftables.go:1911-1921`)
  is unconditional `pkttype broadcast drop`.
- **What it can break:** DHCP. **UNVERIFIED against this code** — the codebase
  has *no* DHCP-specific exemption anywhere (`grep -n "dhcp\|DHCP\|:67\b\|:68\b"
  internal/core/nftables.go` → zero hits). Whether a given DHCP exchange
  survives depends on client/server behavior the firewall does not special-case:
  a DHCPOFFER/DHCPACK sent to a client that has no address yet is commonly
  broadcast to 255.255.255.255 (RFC 2131 §4.1), while renewal traffic once an
  address is held is typically unicast. `docs/_docs/features/filters.md:159`
  states the general claim ("These carry DHCP") as a documentation fact, not
  as something this code enforces one way or the other — there is no rule in
  `nftables.go` that lets DHCP through this filter selectively. Mark:
  **UNVERIFIED from code; the risk is real for a host acquiring a lease from
  scratch, not proven safe or unsafe by any exemption in this codebase.**
- **Recommended setting:** off unless the host has a fixed IP and does not
  rely on broadcast-based discovery — same posture as multicast.
- **Shipped default:** `drop_broadcast = false` (`config/easywall.toml:128`) — matches.

### Drop anycast

- **Protects against:** traffic sent to an anycast address reaching this host
  when it should not answer for it — `addAnycastDrop`
  (`internal/core/nftables.go:1680-1699`) matches `fib daddr type anycast` via
  the kernel's own routing-table classification (`RTN_ANYCAST`), not a fixed
  address list.
- **What it can break:** anycast is rare on end hosts (mostly used by
  DNS/CDN infrastructure and some routing setups); breaking it means the host
  stops answering for an anycast address it was deliberately assigned, if any.
  On a typical home server or VPS this never fires either way, because the
  host has no anycast address configured. **UNVERIFIED beyond that generality**
  — nothing in this codebase either grants or removes an anycast address; the
  rule only decides whether *incoming* traffic to one is dropped once the
  kernel FIB says the destination is anycast-classed.
- **Recommended setting:** on is harmless for the overwhelming majority of
  hosts (no anycast role); off makes no practical difference either. Lowest
  priority of the three filtering toggles to explain.
- **Shipped default:** `drop_anycast = false` — consistent either way.

### Bogon filter — already the best-documented module

- Fully covered in `filters.md:108-149`: the 11 ranges, the whitelist/Docker
  exemption, and the explicit DHCP-server warning ("Not on a DHCP server: a
  client requesting a lease has no address yet and sends from `0.0.0.0`,
  which this filter drops" — `filters.md:149`). This is a **documented,
  code-consistent** exemption model the multicast/broadcast/anycast trio
  lacks; it is the pattern the redesign should hold the other three to.
- Recommended: on for a public server with a static address
  (`filters.md:24`), off behind NAT unless the operator's own network is
  whitelisted first (`filters.md:25`, and the "Before switching it on" table
  at `filters.md:146-149`).
- Default: off (`config/easywall.toml:112`) — matches the cautious case.

### The nine attack-protection modules (SSH brute-force, ICMP flood, SYN flood,
port scan, invalid packets, fragment drop, connection limit, TCP RST flood)

All nine are already summarized correctly and specifically in both the UI
description and `filters.md:87-106`; none is vague in the way `drop_multicast`
is. The one place they underserve a non-expert is the *default-vs-recommended*
question:

| Module | Default | Recommended: home server | Recommended: VPS | Match? |
|---|---|---|---|---|
| SSH brute-force | **on** | on | on | yes |
| ICMP flood | **on** | on | on | yes |
| SYN flood | **on** | on | on | yes |
| Port scan detection | **on** | on | on | yes |
| Invalid packets | **on** | on | on | yes |
| Fragment drop | off | off, "unless you know your traffic" (`filters.md:24`) | on for a public static-address host (`filters.md:24`) | **default does not match the VPS recommendation** — matches home/NAT, not VPS |
| Bogon filter | off | on once own LAN is whitelisted (`filters.md:25`) | on (`filters.md:24`) | **default is the cautious floor, not the VPS recommendation** — same shape as fragment drop |
| Connection limit | off | operator judgment; no doc recommendation given | operator judgment | UNVERIFIED — `filters.md` gives no per-host-type call for this one |
| TCP RST flood | off | operator judgment | operator judgment | UNVERIFIED — same, no doc recommendation |

The gap is consistent: **defaults are tuned for the safest/most common case
(home/NAT), and the doc's own "Which to turn on" table already says a public
static-address VPS should turn on more.** The options page has no concept of
"you look like a VPS, consider these" — that is exactly the presets idea in
approach B below.

## 4. Existing UI patterns to reuse

- **The "why" aside-card pattern already exists** on `/blacklist`, `/ports`
  and `/settings`. `web/templates/blacklist.html:55-72`: a `page-grid` layout
  with a `.aside-stack` of `.aside-card` blocks, each an icon + `{{T
  "..._title"}}` heading + one or two `<p>` of explanation, one of which uses
  `richText` to embed a link (`blacklist.html:70`,
  `richText (T "blacklist_order_body") "/whitelist" (T "link_whitelist")`).
  Locale keys follow `<page>_what_title` / `<page>_what_body` /
  `<page>_..._title` (`grep` hits: `blacklist_what_body`,
  `ports_ssh_card_title`, `ports_sources_card_title`,
  `settings_docker_card_title`, `settings_routing_card_title`,
  `totp_card_title`, `passkey_card_title`). **`options.html` currently has no
  `page-grid`/aside column at all** — it is a bare `module-grid`, so adopting
  this pattern is a structural addition, not a copy-paste.
- **A `<details>` disclosure pattern already exists**, on `/blocked`:
  `web/templates/blocked.html:153-165`, `<details class="pkt-detail"
  id="pkt-{{.Seq}}" hx-preserve="true"><summary>{{T "blocked_detail"}}</summary>
  <dl>...</dl></details>` — a native, no-JS, keyboard- and touch-accessible
  expand/collapse the codebase already ships and already has CSS for
  (`.pkt-detail`). This is the natural mechanism for a per-module "What does
  this do?" disclosure (approach A below) rather than inventing a new
  JS-driven popover.
- **`richText`** (`internal/web/server.go:1167-1196`) is the only sanctioned
  way to put a link inside translated prose — one `{}` slot per link, whole
  sentence kept intact for German word order (see
  `project_easywall_i18n_gap.md`). Any docs link on the options page must go
  through this, as `save-bar-note` already does
  (`options.html:288`, `richText (T "options_saved_note") "/apply" (T
  "link_apply_rules")`).
- **DESIGN.md is explicit and already against tooltips for this exact
  content:** *"Tooltips explain a control, they never carry information that
  exists nowhere else... Anything an operator needs in order to decide belongs
  on the page"* (`DESIGN.md:1427-1432`), and under Don'ts: *"Don't put
  decision-relevant information in a tooltip"* (`DESIGN.md:1553`). This rules
  out a tooltip-based fix outright — a hover/focus popover is not an
  acceptable design for "what does Drop multicast break", it has to be
  on-page (inline description, disclosure, or aside card).
- DESIGN.md's page-grid section (`DESIGN.md:1011-1041`) already reasons about
  when a context column is/isn't worth the width, including a documented
  case (`/ports`) where the aside column was dropped because the table needed
  the width instead — relevant precedent if a page-grid aside is considered
  for `/options` (14 modules, likely similar width pressure to `/ports`'s 7
  columns; need to render before deciding, per DESIGN.md's own repeated rule
  of "verify by rendering, not by reading the token table").

## 6. Design approaches

**A — Better one-line descriptions + a "What does this do?" disclosure per
module + a docs anchor link.**
- Reuses `<details>` (§4) inside `.module`, no new JS. Reuses `richText` for
  the docs link inside the disclosed body.
- en/de parity: every disclosure body is a new locale key pair
  (`opt_<key>_what_body` or similar), so this is 14 (or more, if params get
  their own line) new key pairs in both `en.json` and `de.json`,
  simultaneously — `TestLocaleFilesAreAtParity` enforces this already exists
  as a guard, so the mechanism to keep parity is already in CI, but the
  authoring work is 14+ new sentences to write and translate carefully (per
  `project_easywall_i18n_gap.md`: German reorders around the link slot,
  render both languages before calling it done).
- fr gap: `locales/fr.json` currently has 213 keys missing relative to `en`
  (471 vs 684, measured by parsing both JSON files) — adding ~14-28 new keys
  widens that gap by the same count; per `CLAUDE.md`/repo convention this is
  tolerated (fr falls back to en, counted by the coverage report, never
  hidden) but should be named explicitly in the eventual PR rather than
  discovered later.
- Screenshots: `docs/assets/img/screens/options-{dark,light}.png` are
  referenced by `filters.md:28-32` and must be retaken (both themes) once any
  card grows a disclosure control — DESIGN.md and
  `feedback_regenerate_screenshots_on_ui_change.md` both require this in the
  same change.
- 390px: a `<details>` inside `.module` should reflow fine (native block
  element, no fixed width assumed by `.module-params`), but this is a claim to
  verify by rendering, not to assume — consistent with
  `feedback_verify_ui_by_rendering.md` and `feedback_render_at_three_widths.md`.
- Lowest structural risk: no new page-grid, no layout change to
  `options.html`'s existing `module-grid`.

**B — Presets ("Home server / VPS / Custom") layered on top of A.**
- Directly answers §3's finding that defaults are the cautious floor and the
  doc's own "Which to turn on" table (`filters.md:22-26`) already encodes
  exactly three profiles (public static server / behind NAT or LAN / container
  host). A preset selector could apply that table's recommendations in one
  click, falling back to "Custom" once any toggle is hand-edited.
- New surface: a preset needs its own state (which preset is "active", how
  "Custom" is detected — probably "any toggle differs from the preset's
  values"), a new handler branch, and new locale keys for the preset names and
  descriptions of what each changes. This is materially more code than A: a
  new concept, not just better copy.
- Same en/de/fr and screenshot/390px obligations as A, plus the preset
  control itself needs the same rendering verification.
- Risk: presets can go stale relative to `filters.md`'s table if that table is
  ever revised without updating the preset logic — a second place carrying
  the same three-profile knowledge, unless the preset literally reads
  `FirewallLimits`-style shared data both consult. Worth deciding up front
  whether the preset table lives in `internal/shared` so `filters.md` could
  eventually be generated from the same source (out of scope for this
  research, flagged for the actual spec).

**C — A + grouping by risk (e.g. "Safe to enable" vs "Read this first" vs
"Only if you know why").**
- The existing two groups (`options_group_attack` / `options_group_filter`,
  `options.html:24-25` and `216-217`) are protocol-shaped (attack protection
  vs traffic filtering), not risk-shaped — port scan detection (default on, no
  known breakage) and drop-multicast (default off, breaks mDNS) currently sit
  in different *existing* groups already, so re-grouping by risk would cut
  across the current two groups rather than just relabeling them. That is a
  bigger template change than A or B: every module's group membership needs
  re-deciding, and `options_group_attack_note` / `options_group_filter_note`
  copy needs rewriting for the new semantics.
- Same i18n/screenshot obligations, larger diff for less clearly-scoped
  benefit than A or B — the risk information A's disclosure already carries
  (what breaks) does most of the work C would add, without moving anything.

**Recommendation:** **A first**, because it is the direct, small fix for the
concrete complaint (multicast's vague description) and every module has the
same shape gap; reuses two patterns already in the codebase
(`<details>`, `richText`+aside pattern) rather than inventing new UI. **B as
a deliberate follow-up**, because §3 shows the "what should I actually pick"
question A's disclosures answer per-module is also answerable in one shot for
whole host types, and `filters.md` has already done that analysis — but B is
a new feature surface and should be its own spec/decision, not bundled into
the fix for "the description is vague." C is the weakest case here: the
value it adds (risk grouping) is largely subsumed by A's per-module "what
breaks" text, for a much larger diff.
