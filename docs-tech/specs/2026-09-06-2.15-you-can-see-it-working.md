# 2.15 — You can see it working

Every port rule gains a stable identity and a kernel counter keyed to it, so the
interface can say when that port last carried a packet. A rule nobody has used in
a month is the most common avoidable exposure on a hobby server, and today
nothing in easywall can point at one.

The release also closes ten entries from `carried-forward.md` — two races, four
audit-silent paths, two guards that do not see enough, and the wording defects
beside them. They are carried here as bugfixes rather than given a release of
their own.

Agreed with the maintainer on 2026-09-06, including the persistent counter over
the live-only one, and the synthetic rule id over a content-derived key.

## 1 · What exists today

- `shared.PortRule` (`internal/shared/models.go:4`) holds `Port`, `Description`,
  `SSH`, `Sources` and `Service`. **There is no identity.** Port alone does not
  supply one: the demo dataset carries `80` twice, once as *HTTP — redirect to
  HTTPS* and once as Pi-hole's *Web interface*.
- `addPortAccept` (`internal/core/nftables.go:1857`) builds **one kernel rule per
  source**, and a rule with no sources becomes exactly one. So a UI rule is one
  *or several* kernel rules, and any counter must be summed across them.
- No rule anywhere in the tree carries `expr.Counter`. The four existing mentions
  of "counter" in `nftables.go` are all about rate limiters.
- `nftables.Rule.UserData` round-trips through `Conn.GetRules`
  (`rule.go:55`, `rule.go:266`), and `expr.Counter` decodes `Bytes` and `Packets`
  on read (`expr/counter.go:58`).
- `appliedconfig.go` is the house pattern for state beside the rules: a
  `readX`/`writeX` pair over one JSON file under `DataDir`, atomic rename, mode
  0600 as `file_modes_test.go` requires.
- The nft connection is serialised by a mutex, pinned by
  `nftables_mutex_test.go`. Anything that reads counters competes with an apply.

## 2 · Identity

```go
// ID identifies this rule across applies, edits and reorderings. Usage counters
// are keyed by it, and 2.18's per-entry metadata will key by it too.
// Assigned once at creation, never rewritten.
ID string `json:"id,omitempty"`
```

Twelve hex characters from `crypto/rand`. Not a UUID — thirty-six characters in
every export buys nothing here. Not a counter — that needs a high-water mark
stored beside the rules.

`omitempty` keeps a `rules.json` written before 2.15 byte-identical until it is
touched. That is the promise `Sources` made in 2.11 and it is kept the same way.

**Backfill is not a migration step.** `NewRulesStore` (`internal/core/rules.go:44`)
already initialises a missing file under the store's lock; it gains one more job
there — fill any empty id in `current`, `staged` **and** `backup`, then write
once. Backup included, or a rollback restores rules whose history has been
orphaned.

Filling ids on the read path would be wrong and the guard test says so: a value
generated per read is a different value every read, and every counter would be
keyed to a rule that no longer exists by the time it is read back.

| Case | Behaviour |
|---|---|
| Duplicate id in `rules.json` | `ValidateRules` rejects the state |
| Import carrying foreign ids | Kept. On this host they have no history, which is the true answer |
| Import with duplicates *inside* the imported set | The duplicates are regenerated, the first occurrence keeps its id |
| Rule edited (port, sources, description) | Id unchanged, history intact |

## 3 · The kernel side

`addPortAccept` attaches to every kernel rule it builds:

```
[ matches… ] → expr.Counter{} → expr.Verdict{Accept}
                     ↑
         after the match, before the verdict
```

Placed before the matches, the counter counts every packet that *reaches* the
rule rather than every packet that *matches* it — the number would then be a
measure of the rules above it and of nothing else. This is the one mistake
available here, and §8 fixes the order with a guard.

`UserData: userdata.AppendString(nil, userdata.TypeComment, rule.ID)`.
`TypeComment` rather than a private TLV type, so `nft list ruleset` shows the
operator the same key the interface uses.

Custom rules are raw nftables statements and cannot be tagged. They get no
counter, and the documentation says so rather than leaving a blank column to be
read as "never used".

## 4 · Collection — `internal/core/usage.go`

```go
type RuleUsage struct {
    Packets, Bytes             uint64
    FirstSeen, LastSeen        time.Time
    KernelPackets, KernelBytes uint64  // baseline: last observed kernel value
}
```

`DataDir/usage.json`, mode 0600, atomic rename — `appliedconfig.go`'s shape.

```
collect():
  1. take the nft mutex; GetRules over the input chain
  2. sum each rule's expr.Counter by its UserData comment
  3. delta = now − baseline        (now < baseline ⇒ table was rebuilt ⇒ delta = now)
  4. delta > 0 ⇒ LastSeen = time.Now(); FirstSeen if unset
  5. baseline = now; write atomically
```

**The baseline is persisted, not merely held in memory.** The table outlives a
daemon restart, so a memory-only baseline would make the first collect after a
restart re-count every packet already booked before it. This is the bug this
field exists to prevent, and `…ADaemonRestartDoesNotDoubleCount` is the test that
proves it.

Called from two places:

| Caller | When | Why |
|---|---|---|
| Ticker | every `[usage] interval`, default 300 s | `last used` needs a resolution that does not depend on someone opening the page |
| `apply()` | synchronously, immediately after the panic gate at `firewall.go:236`, before `nft.Apply` | The flush zeroes every kernel counter. Collect first or the last interval is lost |

After collecting, `apply()` sets every baseline to 0, because the table it is
about to write has none of the old counts in it.

The remaining lossy case is a flush that easywall did not perform — `nft flush
ruleset` typed by hand. The `now < baseline` branch catches it and the interval
since the last collect is lost. Documented as a known limit, not defended
against: the reconciler already owns that class of event.

`addPortAccept` writes to the **input** chain and nowhere else — two call sites,
`nftables.go:523` and `:526` — so collection reads that chain alone. A guard pins
it, in the family of the kernel-write guard §7 is already widening.

A packet dropped by the `sshbrute` rate limiter never reaches the input chain's
accept rule and is therefore not counted. That is the right semantics: the column
says *last used*, not *last attempted*, and an operator deciding whether to close
a port wants the first.

Interval configuration follows `AcceptanceDuration` (`internal/core/config.go:279`):
an integer of seconds in TOML, a `time.Duration` accessor on `Config`.

```toml
[usage]
interval = 300  # seconds between counter reads; 0 stops the ticker
```

`interval = 0` stops the **ticker** only. `apply()` still collects, because that
call exists to keep the flush from destroying a number rather than to sample one.
So a host with collection switched off still shows a *Last used* that advances at
every apply, and the configuration reference says exactly that instead of leaving
it to be discovered.

## 5 · Protocol

`CmdGetUsage = "GET_USAGE"` — the twenty-first command. Returns
`map[string]RuleUsage` keyed by rule id, plus `CollectedAt`.

Read-only. No audit entry: reading a counter is not an event, the same reasoning
`CmdGetStatus` already runs on.

## 6 · The interface

| Surface | Change |
|---|---|
| Ports table | A **Last used** column, right of *Description*: `never` · `3 days ago` · `just now` |
| A rule with no id | `—`, never `never`. A rule that has not yet been observed and a rule observed to be idle are different claims |
| Dashboard | The existing *TCP ports · 8 · accepting connections* tile takes a second line when it applies: `2 unused for 30+ days`. **No new tile** |
| Demo mock | `democlient.go` returns usage including at least one port unused for sixty days — otherwise the public demo does not show the feature at all |

Thirty days follows FortiGate's convention, which is the interface most operators
will have met this idea in.

No new CSS component. The column is a table cell in `ink-subtle`.

**The unused count carries no colour.** `DESIGN.md` rule 1 reserves green, amber
and red for firewall state — live, unconfirmed, rolled back, failing — and an
unused open port is none of the four. The number is bent rather than the rule.
Reopening this means amending `DESIGN.md` openly, not deviating from it quietly.

**Bytes are stored and not shown.** Only *last used* reaches the screen. A byte
total on a firewall rule invites the wrong question; the roadmap asked about
exposure, not accounting. Storing them costs nothing and 2.17's notifications may
want them.

## 7 · What was carried forward is done

Ten entries from `docs-tech/carried-forward.md`, moved to done in the same pass:

| | |
|---|---|
| `Panic` and `Resume` share no lock | A `panicMu` around both. `Resume`'s `ClearPanic` interleaving today leaves no marker and an empty table |
| Marker check to netlink write is not atomic | The third site stats the marker three times; pass the known state into the helper instead |
| Four audit-silent paths in `apply` | `BackupCurrent`, `PromoteStaged` and the re-read `GetState` all return with `fmt.Errorf` and no entry, directly below a first `GetState` that writes one |
| `acceptance.Start`'s error path | Returns with new rules live, no window and no rollback. It should roll back |
| The kernel-write guard is scoped to two files | `daemon_source_order_test.go` names `firewall.go` and `restore.go`; `filepath.Glob` over the package closes it |
| `bootBridges` has no test | All four reconciler tests write the field directly, so deleting `setBootBridges` from `RestoreCurrent` leaves the suite green |
| `CHANGELOG.md`'s count claim | Says the assertion "now says seventeen"; it says at least fifteen |
| `locales/de.json`'s `Fortsetzen` | A hapax; every other panic string uses `Notfallmodus` |
| The Docker reconcile reuses `RestoreReasonBoot` | A restore minutes after boot logs the detail "daemon start". A third constant costs nothing |
| The reconciler polls under panic mode | Logs "putting the rules back" immediately before `RestoreCurrent` logs the refusal. One check at the top |

`CmdPanic`'s 35-second deadline is **not** in this list. It wants a timeout that
checks the marker and reports what it finds, which is a behaviour change to the
CLI's contract rather than a fix — it stays carried, with that reasoning added to
its entry.

## 8 · The proof this release owes

A counter that is wrong is worse than no counter: it is a number an operator will
close a port on. Every guard below must be verified by **breaking the
implementation and watching it go red** — 2.12 produced seven tests that were
green while proving nothing, and this release will not repeat it.

| Guard | Mutation that must turn it red |
|---|---|
| `…EveryPortKernelRuleCarriesItsRuleID` | Drop the `UserData` assignment |
| `…TheCounterSitsAfterTheMatch` | Move `expr.Counter` ahead of the matches |
| `…ApplyCollectsBeforeItFlushes` | Swap the collect and the kernel write |
| `…ARebuiltTableDoesNotLoseTheInterval` | Remove the baseline reset in `apply()` |
| `…ADaemonRestartDoesNotDoubleCount` | Hold the baseline in memory only |
| `…RuleIDsAreUniqueAndStable` | Move the backfill to the read path |
| `…ARuleWithoutAnIDRendersEmDash` | Render `never` for a missing id |
| `…CollectionReadsTheInputChain` | Point the collector at another chain |

One integration test against a real kernel, in the `integration` tag beside the
existing veth proofs: open a port, send packets to it, assert the counter moves
and `LastSeen` advances past the collect that preceded them. It is the only test
here that proves the *feature*; the eight above prove the plumbing.

## 10 · Scope

**In:** the rule id and its backfill, counters and `UserData` on port rules,
`usage.go` with its persisted baseline, the ticker and its configuration,
`GET_USAGE`, the *Last used* column, the dashboard's second line, the demo mock,
the eight guards, the integration proof, the ten carried-forward fixes, the
roadmap amendment in §0.

**Out:** counters on blacklist, whitelist and forwarding rules — a different
question, and 2.18's. Any byte figure on screen. Sorting or filtering the ports
table by last use. Notifications about an unused port, which is 2.17. The design
work in §0's new 2.16 — this release inserts it into the roadmap and does not
begin it.
