# 2.24 — Containers answer over IPv6

With `[docker] published_ports = "filtered"`, a port Docker publishes on IPv6 is
forwarded like its IPv4 twin: open where a forwarded rule names it, dropped where
none does. A Docker network that appears after the last apply is named instead of
silently dropping its containers.

**Who waits for it.** root01xvp wants mail over IPv6 through Docker: a ULA bridge
beside the IPv4 /24, ports published on `[::]`, Docker's own ip6 DNAT so the
client's source address survives for postfix, rspamd, RBLs and fail2ban. The last
hop — ip6 DNAT → forward — is the one easywall drops today.

## 0 · Decisions, and what decided them

| # | Decision | Evidence |
|---|---|---|
| D1 | **Family twin** (approach A): a forwarded accept is emitted once per address family that has at least one container network. | Maintainer's choice. Same shape as the proven IPv4 path; the per-bridge deny carries it. Approach B (accepts bound to container destinations) changes IPv4 behaviour for every `routing.networks` host and is its own release; approach C (no family pin) reopens the hole `forwardFamilyPin` closes (`nftables.go` comment on it). |
| D2 | **A host with no IPv6 container network gets a ruleset byte-identical to 2.23.2** — with one named exception: under `ipv6.mode = "block"`, a forwarded rule's IPv6 sources no longer render (D3). | The release fixes a gap; it must not move anybody who is not in it. The exception touches only a configuration that contradicted itself. Pinned by a recording-adder test. |
| D3 | **`ipv6.mode = "block"` keeps IPv6 away from containers.** IPv6 prefixes are removed from the container networks before the forward chain is built — detected ones and `custom_networks` alike — so no IPv6 twin, deny or exception renders and IPv6 to a container meets policy drop. | "No business speaking IPv6" (`models.go`, IPv6Block) is a statement about the host; a container reached through it is the host speaking IPv6. `filter` and `passthrough` both handle IPv6 in the forward chain like IPv4: passthrough is defined on the input chain only. |
| D4 | **Link-local (`fe80::/10`) is never a container network.** | Every bridge carries one; counting it would make every host an IPv6 container host and render IPv6 twins everywhere, breaking D2. |
| D5 | **A bridge the rules in force do not know is a warning, not a re-apply and not a health state.** Named in `easywall-core status` and on the dashboard; `/healthz` and `health` unchanged. | Maintainer's choice ("warning only"). The firewall still enforces what it says — it is stricter than expected, and one apply fixes it. `degraded` would page monitoring and restart a container healthcheck for that. Nothing changes the kernel without the operator. |
| D6 | **The published-port check reads the `ip6` family too.** | Its own comment calls the gap inherited; `features/docker.md` tells operators to check IPv6 by hand ("Silence is not a clearance"). With IPv6 forwarding real, that silence becomes a false green. |

## 2 · The forward chain

Order unchanged; the IPv6 lines render only under D1's condition and never under
`ipv6.mode = "block"` (D3):

```
ct state established,related                       accept
<forwarded rules>  meta nfproto ipv4 … dport N     accept    today
<forwarded rules>  meta nfproto ipv6 … dport N     accept    new
ip  daddr <v4 bridge> ip  saddr != <v4 bridge>     drop      today
ip6 daddr <v6 bridge> ip6 saddr != <v6 bridge>     drop      via detection
<bridge / routing exceptions, both families>       accept
                                                   policy drop
```

A forwarded rule with sources renders as today: `portAcceptRules` emits one
kernel rule per source, each carrying its own family from `cidrMatch`, and
nothing here re-pins it — except under `ipv6.mode = "block"`, where the forward
chain skips a forwarded rule's IPv6 sources (D3). Without that, an IPv6 source
named on a forwarded rule would still carry IPv6 to anything the host routes,
past the statement `block` makes.

`forwardPortRulesRender` and `addForwardPortRules` keep their guard: no container
network at all renders nothing. "Container network" now means either family.

## 3 · A bridge the rules do not know

- The manager records, at every build, the container networks it baked into the
  forward chain (after D3's filter), with the interface each came from.
- `STATUS` gains `unknown_bridges`: every current bridge network (detected now,
  D3-filtered) absent from that record, as interface + CIDRs. Empty when Docker
  coexistence is off, when `allow_bridge_networks` is off, or in panic mode.
- `easywall-core status` prints one line per interface: *Docker network br-4f2a
  (fd00:…/64, 172.20.0.0/24) exists and is not in the rules in force: apply to
  name it.*
- The dashboard shows the same sentence as an `alert-warn` with a link to
  `/apply`, in `en`, `de` (and `fr` where its catalogue has the surrounding
  keys). The demo mock returns one unknown bridge so the notice can be reviewed.
- A bridge that disappeared is not reported: rules naming a vanished network
  cost nothing.

## 4 · Documentation

- `features/docker.md`: the *IPv4 only, until 2.24* callout is replaced by a
  short how-to for an IPv6 Docker host — a user-defined bridge with
  `enable_ipv6` and a ULA /64, ports published on `[::]`, `ip6tables` enabled in
  Docker, what `ipv6.mode` does to containers (D3), and the unknown-bridge line.
  The published-port check's *IPv4 only* and *Silence is not a clearance* rows go.
- `configuration.md`: `ipv6.mode` and `docker.published_ports` say what they do
  to container traffic.
- `CHANGELOG.md`; the 2.24 row leaves the roadmap; `docs-tech/protocol.md` for
  the new `STATUS` field; `invariants.md` for the new guard tests.

## 5 · Proof

Every test is seen red by breaking the code it covers, in a throwaway worktree.

| Test | Proves |
|---|---|
| recording adder: IPv4-only host | ruleset byte-identical to 2.23.2 (D2) |
| recording adder: IPv6 container network | one IPv6 twin per source-less forwarded rule, IPv6 deny and exceptions present, order as §2 |
| recording adder: `ipv6.mode = "block"` | no IPv6 line in the forward chain — from detection, `custom_networks`, or a forwarded rule's IPv6 source (D3) |
| unit: detection | `fe80::/10` never returned; a ULA address masked to its network (D4) |
| unit: decoder | an IPv6 DNAT rule → published port, against a rule **dumped from a live kernel's `ip6 nat`** |
| integration, real kernel | veth proof over IPv6: client namespace ↔ host ↔ a `br-` interface with a ULA /64. A named port reachable over IPv6, an unnamed one dropped, IPv4 in the same run unchanged. An IPv6-only published DNAT with no rule is named by the check |
| unit + `check:ui` | `unknown_bridges` computed from record vs detection; the status line; the dashboard notice in both themes at 1600 / 900 / 390 |

## 6 · Out of scope

- Accepts bound to container destinations (approach B) — IPv4 behaviour change,
  its own release if ever.
- Re-applying on its own when a bridge appears after boot (D5).
- IPv6 NAT or masquerade by easywall — Docker's.
- Interface-bound rules (roadmap *Every rule knows its interface*).

and drops on root01xvp and makes one IPv6 connection from outside to port 25;
