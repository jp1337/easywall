# 2.24 — Containers answer over IPv6

With `[docker] published_ports = "filtered"`, a port Docker publishes on IPv6 is
forwarded like its IPv4 twin: open where a forwarded rule names it, dropped where
none does. A Docker network that appears after the last apply is named instead of
silently dropping its containers.

**Who waits for it.** root01xvp wants mail over IPv6 through Docker: a ULA bridge
beside the IPv4 /24, ports published on `[::]`, Docker's own ip6 DNAT so the
client's source address survives for postfix, rspamd, RBLs and fail2ban. The last
hop — ip6 DNAT → forward — is the one easywall drops today.

## 0 · Decisions, and what decided them

| # | Decision | Evidence |
|---|---|---|
| D1 | **Family twin** (approach A): a forwarded accept is emitted once per address family that has at least one container network. | Maintainer's choice. Same shape as the proven IPv4 path; the per-bridge deny carries it. Approach B (accepts bound to container destinations) changes IPv4 behaviour for every `routing.networks` host and is its own release; approach C (no family pin) reopens the hole `forwardFamilyPin` closes (`nftables.go` comment on it). |
| D2 | **A host with no IPv6 container network gets a ruleset byte-identical to 2.23.2** — with two named exceptions: under `ipv6.mode = "block"`, a forwarded rule's IPv6 sources no longer render (D3); and a container-network list holding no usable network at all (only comments, say) no longer renders forwarded accepts with no deny beside them. | The release fixes a gap; it must not move anybody who is not in it. Both exceptions touch only a configuration that contradicted itself, and both change toward closed. Pinned by a golden captured on the pre-2.24 base. |
| D3 | **`ipv6.mode = "block"` keeps IPv6 away from containers.** IPv6 prefixes are removed from the container networks where Apply assembles them — detected ones and `custom_networks` alike, once, for every consumer — and a forwarded rule's IPv6 sources are skipped, so no IPv6 twin, deny or container exception renders and IPv6 to a container meets policy drop. `routing.networks` is not a container network and is untouched. | "No business speaking IPv6" (`models.go`, IPv6Block) is a statement about the host; a container reached through it is the host speaking IPv6. `filter` and `passthrough` both handle IPv6 in the forward chain like IPv4: passthrough is defined on the input chain only. |
| D4 | **Link-local (`fe80::/10`) is never a container network.** | Every bridge carries one; counting it would make every host an IPv6 container host and render IPv6 twins everywhere, breaking D2. |
| D5 | **A bridge the rules in force do not know is a warning, not a re-apply and not a health state.** Named in `easywall-core status` and on the dashboard; `/healthz` and `health` unchanged. The wording is neutral — *not in the rules in force; apply to include it* — because the effect depends on `routing.mode`. | Maintainer's choice ("warning only"). The firewall still enforces the ruleset it says it enforces; one apply fixes the gap. Under `routing.mode` `closed` or `networks` the unknown network is more closed than intended (its containers' new connections meet policy drop); under `open` it is less (no per-bridge deny for it), so no single consequence may be printed. `degraded` would page monitoring and restart a container healthcheck for a state one apply fixes. Nothing changes the kernel without the operator. |
| D6 | **The published-port check reads the `ip6` family too — and reads the DNAT the way Docker's iptables backend writes it.** | Its own comment calls the IPv6 gap inherited; `features/docker.md` tells operators to check IPv6 by hand. Found while planning: `iptables-nft`/`ip6tables-nft` 1.8.11 write `-j DNAT` as an xtables target (`target name DNAT rev 2`, decoded by google/nftables as `*xt.NatRange2`), not an nft `nat` expression — dumped from a live kernel 2026-09-26. The check reads only `expr.NAT`, so since 2.20.1 it has named nothing on any host where Docker uses its default iptables backend. Its integration fixture is written with `nft -f`, which produces the other encoding, and so passed. Fixed here, both families. |

## 2 · The forward chain

Order unchanged; the IPv6 lines render only under D1's condition and never under
`ipv6.mode = "block"` (D3):

```
ct state established,related                       accept
<forwarded rules>  meta nfproto ipv4 … dport N     accept    today
<forwarded rules>  meta nfproto ipv6 … dport N     accept    new
ip  daddr <v4 bridge> ip  saddr != <v4 bridge>     drop      today
ip6 daddr <v6 bridge> ip6 saddr != <v6 bridge>     drop      via detection
<bridge / routing exceptions, both families>       accept
                                                   policy drop
```

A forwarded rule with sources renders as today: `portAcceptRules` emits one
kernel rule per source, each carrying its own family from `cidrMatch`, and
nothing here re-pins it — except under `ipv6.mode = "block"`, where the forward
chain skips a forwarded rule's IPv6 sources (D3). Without that, an IPv6 source
named on a forwarded rule would still carry IPv6 to anything the host routes,
past the statement `block` makes.

`forwardPortRulesRender` and `addForwardPortRules` keep their guard: no container
network at all renders nothing. "Container network" now means either family.

## 3 · A bridge the rules do not know

- The manager records, at every successful write, the container networks the
  forward chain was built over (after D3's filter), as CIDRs — the comparison is
  by network; the interface is taken from detection at the time of the question.
- `STATUS` gains `unknown_bridges`: every current bridge network (detected now,
  D3-filtered) absent from that record, as interface + CIDRs. Empty when Docker
  coexistence is off, when `allow_bridge_networks` is off, or in panic mode.
- `easywall-core status` prints one line per interface: *docker:     network
  br-4f2a (172.20.0.0/24, fd00:…/64) exists and is not in the rules in force:
  apply to name it*.
- The dashboard shows *Docker network br-4f2a (…) exists and is not in the rules
  in force. Apply to include it.* as an `alert-warn` with a link labelled like
  the sidebar's *Apply Rules* (`nav_apply`) to `/apply`, in `en`, `de` (and `fr` where its catalogue has the surrounding
  keys). The demo mock returns one unknown bridge so the notice can be reviewed.
- A bridge that disappeared is not reported: rules naming a vanished network
  cost nothing.

## 6 · Out of scope

- Accepts bound to container destinations (approach B) — IPv4 behaviour change,
  its own release if ever.
- Re-applying on its own when a bridge appears after boot (D5).
- IPv6 NAT or masquerade by easywall — Docker's.
- Interface-bound rules (roadmap *Every rule knows its interface*).
