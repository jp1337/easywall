# 2.23 — Other people's lists

Curated IP blocklists, each switched on individually, all off by default — and
the words *blacklist* and *whitelist* leave the product.

Pulled forward from roadmap row 2.26. Country zones, which shared that row, get
their own release. Everything from the old 2.23 (metrics) onward moves back one
number.

## 0 · Decisions, and what decided them

| # | Decision | Evidence |
|---|---|---|
| D1 | Feed sets live in `table inet easywall`. `Apply` builds them from the core's stored copy; a refresh replaces a set's contents without a rebuild and without an acceptance window | A second table cannot order a feed after the allowlist — sets are not referenced across tables — and panic/rollback would have two tables to handle. Research §code 2, §crowdsec "The bouncer" |
| D2 | Switching a feed on or off is a **rule change**: staged, applied, 120 s window. Refreshing a feed that is already on is not | A feed can block half the internet; the switch deserves the same net as any rule. An hourly window would be unusable |
| D3 | Feeds are evaluated **after** the allowlist; the manual blocklist stays **before** it | Roadmap spec 2026-08-16 §2.18 "The finding that shapes this release most" |
| D4 | The core strips private and reserved ranges from every feed, unconditionally | FireHOL level1 carries 10/8, 172.16/12, 192.168/16, 100.64/10, 127/8; Hagezi TIF carries 100.83.3.144 and three 240/4 addresses. Research §feeds finding 1–2, §pihole 4 |
| D5 | The change guard is on **shrink only**: refuse a version with fewer than 70 % of the previous entry count | CINS rotates 13.9 % of 15 000 entries in 68 minutes at constant size; a symmetric-difference guard would refuse it. Research "Churn, measured" |
| D6 | Refuse any prefix broader than /8 (IPv4) or /16 (IPv6) | The broadest in any offered feed today is /12 and /29 (Spamhaus DROP) |
| D7 | No never-block set for gateway, resolvers or feed hosts | easywall filters new inbound connections only; replies to its own fetches and lookups are `established` and accepted before any feed (`nftables.go` input order). Pi-hole needs one because DNS blocking hits outbound names |
| D8 | Up to three **own feeds**: a URL, optional HTTP Basic credentials, plain-text format | Covers CrowdSec's per-user integration endpoint and any other list, with the same core guards. Research §crowdsec answer 2 |
| D9 | No list published from root01xvp in this release | One sensor behind the Hetzner firewall sees SSH brute force only, which blocklist.de and DShield already publish; publishing IPs needs a GDPR balancing test, a delisting channel and an Art. 30 record. Research §root01xvp 6. Recorded on the roadmap as deferred |
| D10 | Blacklist → **blocklist**, whitelist → **allowlist**, everywhere, with migration | The maintainer's decision. Stored names are read in both spellings and written in the new one |
| D11 | The interface calls the external lists **Feeds** (de: *Fremdlisten*) | After D10, "blocklist" names the operator's own list; the other word marks the one they did not write — the difference D3 turns on |

### Quality: false positives, and what we recommend

A false positive here means **a legitimate client can no longer open a
connection to this host** — a visitor, a webhook sender, a mail server
delivering, your own monitoring. Outbound traffic is never affected (D7).
Measured 2026-09-24 against AWS `ip-ranges.json`, GCP `cloud.json` and
Cloudflare `ips-v4` (research "Churn, measured" and §feeds).

| Feed | Bogon / private entries | Cloud IPs | Tor exits | False positives | Why | Verdict |
|---|---|---|---|---|---|---|
| Spamhaus DROP | 0 | 0 | 0 | **practically none** | curated netblocks handed to criminals or hijacked; in every peer tool's default set | ✓ **recommended** |
| DShield | 0 | 0 | 0 | **practically none** | 20 /24 networks with the most scanning sources right now | ✓ **recommended** |
| blocklist.de | 0 | 1033 (3.3 %) | 95 | **some** | fail2ban reports, 48 h window: dynamic and recycled addresses, some Tor | ✓ recommended for a server with SSH, mail or login pages |
| CINS Army | 0 | 1299 (8.7 %) | 0 | **some** | own sensors, rotating 15 000; cloud addresses are reassigned | • optional |
| ET compromised | 0 | 177 (25.8 %) | 0 | **yes, notable** | a quarter are AWS/GCP addresses, which change owner | • optional; not for hosts receiving webhooks or monitoring from cloud providers |
| IPsum ≥ 3 | 0 | 1362 (7.0 %) | 183 | **yes** | aggregate of ~30 lists, some aggressive; overlaps the ones above | ✗ only if you know why |
| Hagezi TIF IPs | 4 (CGNAT, 240/4) | 1341 (1.7 %) | 587 | **yes** | large aggregate built for DNS blocking; stripped of the 4 by D4 | ✗ only if you know why |
| Tor exits | 0 | 0 | 1370 | **by design** | blocks every Tor user, legitimate or not | ✗ only for hosts that must refuse Tor |

- The three marks follow firebog: **✓** least likely to lock out a legitimate
  client · **•** useful, with a stated cost · **✗** a deliberate choice, not a
  default. "Only if you know why" is the text, not a hidden flag.
- **Start with** Spamhaus DROP and DShield. That is the sentence at the top of
  the Feeds card and of the how-to page. Nothing is switched on for the
  operator (principle 4).
- The verdict, the false-positive level and its *why* are catalogue fields,
  rendered on the row and in the reference table; they are not prose that can
  drift from the data. A test checks that every catalogue feed carries all
  three in both locales.
- The figures are a snapshot. They go into the reference table with their
  date, and the release that changes a feed's verdict re-measures it.
- **Rejected**, with reasons in research §feeds: FireHOL (bogons), GreenSnow
  (no republication), AbuseIPDB (non-commercial, 5 calls/day), Feodo (5
  entries, stale since March), EDROP (merged, 0 entries), Talos (403),
  dan.me.uk (200 with an error sentence), Dataplane, Artillery, ThreatView,
  darklist.de, botvrij.
- **Spamhaus**: the name may not be used in marketing (terms §3.2). The
  interface names the list; `docs/` and the changelog describe it, never
  advertise it.
- The catalogue is Go data in `internal/shared` — id, name, URLs, format,
  interval, verdict, false-positive level and its why, homepage, terms URL.
  The core uses only the ids.

## 2 · Data model

| Where | What | Size |
|---|---|---|
| `shared.Rules.Feeds []string` | enabled feed ids (catalogue ids and `own-1`…`own-3`), in Current/Staged/Backup | a few bytes; enters `DiffRules` and `IsEmpty` by their existing reflection guards |
| `<data_dir>/feeds.json`, root 0600 | per feed: validated prefixes, `changed_at`, `checked_at`, entry count, rejected count | up to 100 000 prefixes per feed. Directly in `data_dir` (`TestEveryCoreDataPathIsDirectlyInDataDir`) |
| `<data_dir>/web/feeds.json`, easywall 0600 | per feed: ETag, Last-Modified, last error, consecutive failures; own feeds' name, URL, user, password | on `stateFiles` |

Feed contents never enter `rules.json`: it holds three copies and `Status()`
re-marshals it on every poll (research §code 2).

## 3 · Two paths

```
switch on/off   UI toggle ─▶ SAVE_RULES(feeds) ─▶ APPLY_RULES ─▶ window ─▶ confirm | rollback
refresh         web timer ─▶ fetch ─▶ parse ─▶ UPDATE_FEED ─▶ core guards ─▶ store ─▶ swap set contents
```

### Refresh, web side

- One timer per feed enabled in Staged ∪ Current; interval from the catalogue
  (own feeds: 24 h, since CrowdSec's free tier allows one pull per day), plus a
  random offset per install.
- On enabling, the first fetch starts immediately, so the apply finds a copy.
- `http.Client`: 30 s total timeout, redirects refused, body capped at
  8 MiB after decompression, `Accept-Encoding: gzip`, `If-None-Match` **and**
  `If-Modified-Since` (GitHub raw honours only the first), User-Agent
  `easywall/<version> (+https://easywall-project.org)` — DShield asks for one
  that identifies the client.
- A `text/html` content type or a body whose first non-space byte is `<` is a
  failure, not a list. So is a 200 with zero parseable entries.
- Parsers: `plain`, `spamhaus-ndjson`, `dshield`. Lines that do not parse are
  counted, and the first five kept for display.
- 304 → `checked_at` only. Demo mode constructs no fetcher.

### Refresh, core side — `UPDATE_FEED`

The core trusts nothing the web process sends. In order:

1. Panic engaged → refuse.
2. Feed id is in the catalogue or `own-1…3`, and enabled in Staged or Current.
3. ≤ 100 000 entries. Each re-parsed with `netip.ParsePrefix`/`ParseAddr`,
   `::ffff:` unmapped.
4. Drop, and count, anything not globally routable: RFC 1918, 100.64/10,
   127/8, 169.254/16, 0/8, 224/3 including 240/4, the v6 equivalents.
5. Refuse the whole update if any prefix is broader than /8 or /16 (D6).
6. Refuse if the count is below 70 % of the stored count (D5). A first load has
   no stored count.
7. Write `feeds.json` atomically.
8. If the feed is enabled in **Current**: under `m.mu` and the apply slot, book
   the counters (`collectUsageBeforeWrite`), then `FlushSet` plus the new
   elements in **chunks of at most 64 KiB of attributes each, all in one
   batch**. `google/nftables` `SetAddElements` wraps its `uint16` length
   silently above 64 KiB (research §code finding D).
9. Audit entry: feed, count before and after, rejected count.

Every refusal leaves the previous version in the kernel and on disk.

Socket limits: 1 MiB → **4 MiB** each way; an over-long request answers
*request too large* instead of today's silent truncation into "invalid JSON".
`UPDATE_FEED` gets the 35 s deadline class. New command `GET_FEEDS` returns
counts, timestamps and counters, never entries. Protocol count 23 → 25.

### Apply, rollback, boot, resume

`Apply` builds one interval set per enabled feed and family,
`feed-<id>-v4` / `feed-<id>-v6`, from `feeds.json`, using the same chunked
writer. A feed with no stored copy yet gets an empty set, and its row says so.
Rollback, boot, `resume` and the Docker reconcile all go through `Apply`, so
they need nothing else. Panic deletes the table and the sets with it.

The rebuild is not atomic today: between `reset()` and the rule flush the table
has no chains (research §code finding C). Large sets lengthen that window. This
release **measures it** with 100 000 elements on the integration harness and,
if it grows, moves the set elements into the rule flush rather than adding a
flush of their own. A widened window is a defect this release causes (CLAUDE.md,
*A release fixes what it caused*).

## 4 · Rules in the kernel

Input chain order, with the new step:

```
… docker accepts → BLOCKLIST drops → ALLOWLIST accepts → FEED drops → port accepts …
```

One rule per feed and family: `ip saddr @feed-<id>-v4 counter drop`, preceded
by the rate-limited log rule under `log_feed_connections`. The counter carries
the reserved id `_feed-<id>`, so `Health()` and usage skip it and `GET_FEEDS`
reports it.

| Guard | Change |
|---|---|
| `shared.Reachable` | a feed step between allowlist and ports. `/apply`'s lockout verdict then reads *your address is in feed X* |
| `TestIntegration_ReachableAgreesWithTheKernel` | extended with a feed hit |
| new `TestIntegration_AllowlistIsEvaluatedBeforeFeeds` | pins the order by the kernel's rendering |
| `TestIntegration_BlocklistIsEvaluatedBeforeAllowlist` | renamed, unchanged |
| source-order guards (`daemon_source_order_test.go`, `usage_collect_test.go`) | widened to the new writer: panic re-check, counter booking, apply slot |

## 5 · Interface

Folded into the blocklist page; no sidebar entry.

- A **Feeds** card below the manual list, headed *Start with Spamhaus DROP and
  DShield*: one row per feed — name, what it blocks, the verdict mark (✓ • ✗),
  false positives with their one-line why, entries, status, *changed* and *checked* as two fields, packets
  blocked since the last apply, a toggle.
- Status, from Pi-hole's five: never fetched · updated · unchanged ·
  failed, previous copy active · failed, no copy.
- Warnings on the row: *unchanged for 30 days* (the check that would have
  caught Feodo) · *contains N addresses from your allowlist, which stay
  reachable* · *failed N times in a row*.
- ✗ feeds confirm before staging, naming who they lock out.
- **Own feeds**: name, URL, optional user and password; the password is
  write-only in the form.
- The *order matters* aside states the three steps: your blocklist, the
  allowlist, the feeds.
- `/blocked`: prefix `easywall feed: `, one new rule name `feed` in
  `PacketLogRules`, the feed id in a new `PacketLogEntry.Feed`, label
  *Feed: Spamhaus DROP*, remedy *add to allowlist*.
- Rendered and checked in both themes at 1600 / 900 / 390 through the Chrome
  extension; screenshots of blocklist, allowlist and `/blocked` re-taken.
