# 2.18 — A password alone is not enough

easywall has had a second factor since 2.8, and it has been a checkbox. An
operator who reads nothing and presses the button ends up with a firewall
interface reachable over the network behind one argon2id hash. `firstrun.html`
offers the factor; `handleFirstRunSkip` exists so it can be declined; and
`handleLoginPOST` reads `secret == ""` as *this login is finished*.

This release removes that path. A second factor becomes a precondition for
using the interface at all, on every installation except the public demo — and
because making something mandatory is only defensible if the good version of it
is available, the release also brings the two things that stand between an
ordinary easywall installation and a passkey: a certificate a browser believes,
and WebAuthn itself.

Agreed with the maintainer on 2026-09-10: **one release, not three**, after the
decomposition into 2.18/2.19/2.20 was proposed and declined; the gate is not
skippable and not deferrable; ACME is pulled forward out of 3.0; multi-user
support (the old 2.28) is dropped rather than deferred.

## 0 · The base this starts from

Nothing here is built from nothing. Four pieces already in the tree carry most
of the weight, and the design is largely a question of where they plug in.

| Already there | Where | What 2.18 does with it |
|---|---|---|
| A complete TOTP implementation | `internal/web/totp.go`, `totpreplay.go` — enrollment, step-replay refusal, recovery codes, `credentialFingerprint` session invalidation, `totp_enabled`/`totp_disabled` audit events | Nothing is rewritten. The factor stops being optional; the machinery is untouched |
| `autocert` | `golang.org/x/crypto/acme/autocert`, already in the module graph because `x/crypto` is a **direct** dependency for argon2 | ACME costs **zero** new dependencies |
| `certManager` | `internal/web/tlscert.go` — `GetCertificate` is already the `tls.Config` hook, `ensure()` already means *make sure one exists*, `maintain()` is already the renewal ticker | Gains a third certificate source beside self-signed and operator-supplied |
| A JSON store written on every login | `internal/web/totpreplay.go` — atomic write, corrupt-file tolerance, one warning rather than one per attempt | Is the shape `passkeys.json` copies, including its error handling |

One thing is genuinely new: `github.com/go-webauthn/webauthn`. Hand-writing
CBOR decoding, COSE key parsing and attestation verification is not a place to
save a dependency.

## 1 · Why passkeys could not have come earlier, and what changed

The roadmap placed passkeys at 3.1, after the API, on one stated ground:
WebAuthn requires a registrable domain as its Relying Party ID and rejects a
bare IP address. That ground still holds — it was re-checked on 2026-09-10
against WebAuthn **Level 3** (W3C Candidate Recommendation, February 2026) and
is unchanged from the 2020 working-group decision. Only `localhost` is
exempted.

The roadmap named one blocker. There are two.

| Blocker | Consequence for a default easywall installation |
|---|---|
| A bare IP is not a valid RP ID | `https://192.168.1.10:12227` cannot begin a ceremony at all |
| Since Chrome 110, WebAuthn is refused on any origin with a TLS certificate error — and `--ignore-certificate-errors` explicitly does not lift it | `tlscert.go:78` generates a self-signed certificate by default, so even `https://firewall.lan:12227` cannot begin one |

So passkeys reach exactly the installations that have **both** a real hostname
and a certificate a browser trusts: a reverse proxy on the operator's own
domain (already documented in `docs/_docs/security.md`), an operator-supplied
Let's Encrypt pair through `[tls] cert`/`key`, or a Tailscale `*.ts.net`
name — and, after this release, anyone who turns ACME on.

That is a minority of installations and the release is honest about it. It is
also why the mandatory factor is **TOTP**, which works on every installation
including a bare IP behind a self-signed certificate, and why passkeys are the
better factor rather than the required one.

## 2 · The gate

### What it does not do

It does not lock anyone out. `handleLoginPOST` keeps granting a session when
`s.cfg.TOTPSecret() == ""`. An operator whose firewall host they can only reach
through this interface must never be shut out of it by an upgrade — that is the
direction 2.7 exists to prevent, and a mandatory-2FA release that strands
somebody is a worse outcome than the one it fixes.

### What it does

A new middleware in the authenticated route group, mounted immediately after
`RequireAuth` (`server.go:435`):

```
RequireSecondFactor
  ├─ DemoMode?                                     → pass
  ├─ TOTPSecret() != "" || len(Passkeys()) > 0 ?   → pass
  ├─ path ∈ {/password, /password/2fa/*,
  │          /password/passkey/*, /logout}
  │  or prefix /static/ ?                          → pass
  └─ otherwise                                     → 303 → /password
```

Every other route redirects. There is no *remind me later*, because the
version of this feature that has one is the version that never gets used.

**The gate has no page of its own.** Enrolment already lives at `/password`,
with `handle2FABegin`, `handle2FAConfirm`, `handle2FADisable` and
`handle2FARecovery` behind it (`server.go:474-477`) — the QR code, the
confirmation step, the recovery codes and the re-stamp are all there. A
dedicated `/2fa/setup` would be a second copy of a flow that already works.
What `/password` gains is a state: when no factor exists it renders with the
requirement stated at the top, and the page it redirects back to on success is
the dashboard rather than itself.

Letting `/password` through the gate also lets the operator change their
password while ungated. That is their own account and costs nothing.

### What the wizard loses

`handleFirstRunSkip` is deleted and the `WantTOTP` checkbox with it; the TOTP
step becomes unconditional. `firstRunData.WantTOTP` goes, and with it the
comment explaining that the checkbox survives a rejected submission.

### The re-stamp, which is easy to miss

`credentialFingerprint(passwordHash, totpSecret)` is compared on every request,
so enrolling a factor invalidates every session — *including the one doing the
enrolling*. `auth.go` already describes the remedy for the settings page: "the
acting one is re-stamped exactly as a password change already does". The gate's
confirm handler must re-stamp for the same reason, or it throws the operator
out in the middle of the step it just forced them into.

The domain separator goes **v2 → v3**, because the fingerprint must also cover
the passkey credential set. Without that, removing a lost device's passkey
would leave every existing session running — which is precisely the case the
mechanism exists for. Every session in flight across the upgrade ends once;
that is the correct direction and it earns a changelog line, exactly as the
v1 → v2 change did in 2.8.

### The last factor cannot be removed

`handle2FADisable` exists and today always succeeds. Under a mandate it must
refuse when it would leave the account with nothing — and the same rule governs
removing a passkey. One predicate, checked in both places:

```
mayRemove(factor) = DemoMode || (factors after removal) > 0
```

Written once and called twice rather than expressed twice, because two copies
of a rule is how the second one comes to disagree. Without it the mandate has a
front door and a back door, and only the front one is locked.

### Recovery codes

Eight codes are generated and shown once, at the enrolment of the **first**
factor, whichever it is — TOTP through `handle2FAConfirm`, or a passkey. Today
they are minted only on the TOTP path, because that is the only path there was;
an account whose single factor is a passkey on a lost phone must not be an
account with no way back.

They are not a factor and the predicate above does not count them: recovery
codes are what is left when both factors are gone, not one of the things that
can satisfy the requirement.

## 3 · The certificate

`certManager` gains a third source. Today it has two — a self-signed
certificate it generates and renews (`sslDir != ""`), and an operator-supplied
pair it reloads but never overwrites. ACME is the third:

| Source | `GetCertificate` | `ensure()` | `maintain()` |
|---|---|---|---|
| self-signed | reads the files, re-reads on mtime change | generates when missing or within 30 days of expiry | 12-hourly tick |
| operator-supplied | same | no-op | no-op |
| **ACME** | **delegates to `autocert.Manager.GetCertificate`** | **no-op** | **no-op — autocert renews itself** |

### HTTP-01 only

TLS-ALPN-01 is refused because it must be served on port 443, which easywall
does not listen on and which is usually already taken on a host that has a
domain pointed at it. DNS-01 is refused because it requires the DNS provider's
API credentials in `web.toml` — and *Deliberately excluded* already rejects
SMTP notifications on exactly that ground, with less at stake than a token that
can take over the domain.

One challenge type, one story, one port.

### Three consequences, all unavoidable

**A second listener on :80, permanently.** Not only during a challenge:
autocert renews at a time it chooses. It serves
`/.well-known/acme-challenge/` and answers everything else with 404 —
deliberately not autocert's default handler, whose HTTPS redirect points at
`https://host/` on port 443, where easywall is not.

**`AmbientCapabilities=CAP_NET_BIND_SERVICE` in
`systemd/easywall-web.service`.** The unit file already names this as the thing
to add for a privileged port. It composes with `NoNewPrivileges=yes`: ambient
capabilities are granted by systemd at exec rather than acquired by the
process.

**Port 80 must be open in easywall's own rule set.** The firewall has to open
a port for its own certificate, and easywall does **not** do it silently. A
firewall program that opens ports on its own initiative contradicts the entire
design. Instead the settings page reads the current rule set and says whether
80 is open — 2.17's principle, *measure rather than assert*, applied to a new
question.

### The terms of service are not accepted on the operator's behalf

`autocert.Prompt` is not wired to `autocert.AcceptTOS`. `acme = true` without
`acme_agree_tos = true` is refused at startup with a message naming the
setting. Accepting a third party's legal terms for somebody is not a default a
program gets to choose.

## 4 · Passkeys

| Decision | Reason |
|---|---|
| **Second factor, never a replacement** | The ceremony lives at `/login/verify`, as an alternative to the code field — not at `/login`. This is what the roadmap has said since 2.8, and it means a stolen phone is not a login |
| **RP ID is the configured hostname** | The same `[tls] hostname` ACME uses. One value, two uses. No hostname, no passkeys |
| **Stored in `passkeys.json` under `DataDir`, not `web.toml`** | The signature counter increments on every login. Rewriting the config file per login is wrong; `totpreplay.go` already writes a JSON file per login and is the model, error handling included |
| **Several passkeys, each with a name and an enrolment date** | One is a device that can be lost. Recovery codes remain the last way in, independent of both factors |

### When they are not possible

The card is rendered, disabled, and says which of the three things is in the
way: `no hostname is configured`, `reachable over an IP address`, or `the
certificate is not one a browser trusts`. Not "unavailable" — the operator
needs to know which one to change.

### The open question

`go-webauthn/webauthn` conventionally expects a server-side session store to
hold the challenge between the two halves of a ceremony. easywall deliberately
has none: `newPendingStore` is a cookie, because "a map any stranger can fill
is memory any stranger occupies". The challenge will almost certainly ride in
the same signed, `Path=/login`, short-lived cookie as `pendingLogin`, but this
is the one part of the design that is a prediction rather than a reading. If
the library cannot be driven that way, the fallback is to use its lower-level
protocol functions directly and keep the cookie.

## 5 · Configuration

```toml
[tls]
cert = ""                # unchanged
key  = ""                # unchanged
hostname       = ""      # new — the RP ID, and the ACME domain
acme           = false   # new
acme_email     = ""      # new, optional: Let's Encrypt expiry warnings
acme_agree_tos = false   # new, required when acme = true
acme_directory = ""      # new, empty = production; Pebble in tests
```

`acme = true` together with `cert`/`key` is a configuration error refused at
startup. `config.go:167` already refuses `cert` without `key` in the same
shape, for the same reason: two answers to one question is not a default, it is
a bug waiting to be discovered in production.

Unknown keys stay tolerated — easywall has never used
`DisallowUnknownFields`, which is what makes a downgrade survivable.

## 6 · Demo mode

| | |
|---|---|
| The gate | **Off.** The demo has no account belonging to anybody |
| Passkey enrolment | **Off, explicitly.** The demo runs behind a real domain, so passkeys *would* work — and then any visitor could leave one behind |
| The passkey card | **Shown**, disabled, reading `switched off in the demo`. It is a feature the demo exists to show |

## 7 · What has to be proven

CLAUDE.md requires a test to be verified by breaking the code, not by reading
it. Five carry this release, and each is written so that the mutation which
should break it does:

| Test | Goes red when |
|---|---|
| `TestTheGateCannotBeWalkedPast` | Any authenticated route answers 200 without a second factor. It walks **every registered route**, not a chosen list — a test over a list protects the list, not the principle |
| `TestTheDemoIsExemptAndNothingElseIs` | The exemption fires on anything other than `DemoMode` |
| `TestEnrollingReStampsTheActingSession` | The fingerprint change ejects the operator mid-enrolment |
| `TestTheLastFactorCannotBeRemoved` | Either removal route drops the count to zero. Both routes, one test — a test that covers only `handle2FADisable` leaves the passkey door open |
| `TestACMEIsRefusedWithoutAgreedTerms` | `acme = true` starts without `acme_agree_tos` |
| `TestPasskeysAreRefusedWithoutAHostname` | A ceremony begins with an empty RP ID |

Plus an integration test against **Pebble**, the ACME test server —
`x/crypto/acme` ships `pebble_test.go`, so the pattern is already in the module
cache rather than being invented here. And `npm run check:ui` gains the gate
path: it is the first screen an operator sees after the upgrade, and this
repository's rule is that an interface is verified by rendering it.

## 8 · What travels with it

A fix carries its documentation, and a release fixes what it caused. Two
defects found while assessing the project on 2026-09-10 are folded in rather
than carried:

**The landing page.** `docs/index.md:55-69` carries `.docs-landstrip`,
`.docs-cardgrid` and three `.docs-card`; `web/src/docs.css` defines none of
them and Tailwind generates none, so the section renders as unstyled prose at
full page width. It is the first page a stranger sees. It has been in
`carried-forward.md` for two releases because
`TestTemplateClassesExistInStylesheet` covers `web/templates/` and `app.js`
only — so the test is widened to `docs/` in the same change, or the next one of
these survives two releases too.

**`/system` has two buttons with one name.** `Save system settings` appears
after *Acceptance window* and again after *Installation count*. Each gains its
section in its name.

| Change | |

| **2.28 — More than one account** | Moved to *Deliberately excluded*. A side effect worth recording: 2.28 was the reason `WriteAuditLog` carries a `user` field that has said `web` since it existed. Passkeys give the field a better use — *which credential* signed in |
| **3.1 — Passkeys** | Removed; absorbed here |
| **3.0 — Reachable from outside** | Keeps its number, and loses its ACME clause, which moved here |
| **Everything from the old 2.18 to the old 2.27** | Moves back one place |
| **2.29 and 2.30** | **Keep their numbers.** Dropping 2.28 cancels the insertion exactly |

The notifications release that was 2.18 becomes 2.19, and it arrives with its
design decisions already taken on 2026-09-10: a generic webhook plus ntfy, one
switch per event, three attempts with backoff and then a journal line, and
https-only destinations. Those go into its own spec unasked.
