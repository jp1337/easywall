# 2.10 — What changes is on the screen

**Date:** 2026-08-21 · **Status:** approved, not yet executed

Not published. This directory sits outside `docs/`, which is the entire Jekyll
source — see `TestTheTechnicalDocsAreNotPublished`.

**The sentence:** before you press Apply, the interface tells you what will
change and whether the staged set still admits a new connection from the
address you are reading it on.

> **Amended 2026-08-22, after review, before release.** Three wordings below
> were corrected: the blocked verdict reads **blocks new connections**, never
> "cuts your connection" — the old phrase claimed exactly what *What the
> wording must not claim* (§3) says applying rules does not do, and a reader
> who tested that claim against a page that kept answering would have learned
> to distrust the warning. `ReasonDockerNetwork` split in two: the case named
> in `docker.custom_networks` stays `docker_network` (`open`), the
> auto-detected bridge pool is a new `ReasonDockerBridge` (`unknown`) — one
> sentence could not honestly stand next to both a green verdict and an amber
> one. And `Reachable` gained a seventh argument, `local`, decided by the
> caller from `net.InterfaceAddrs()`: the kernel's first input rule accepts on
> the *arrival interface* (`iifname "lo"`), not the address, so a connection to
> any address the host itself holds is accepted before a rule is consulted —
> without it, an operator at the console on the host's own LAN address was told
> a working connection was about to be cut. All three are reflected below and
> shipped in `internal/shared/reach.go`.

---

## The situation

Everything needed for a preview is already stored. `GET_RULES` returns
`RulesState{Current, Staged, Backup}`; `shared.DescribeRuleChange` and
`DescribeStructChange` already turn a before/after pair into text for the audit
log. What the apply screen does with all of that today is one boolean:

```
Status.HasPending  ->  "You have staged changes that the running firewall
                        does not have yet."
```

Six rule sets, any number of edits, one sentence. The operator applies without
being told what, and the acceptance window — 120 seconds — is where they find
out.

### Half the interface is missing from that boolean

`HasPending` comes from `rules.HasPendingChanges()` (`firewall.go:526`), which
compares `Current` against `Staged` and nothing else. Firewall options and
network settings are written straight into the core's config
(`daemon.go:373`, `:390`) and take effect only at the next apply. They are not
part of any pending calculation, so two pages contradict each other:

| Page | What it says | |
|---|---|---|
| `/options` after a save | *Options saved. Apply rules to activate changes.* | `options_saved` |
| `/apply`, same moment | *The running firewall matches what is staged. There is nothing to apply.* | `apply_lead_clean` |

The false one is on the page with the button. `Firewall.apply` does not refuse
an apply with no rule delta, so pressing Apply anyway does activate the option —
the operator just has to disbelieve the screen first.

### Two defects reported against the running demo

**The forwarding rows are out of line.** `web/src/app.css:1415` puts
`display: flex` on a `<td>` (`.cell-flow`), which stops the element being a
table cell: the browser wraps it in an anonymous cell and its box no longer
shares the row's height or border. Measured on the demo at 1600px in both
themes, the row separator under the first two columns sits ~10px below the one
under the third. It is invisible below the 720px reflow breakpoint, where every
`td` is `display: block` anyway — which is why it survived. The comment above
the rule states the real constraint correctly (`.input-cell` is `width: 100%`,
so an inline arrow wraps onto its own line); the flex container belongs on an
element *inside* the cell.

**The audit log's address is the proxy's.** On the public demo a login records
`from 172.16.4.1`. `curl -I https://easywall.wdkro.de` answers with
`server: nginx` over HTTP/2, so that is nginx's address on a container network,
recorded faithfully as the TCP peer by `clientIP()` (`auditevents.go:78`).
Refusing `X-Forwarded-For` is deliberate and stays — the note at that function
and `docs-tech/threat-model.md` both say why. What is missing is the second
half: nothing tells the reader that the number is not the client. Behind any
reverse proxy the column is a constant that looks like a client address, on
every login, forever.

That is the same value 2.10's lockout warning has to reason about, which is why
it is in this release rather than filed separately.

## Decisions

| Question | Decision |
|---|---|
| Scope | The rule diff **and** the configuration drift. A preview that covers six rule sets and ignores thirty-one options is not "what changes" |
| Where the diff is computed | In the web process, as pure functions in `internal/shared`. The privileged side gains no new parsing of network-facing input |
| How the core exposes the missing half | One new command, `GET_APPLIED_CONFIG` — the 19th. `RulesState` is not widened |
| Whether the core still owns "is anything pending" | Yes. The core answers *whether*, the web process answers *what*. Two definitions of pending would be worse than the current one |
| Lockout analysis | Three verdicts: reachable, blocks new connections, cannot tell. Every "cannot tell" names its reason |
| Automatic anti-lockout rule | Refused. See *Why nothing is opened automatically* |
| Add/remove colour | Structural (`+` / `−` / `~` in mono), never chromatic. DESIGN.md reserves green and red for firewall state |
| New sidebar entry | None. The roadmap's rule 5 holds: this folds onto `/apply`, which already exists |
| The 40px countdown and a rollback endpoint | Out of scope. Named in DESIGN.md's *Known Gaps*, a different theme, its own release |

## 1. The applied-config snapshot

### What it is

```go
// internal/shared
type AppliedConfig struct {
    Firewall FirewallOptions `json:"firewall"`
    Network  NetworkSettings `json:"network"`
}

type AppliedConfigResult struct {
    Recorded bool          `json:"recorded"`
    Config   AppliedConfig `json:"config"`
}
```

The configuration that went into the kernel with the rules that are in it.
Stored by the core in its data directory as `applied-config.json`, written with
the same atomic rewrite the rules store uses, mode 0600.

### Where it is written

Everywhere `nft.Apply` succeeds, and nowhere else:

| Call site | Why it counts |
|---|---|
| `Firewall.apply` after `nft.Apply` returns nil | the ordinary case |
| `Firewall.rollback`, after the guarded `nft.Apply` | the previous rules go back in with the config as it is *now*, not as it was |
| `Firewall.RestoreCurrent` (boot, and `resume`) | same reasoning; this is also what establishes the file on an upgraded installation |

Not written on a refused or failed apply: the kernel did not take it.

### A missing file claims nothing

An installation upgrading to 2.10 has no snapshot. That state means *unknown*,
not *identical*:

- `Status.HasPending` keeps its 2.9 meaning — the rule diff alone. No
  installation is greeted with a pending change it did not make.
- `/apply` says so in one sentence, once: the configuration that went into the
  kernel was not recorded before this version, and the next apply records it.
- The first daemon start under 2.10 runs `RestoreCurrent`, so in practice the
  file exists after the upgrade's service restart and the sentence is never
  seen. It is written for the case where it is.

### The 19th command

```
GET_APPLIED_CONFIG   payload: none   ->  AppliedConfigResult
```

Read-only, short deadline (`CommandTimeout`'s default — it touches one file).
Three guards already force the paperwork: `AllCommandTypes` must list it,
`TestAllCommandTypesMatchesTheProtocolSource` reads the source for it, and the
docs-coverage test requires `docs-tech/protocol.md` to document it.

### `HasPending` grows one clause

```
pending = rulesDiffer || (snapshotRecorded && configDiffers)
```

Computed in `Firewall.Status`, which already reads the rules store and has the
config. One consequence to carry through: the dashboard hero's *Unapplied
changes* chip and `/apply`'s lead sentence become true for an options change,
which is the whole point, and `options_saved` / `settings_saved`'s copy stops
being a workaround for a lie ("Options save immediately" was written to explain
away exactly this).

## 2. The diff

### Shape

```go
// internal/shared
type DeltaKind string   // "added" | "removed" | "changed"

type RuleDelta struct {
    Set   string    `json:"set"`   // "tcp" "udp" "blacklist" "whitelist" "forwarding" "custom"
    Kind  DeltaKind `json:"kind"`
    Key   string    `json:"key"`   // "8443", "192.0.2.42", "8080->80/tcp", "#3"
    Label string    `json:"label"` // the port description, when it has one
    From  string    `json:"from"`  // "changed" only
    To    string    `json:"to"`    // "changed" only
}

type ConfigDelta struct {
    Key  string `json:"key"`   // the toml key: "drop_fragments", "ipv6.mode"
    From string `json:"from"`
    To   string `json:"to"`
}

func DiffRules(current, staged Rules) []RuleDelta
func DiffConfig(applied, live AppliedConfig) []ConfigDelta
```

### What counts as a change, per set

Not one comparison. Each set is compared the way the kernel reads it:

| Set | Compared as | Why |
|---|---|---|
| `tcp`, `udp` | keyed by port | order does not change what is accepted; a description edit is `changed`, not add+remove |
| `blacklist`, `whitelist` | as a set, `IsListComment` lines skipped | distinct addresses, order irrelevant. A comment or a blank line is not a rule — the dashboard's `countListEntries` already established that |
| `forwarding` | keyed by (protocol, source port) | one redirect per incoming port |
| `custom` | as a sequence, index in `Key` | raw nftables rules are evaluated in the order they are written, so a moved line **is** a change |

### `DescribeStructChange` is refactored, not duplicated

It already walks two structs by reflection and names the fields that differ by
their toml tag. `DiffConfig` needs the same walk with the values kept rather than
discarded. One walker returning `[]ConfigDelta`; the audit-log string is built
from its result. The existing behaviour — including `maxDetailItems`, which
bounds the audit line and must not bound the page — is preserved by its own
tests.

### A forgotten field fails a test

Both diffs are reflection-checked against their inputs: every field of `Rules`
must be reached by `DiffRules`, every field of `FirewallOptions` and
`NetworkSettings` by `DiffConfig`. A seventh rule set or a thirty-second option
that the preview silently omits fails here rather than shipping as a preview
that under-reports. Same idiom as the existing guards, including the part that
matters most: a walk that matches nothing fails instead of passing.

## 3. The lockout verdict

### The question it answers

Not "will I be disconnected" — "can a new connection from this address reach the
interface once the staged set is live". The distinction is load-bearing; see
*What the wording must not claim*.

```go
// internal/shared
type ReachVerdict string // "open" | "blocked" | "unknown"
type ReachReason  string // a closed enum, localised by the web layer

func Reachable(r Rules, o FirewallOptions, n NetworkSettings,
               src netip.Addr, port uint16, proxied, local bool) (ReachVerdict, ReachReason)
```

A closed enum, never free text, for the same reason `LoginEvent` is one: this
text ends up on a page and in two locale files, and a sentence assembled in Go
cannot be translated.

### The model

`nft.Apply` builds the input chain in one order, and that order is the whole
algorithm. Chain, in the order rules are appended, with what each means for a
single TCP connection from `src` to `port`:

| # | Rule | Verdict |
|---|---|---|
| 1 | loopback accept | `open` · `loopback` |
| 2 | IPv6 mode: passthrough / block | `open` · `ipv6_passthrough` / `blocked` · `ipv6_blocked` (IPv6 `src` only) |
| 3 | established/related accept | **not consulted** — a new connection is not established |
| 4 | ICMP | irrelevant to TCP |
| 5 | protection modules | rate limits: not a verdict. **Bogon filter**, when on and `src` is private and neither whitelisted nor a Docker network: `unknown` · `bogon_filter` |
| 6a | Docker bridge accepts — a network named in `docker.custom_networks` | `open` · `docker_network` |
| 6b | Docker bridge accepts — the auto-detected bridge pool | `unknown` · `docker_bridge` |
| 7 | blacklist drop | `blocked` · `blacklisted` |
| 8 | whitelist accept | `open` · `whitelisted` |
| 9 | tcp port accept | `open` · `port_open` |
| 10 | custom rules (appended by the nft CLI, after everything above) | `unknown` · `custom_rules`, when any exist and nothing above decided |
| — | policy | `blocked` · `no_rule` |

Read in order and stop at the first that decides. Three entries are earlier than
the chain suggests, or split, and must be checked first:

- `proxied` → `unknown` · `proxied`. If the peer is a proxy, `src` is not the
  operator's address and no amount of rule evaluation fixes that.
- `local` → `open` · `loopback`, ahead of step 1's own address check. The
  kernel accepts on the *arrival interface* (`iifname "lo"`), not on the
  address, so a connection to any address this host holds is routed over lo
  and accepted before a rule is consulted. `src.IsLoopback()` only catches the
  `127.0.0.0/8`/`::1` spelling of that; the caller enumerates this host's own
  addresses via `net.InterfaceAddrs()` and passes the rest as `local`, because
  reasoning about which interfaces exist on the machine is not this package's
  job.
- Step 5's bogon case is `unknown` rather than `blocked` because the rule matches
  on the arrival interface, which the web process cannot know.
- Step 6 is two reasons, not one, because a single sentence cannot honestly sit
  beside both verdicts it used to share: a network named in the settings is one
  this process can and does list (`open` · `docker_network`); the auto-detected
  bridge pool is settled in the core at apply time and cannot be enumerated
  here (`unknown` · `docker_bridge`, bounded to `172.16.0.0/12` so an ordinary
  `192.168.x` or `10.x` LAN address still gets a real answer rather than a
  shrug).

Why the bogon filter cannot be waved through: it drops RFC-1918 sources on
external interfaces, and easywall's own audience reaches the interface from
exactly such an address. Guessing either way here would produce the two worst
outcomes available — a false alarm on every LAN request, or silence on a real
lockout.

### What the wording must not claim

Flushing and rebuilding the table does not touch conntrack. The operator's
browser connection stays `ESTABLISHED`, matches rule 3, and keeps working after
an apply that closes the web port — so *this page may keep answering while the
firewall no longer admits anyone*. Confirming from it would confirm a lockout.

The copy therefore says what is true — new connections to `:12227` will not be
accepted — and repeats the discipline `apply_step2_desc` already asks for: open
a second connection and check there. It never says "you will be disconnected",
because that is the one thing that probably will not happen first.

### Why nothing is opened automatically

pfSense and OPNsense insert an implicit anti-lockout rule. In OPNsense that rule
has picked a WAN interface and published the web GUI and SSH on it
([opnsense/core#7372](https://github.com/opnsense/core/issues/7372)). easywall
already owns a safety net that costs nothing and opens no port: every apply
reverts itself after 120 seconds. A second net that quietly adds an accept rule
would trade the product's central promise for a convenience.

### Where the address and port come from

`clientIP(r)` and `s.webPort()`, both existing. `proxied` is new and is decided
by the **presence** of `X-Forwarded-For`, `X-Real-IP`, `True-Client-IP` or
`Forwarded` on the request — never their value. A client that forges a header
can therefore move the verdict to `unknown` and nothing else: it cannot insert
an address, cannot suppress a warning, and cannot reach the recorded peer
address. That asymmetry is what makes reading an untrusted header acceptable
here, and it goes in `docs-tech/threat-model.md` in those terms.

`local` is new too, and it is decided by the caller, not by `Reachable`: the
handler walks `net.InterfaceAddrs()` and reports whether `src` is one of the
addresses this host itself holds. `Reachable` is given an address, not an
interface, and `src.IsLoopback()` only recognises the `127.0.0.0/8`/`::1`
spelling of "this connection arrived on `lo`" — a connection to the host's own
LAN or public address is routed over loopback exactly the same way and needs
the same accept. A failed `net.InterfaceAddrs()` costs only the shortcut: the
chain below still answers, and a console-local operator gets the ordinary
verdict rather than a wrong one.

## 4. Proxy honesty in the audit log

The same signal, one field further down the protocol:

```go
type LogEventPayload struct {
    Event   LoginEvent `json:"event"`
    Addr    string     `json:"addr"`
    Left    int        `json:"left"`
    Proxied bool       `json:"proxied"`  // new
}
```

Still nothing free-text. The core's `immediateDetail` and the debounced summary
write one fixed token after the address — `from 172.16.4.1 via-proxy` — in the
log file, in English, where every other detail already is, and `grep 'via-proxy'`
finds every proxied login.

Rendering it needs one rule, because `detailLabel` is an exact-match lookup
against `auditDetailKeys` (`server.go:883`) and a detail carrying an address can
never be a map key: a detail ending in ` via-proxy` has the token stripped and
renders as the address plus a **neutral chip** reading *via proxy* in the
operator's language. A chip rather than a longer sentence because DESIGN.md
assigns informational marks to neutral chips, and because the Detail column is
scanned, not read.

Two comments in that area are stale and are corrected in the same pass:
`auditDetailKeys`' own note claims "almost every entry the core records carries
an empty detail", and DESIGN.md's *Known Gaps* says the detail column is a dash
almost every time. `DescribeRuleChange` has filled it since 2.5 — the demo's log
shows `6 ports removed (2 total)` and `+8443` today.

The demo's `handleLogEvent` gets the same suffix, so the public demo — which is
behind nginx and is where this was noticed — shows what a proxied installation
shows.

## 5. `/apply` becomes two screens

Today the page has one shape for four acceptance states. The diff belongs to
only one of them: while a window is open the change is already live, and a
preview of it is history.

```
IDLE, changes staged                          PENDING (window open)
┌ What changes ───────────────────────┐       ┌ Confirm ──────────────┐
│ ● 192.168.133.234 -> :12227         │       │  waiting for you      │
│   reachable                         │       │ [ Everything works ]  │
│                                     │       └───────────────────────┘
│  TCP ports                      2   │
│  +  8443   Nextcloud                │       The diff collapses to one
│  -    22   SSH                      │       line: "4 changes are live
│                                     │       and unconfirmed."
│  Blacklist                      1   │
│  +  192.0.2.42                      │
│                                     │
│  Options                        1   │
│  ~  drop_fragments      off -> on   │
├─────────────────────────────────────┤
│ [ Apply now ]   Rolls back in 120 s │
└─────────────────────────────────────┘
```

The action sits under the evidence, and the verdict sits above both — it is what
changes the decision. `accepted` and `rolled_back` keep today's panel; with
nothing staged the page keeps `apply_lead_clean` and shows no empty diff.

### The verdict line

One line, in the mono `data` role, naming the operator's own address and port —
the page's signature, and the only place the interface has ever said out loud
where the request came from:

```
●  192.168.133.234 -> :12227   reachable
◐  172.16.4.1      -> :12227   cannot tell
                               The request came through a proxy. That is its
                               address, not yours.
◉  192.168.133.234 -> :12227   blocks new connections
                               Port 12227 is not open in the staged set and
                               your address is not whitelisted.
                               [ Apply anyway ]   The window brings the
                               previous rules back after 120 seconds.
```

`blocked` replaces the primary action with a deliberate second one — a
differently-labelled button, not a filled red block (DESIGN.md: a filled red
button invites the misclick it warns about) and not a disabled control. An
operator who has decided is allowed to proceed; the acceptance window is what
catches them.

### Colour

Add and remove are `+` / `-` / `~` in the mono column and neutral chips, with no
hue at all. DESIGN.md's first rule is that colour outside the blue family means
firewall state, and a green/red diff would break it twice over: a new blacklist
entry is not good news and a removed port is not a failure. The three state
colours stay with the verdict, which genuinely is a state — `state-warn` for
`unknown`, `state-crit` for `blocked`, `state-ok` for `open`, each with the dot
*and* the word, as `Status` already requires.

### Elsewhere

The dashboard hero's *Unapplied changes* chip carries the count and keeps
linking to `/apply`. Nothing else changes, and no page is added.

## Proof

| Test | What it holds | Where |
|---|---|---|
| `DiffRules` / `DiffConfig` table tests | every set's comparison rule, comments skipped, a description edit as `changed`, a moved custom rule as a change | `internal/shared` |
| Reflection guards | every field of `Rules`, `FirewallOptions`, `NetworkSettings` is reached by a diff; an unmatched walk fails | `internal/shared` |
| `Reachable` table tests | the chain order, and the trap it exists for: **blacklist is consulted before whitelist**, so an operator's own address on both is blocked | `internal/shared` |
| **veth integration test** | for a set of generated rule sets: apply to a real kernel, send a real packet from a real source address to the port, assert the kernel's verdict equals `Reachable`'s. Extends the harness in `nftables_forward_test.go` | `internal/core`, `-tags integration` |
| Snapshot tests | written on apply, on rollback and on restore; absent file reports `recorded: false`; `HasPending` unchanged while unrecorded | `internal/core` |
| Protocol guards (existing) | `GET_APPLIED_CONFIG` is in `AllCommandTypes`, in the source switch, and in `protocol.md` | `internal/shared` |
| `ui-check.mjs` | all four cells of a `/forwarding` row share one top edge (±1px); the diff at 390px produces no horizontal overflow; no console error on `/apply` in either theme | browser |

## Risks

| | |
|---|---|
| The evaluator drifts from `nft.Apply` | The chain order is duplicated in two files by construction. The veth test is the coupling; a rule inserted into `Apply` without a matching branch shows up as a disagreement rather than as a wrong warning |
| A false "blocks new connections" | Costs trust in the one warning that must be believed. Every uncertain case is `unknown` with its reason on screen, never `blocked` |
| `HasPending` turning true for existing installations | Only once a snapshot exists, and a snapshot only exists after an apply or a restart under 2.10 — at which point it matches the live config, so nothing lights up spuriously |
| Scope creep toward the countdown | The apply screen is the page DESIGN.md most wants rebuilt. It is not this release |
