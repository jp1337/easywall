# 2.13 — Behind a proxy, easywall knows who you are

A list of trusted proxy addresses, configurable from the environment. When the
TCP peer is on that list, and only then, the forwarding header is read and the
resolved client becomes the truth in the audit log, the reachability verdict and
the login rate limiter. Demo mode stops recording login addresses at all.

Agreed with the maintainer on 2026-08-27, including the full scope over the
smaller display-only option.

## 0 · This pulls a 3.0 item forward, and amends the threat model

Two documents currently say otherwise and are amended **openly**, as part of this
release, not quietly:

- `docs/_docs/roadmap.md` schedules a trusted-proxy list inside **3.0**. It moves
  here; 3.0 keeps its number and loses that clause.
- `docs-tech/threat-model.md` §"Why `X-Forwarded-For` is ignored" states the
  condition this design must satisfy, and it is quoted here so no plan can lose
  it:

  > Making that configurable is on the roadmap and must be opt-in and explicit —
  > **a list of trusted proxy addresses, not a boolean**. A boolean that says
  > "trust the header" is the vulnerability those three advisories describe.

  The advisories are GHSA-3fxj-6jh8-hvhx, GHSA-rjr7-jggh-pgcp and
  GHSA-9g5q-2w5x-hmxf. A boolean is not an acceptable implementation of this
  spec under any circumstance.

## 1 · What exists today

- `buildRouter` deliberately does **not** use `middleware.RealIP`. `r.RemoteAddr`
  is authoritative everywhere.
- `clientIP(r)` (`internal/web/auditevents.go:78-84`) splits the host from
  `r.RemoteAddr` and nothing else.
- `proxiedRequest(r)` reads only the **presence** of `X-Forwarded-For`,
  `X-Real-IP`, `True-Client-IP` or `Forwarded` (`auditevents.go:88`), never a
  value. That flag marks a login `via-proxy` and moves the apply screen's verdict
  to *cannot tell*.
- The login limiter keys on `r.RemoteAddr`'s host directly
  (`internal/web/middleware.go:142-146`): five attempts per ten minutes, refilling
  one per two minutes, in an in-memory bucket map. Behind a proxy everyone shares
  one bucket — the cost the threat model already names.

## 2 · The design

One new setting, a **list**, configurable from the environment as 2.12
established:

```
EASYWALL_WEB_TRUSTED_PROXIES   trusted_proxies   list of addresses and CIDRs
```

Resolution, in one place, used by everything:

```
peer = host(r.RemoteAddr)
if peer is in trusted_proxies:
        client = the rightmost address in the forwarding header that is
                 NOT itself in trusted_proxies
        if none, client = peer
else:
        client = peer          # header ignored entirely, as today
```

Empty list — the default — must behave **byte-identically to 2.12**. That is a
test, not an intention.

## 3 · What the resolved client changes

| Surface | Today | After |
|---|---|---|
| Audit log address | the proxy | the client |
| `via-proxy` marker | on header presence | on *untrusted* header presence only |
| Reachability verdict | *cannot tell* whenever a header is present | a real verdict when the peer is trusted |
| Login rate limiter | keyed on the proxy — one shared budget | keyed on the client |

The limiter is the risky half and the reason the maintainer chose full scope: it
also fixes the shared-budget problem the threat model documents as a cost.

## 4 · The proof this release owes

A mistake in the list check is a rate-limiter bypass — precisely the three
advisories. Reading the code is not enough. This release carries a veth test in
the same spirit as 2.11's chain-ordering proof:

1. A forwarding header from a peer **not** on the list changes nothing —
   not the audit address, not the verdict, not the limiter's bucket.
2. A forwarding header from a peer **on** the list resolves to the client.
3. A header naming an address that is itself a trusted proxy does not let the
   caller pick its own identity (the rightmost-untrusted rule in §2).
4. Every assertion must **fail when the feature is reverted**. 2.11 produced five
   tests that were green while proving nothing; that must not repeat here, and a
   test whose failure mode has not been observed does not count as written.

## 5 · Demo mode records no login addresses

In demo mode the audit log stores no address for login events — the field is
omitted rather than filled with a placeholder, because it is already optional and
a dash would be one more line of code for the same statement.

This sits in this release, not 2.12, because its subject is which address is
recorded — the same surface the proxy list changes, in the opposite direction. In
the demo that combination is deliberate and coherent: the reachability verdict
shows the operator their real public address, while the audit log records none
for anyone.

## 6 · Documentation

- `docs-tech/threat-model.md`: the amendment from §0, plus what the list does and
  does not defend. Being on the list is total trust in that peer.
- `docs/_docs/` — the operator-facing page must state the failure mode plainly:
  listing a proxy that is not actually in front of easywall, or listing a network
  wider than the proxies it holds, hands address spoofing to anyone who can reach
  the port from inside it.
- `docs-tech/invariants.md`: the four guards from §4.
- CHANGELOG: *Added* for the list, *Changed* for the limiter now counting per
  client, which alters behaviour for anyone already behind a proxy.

## 7 · Scope

In: the list, its environment variable, the resolution rule, the four surfaces in
§3, the veth proofs, demo-mode address suppression, the two amendments.

Out: ACME, a REST API, anything else from 3.0. This release takes the
trusted-proxy clause out of 3.0 and nothing more.
