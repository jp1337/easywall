# 2.14 — The window shows that it is running

**Date:** 2026-09-02 · **Status:** approved, not yet executed

Not published. This directory sits outside `docs/`, which is the entire Jekyll
source — see `TestTheTechnicalDocsAreNotPublished`.

**The sentence:** while the rules are live but unconfirmed, the interface says how
long is left and offers the way back.

## Why this is a release and why it is this one

easywall's whole argument is one sentence: *every apply reverts itself after 120
seconds unless it is confirmed*. It is on the landing page, in `README.md`, in the
architecture diagram and in the name of the product's safety.

On screen, during those 120 seconds, it is a static clock glyph and the word
*Open*. Two screenshots taken nine seconds apart are pixel-identical. The operator
cannot tell 110 seconds from 4, and the aside says *"the default is 120 seconds"* —
a constant, not the state.

`DESIGN.md` has specified the fix since 2.10: a `countdown` role at 40px in
`state-warn`, and *"both actions offered plainly: confirm, or roll back now"*. It
also records why neither could be built — `shared.FirewallStatus` carries no
deadline and there is no rollback route. That entry has been in *Known Gaps*
across four releases because no feature on the roadmap justified the model change,
and the roadmap's own principle 2 says a model change travels with the feature
that justifies it. This release is that feature.

**Ordering.** The roadmap sorts by exposure. An unused open port (2.15, counters)
is a real exposure; a safety mechanism the operator cannot see running is the
product's central promise being unverifiable. This goes first, and everything
below it moves one place. See *What changes on the roadmap*.

## Most of it already exists

The gap turned out to be smaller than *Known Gaps* describes, and the description
should not be trusted again without reading the code.

| | Today |
|---|---|
| Remaining time | `Acceptance` holds `duration`; the timer is built inside `Wait()` from it. No instant is stored — but `Wait` is the one place that knows it |
| Rollback | **`Acceptance.Cancel()` exists and does exactly this.** It ends a pending window as *not accepted*, so `Wait` returns false and the caller rolls back. Written for shutdown; never reachable from the protocol |
| Transport | `GET /apply/status` already serialises the whole `FirewallStatus` as JSON and `app.js` polls it every 2 s. A new field arrives at the browser with no transport work |
| A live window in demo mode | `democlient.go` runs a real `acceptanceTimer` at 120 s and really rolls back to `Backup`. The window is fully drivable without a kernel |

So the work is one integer, one command, one route, and the screen.

## The defect this uncovered

`Acceptance.Start`'s doc comment says:

> It must be called before nftables rules are applied.

The only call site calls it **after**. `internal/core/firewall.go`: `f.nft.Apply`
returns at step 4; `f.acceptance.Start` is step 5. Between them run a panic-marker
stat, `recordAppliedConfig` (**a file write**), a settings read and a
`WriteAuditLog` (**a second file write**). On the hardware this product documents
itself for — a Raspberry Pi on an SD card — two file writes are not microseconds.

During that gap the kernel holds unconfirmed rules and `Acceptance.Status()` is
`Idle`. Two consequences, from code that is already in the tree:

1. `FirewallStatus.Acceptance` reports `idle` while unconfirmed rules are live, so
   the interface shows no window at all.
2. **A SIGTERM landing in the gap blocks shutdown for the whole window.** `Stop`
   calls `CancelAcceptance()` — which returns immediately, because the status is
   not `pending` — and then `wg.Wait()`. `APPLY_RULES` runs in a `d.wg`-tracked
   goroutine (`daemon.go`), which then reaches `Start`, opens the window and
   blocks in `Wait()` for the full duration, up to an hour. `Stop` waits behind
   it. systemd's `TimeoutStopSec` fires first and `SIGKILL`s the daemon, leaving
   the unconfirmed rules live — which is precisely the failure `Cancel` was
   written to prevent, and its own comment says so.

**Reproduced, and the fix in this section was half wrong.** Consequence 1 — the
interface showing no window while unconfirmed rules are live — is exactly as
described, and moving `Start` above `nft.Apply` fixes it. Consequence 2, the
shutdown hang, is real but this move does not close it: after the move the gap
between `wg.Add(1)` and `Start` still holds a rules read, a backup write, an
`nft` snapshot subprocess bounded at 30 s, a promote and a second read — a
*larger* wall-clock gap than the one removed. The root cause is that
`Acceptance.Cancel` discards a cancel arriving while the status is `Idle`, and
that is what was fixed: `CancelForShutdown` latches, so a window opening after a
SIGTERM opens already cancelled. See `TestAcceptance_ShutdownBeforeTheWindowOpensDoesNotOpenOne`.

**The fix is what the comment already demands:** move `f.acceptance.Start` above
`f.nft.Apply`. This is a change to the apply path of a firewall and is called out
here rather than folded in quietly.

**Its consequence, stated plainly.** The window then begins before the kernel
write instead of after it, so the kernel write and the two file writes are inside
the window rather than before it. On a fast host this is milliseconds; on a slow
SD card it could be a second or two of 120. That is the right direction: the
moment an operator can be locked out is the moment the rules land, not the moment
the bookkeeping finishes.

## 1 · The data

One invariant carries this section:

> **The number on the screen and the timer that fires come from one source.**

Today they cannot, because the number does not exist and `Wait` builds its timer
from a duration rather than an instant.

```go
// internal/core/acceptance.go
type Acceptance struct {
    // …
    deadline time.Time   // set by Start, cleared by Reset
}

func (a *Acceptance) Start(d time.Duration) error {
    // … existing idempotent early return for an already-pending window,
    //     which must NOT move the deadline
    a.deadline = time.Now().Add(d)
}

func (a *Acceptance) Wait() bool {
    // Read under a.mu like acceptCh/cancelCh already are, then:
    timer := time.NewTimer(time.Until(deadline))   // not a.Duration()
}

// Remaining is 0 unless a window is pending, and never negative.
func (a *Acceptance) Remaining() time.Duration
```

**`Duration()` is left with one caller, and that is worth saying out loud.** It has
exactly two today, both inside `acceptance.go`: the timer in `Wait` and the
`"duration"` field on the timeout log line. The change takes the first away. The
method and the `duration` field stay for the log line — a timeout entry that says
how long the window was is worth its two lines — but nothing may derive a *time*
from it again. That is the invariant above, stated as a rule about the code rather
than about the screen.

The configured length reaches `Start` as its parameter, from
`f.cfg.AcceptanceDuration()`, and that does not change. `AcceptanceDurationMax` is
3600 (`internal/shared/models.go`), so the longest window is exactly `60:00`.

`shared.FirewallStatus` gains one field:

```go
// AcceptanceRemaining is whole seconds left in the open window, 0 when none is
// open. Relative rather than an absolute instant on purpose: an absolute
// deadline is read against the browser's clock, and the machines a firewall is
// administered from are exactly the ones whose clocks drift — a Pi with no RTC,
// a laptop that just changed timezone, a VPN client. A relative count cannot be
// wrong about a clock it never crosses.
AcceptanceRemaining int `json:"acceptance_remaining"`
```

The browser ticks locally between polls and takes the server's number as the
correction on each one. `/apply/status` needs no change; `democlient.go` computes
the same field from its own `acceptanceTimer`.

### Rejected

| | Why not |
|---|---|
| An absolute RFC3339 deadline | Breaks on client clock skew, on precisely the devices this product runs beside. The 3.0 REST API may add one when a machine consumer needs it; a human reading a screen does not |
| Server-sent events | A streaming endpoint, one held-open connection per viewer, CSP and reverse-proxy buffering — for a 120-second counter a 2-second poll already tracks |

## 2 · The rollback command

`Cancel()` exists. What is missing is the way to it.

| | |
|---|---|
| Protocol | `CANCEL_ACCEPTANCE` — the **twentieth** command, added to `AllCommandTypes`, which is what the guards over the command list hang off |
| Core handler | calls `f.acceptance.Cancel()`; `Wait` returns false and the existing rollback path runs unchanged |
| Route | `POST /apply/rollback` |
| Audit | `apply_rolledback`, detail `cancelled by operator` instead of `timeout`. **No new action and no new action label** — the reason belongs in the detail, which is exactly what `carried-forward` demands after the Docker reconcile reused `RestoreReasonBoot` for a restore that was not a boot |
| Refusal | `Cancel` reports whether there was an open window to cancel, the same shape `Accept()` already has. A rollback arriving after the window closed produces a `rollback_too_late` flash, not a success |

### Why this is not the panic button

The panic banner deliberately has no control: the network-facing process may not
**re-arm** a firewall a human disarmed at the console, because a stolen session
would then be able to. Rollback runs the other way. It restores the last
**confirmed** rule set — the state the operator already approved — and a stolen
session reaches the identical outcome today by doing nothing for 120 seconds. The
button grants no capability; it saves the wait.

This paragraph goes into `docs-tech/threat-model.md` beside the panic reasoning,
so the two refusals are visibly different refusals rather than one rule applied
inconsistently.

## 3 · The screen

`DESIGN.md` already specifies the tokens: `countdown` at 40/300 JetBrains Mono
with `tnum`, `state-warn` on `surface`, and *"never style the confirm button as
the calm default and the rollback as a subdued link"*. Nothing is invented here.
What follows is what is **cut**.

### Five defaults, five refusals — each by the system's own rule

| The obvious reach | Refused because |
|---|---|
| A ring or donut that depletes | The system is flat and separated by hairlines. This would be the only circular gauge in the product |
| Colour moving green → amber → red | Rule 1: `state-crit` means *rolled back, unreachable, validation failed*. A window with 8 seconds left is none of those. `state-warn` throughout |
| A pulsing glow | Decoration. The digits **are** the motion |
| A progress bar under the number | Says what the number says, less precisely |
| Confirm large, roll back as a grey link | `DESIGN.md` forbids it in those words |

None of these is a matter of taste. All five were already written down.

### Two things are removed

**The clock icon goes.** The pending state currently shows a 48px circular clock
glyph. Above a running clock it is a drawing of the thing standing beside the
thing. It is removed and the countdown takes that slot — the signature gets its
weight without anything being added. The `accepted`, `rolled_back` and `idle`
states keep their icons.

**The pending dot stops pulsing, on this screen.** Two "still happening"
indicators side by side, and the digits say it more precisely. `DESIGN.md` permits
both loops; permitting is not requiring. This is an amendment to its *Motion*
section, entered openly.

```
┌───────────────────────────────────────────────┐
│                    01:47                      │  countdown · 40/300 mono · tnum · state-warn
│                  ● Open                       │  dot static
│                                               │
│   The new rules are live but unconfirmed.     │
│   Open a second connection and check that     │
│   SSH still answers.                          │
│                                               │
│  [ Confirm — the rules work ]                 │  btn-primary  btn-lg
│  [ Roll back now ]                            │  btn-danger   btn-lg
└───────────────────────────────────────────────┘
┌───────────────────────────────────────────────┐
│ Live now — unconfirmed                     3  │
│  ~ tcp        8443   added                    │
│  ~ tcp        22     sources  — → 10.0.0.0/8  │
│  - blacklist  192.0.2.42                      │
└───────────────────────────────────────────────┘
```

**Format `mm:ss`, leading zero.** `tnum` holds the width; the leading zero holds
the *character count*, or the block reflows by one glyph at `1:00 → 0:59`. Carries
to `60:00`, which `AcceptanceDurationMax = 3600` makes the longest there is.

**Nothing changes in the last ten seconds**, because nothing about the state
changed. The only real informational change is at zero, and the screen already
handles it.

**At zero the screen waits rather than guesses.** The local tick will reach
`00:00` up to two seconds before the poll learns what actually happened, and the
two outcomes — confirmed in the last instant, or rolled back — are not
distinguishable from the browser. So the countdown stops at `00:00` and the state
word stays as it is until a poll returns something else. It must never announce a
rollback the core has not reported: this screen's whole argument is that it says
what is true, and the one moment it would be guessing is the moment it matters.

**`prefers-reduced-motion` does not stop the digits.** They are information, not
decoration, and `DESIGN.md`'s own rule is that the information must never live in
the animation alone — here the information *is* the changing number. What the
setting does drop is everything around it: the transitions on the buttons and the
chip, as everywhere else.

**The order inverts, deliberately.** Before the apply the diff is the subject —
you are deciding — and it sits above the panel. During the window the clock is the
subject — you are checking — so the panel goes first and the live diff below it.
The page's subject changes, so its order changes with it.

### The live diff

`handleApplyGET` sets `Preview` to nil while a window is open, on the reasoning
that *"a preview of it is history"*. That is right about the preview and wrong
about the operator: step 2 of the instructions says to check that SSH and your own
services still answer, and what to check is then not on the page. Only a count
survives, and a count does not name a port.

`liveChangeCount()` already computes `DiffRules(state.Backup, state.Current)` and
throws away everything but its length. It returns the deltas instead, rendered
with the existing `.diff` markup under a heading that is not the preview's:
`apply_live_title` — *Live now — unconfirmed* — against `apply_preview_title` —
*What changes*.

Both buttons are `btn-lg`, side by side from 640px and stacked below it. The
distinction between them is fill against outline, never size or position.

**Declined:** the reachability verdict does not return during the window. It
answers by prediction what step 2 has the operator testing for real, and a
prediction standing next to a live test is the weaker statement.

## 4 · The topbar

```
[≡]  Ports    ● 01:47 unconfirmed →                    [a] admin
```

An operator who opens `/ports` during the window loses the clock. The panic banner
is the precedent for something every page carries — but the panic flag is a
boolean and this is a number that moves, so the banner's mechanism does not
transfer.

| Step | Cost |
|---|---|
| The server renders the remaining seconds into `data-remaining` on the chip at page load | **0** — the page already pays a `GET_STATUS` |
| The browser ticks locally, once per second | 0 |
| At zero the chip goes neutral and makes **one** `fetch('/apply/status')` | 1 per window |
| The result shows *Confirmed* (which fades) or *Rolled back* (which stays and links to `/apply`) | 0 |

Requests during a 120-second window, from a page that is not `/apply`: **none**.
One at the end.

**The chip is hidden on `/apply`.** That page carries the clock at 40px; two
clocks side by side make neither of them important.

### What this makes load-bearing

`carried-forward` records that every page pays a `GET_STATUS`, that `Enforcing()`
can block behind a whole apply cycle for up to 30 s, and that `render` swallows
the error so the panic banner disappears exactly when the core is busiest. With
the chip, that stall eats the countdown too, on every page.

**The ~2-second TTL cache from that entry ships in this release** — roughly fifteen
lines, per its own estimate. Not as a passenger: this feature is what makes it a
requirement rather than a nicety.

## 5 · Proof

Every test below is verified by breaking the implementation and watching it go
red, never by reading it. The seven false-green tests 2.12's review found are why.

| What must hold | The mutation that must fail |
|---|---|
| The number shown is the timer that fires | `Wait` back to `time.NewTimer(a.Duration())` with the deadline set elsewhere |
| A second `Start` does not move the deadline | remove the idempotent early return |
| `Remaining()` is 0 when idle and never negative | remove the clamp; return a negative |
| The window opens before the kernel write | move `acceptance.Start` back below `nft.Apply` |
| Shutdown during an apply does not block for the window | as above — this is the same mutation, asserted from `Stop` |
| Rollback records why it happened | write detail `timeout` instead of `cancelled by operator` |
| Rollback after the window closed is refused | make `Cancel` report success unconditionally |
| The chip does not appear on `/apply` | remove the guard |

Beyond the table:

- **`en` and `de` at exact parity.** New keys: the roll-back button, its result
  flash, `rollback_too_late`, the chip's label, `apply_live_title`. `fr` may lag
  and is counted by the coverage report, never hidden.
- **The demo mock gains both** — the field and `CANCEL_ACCEPTANCE`. A demo client
  that silently does nothing is how the validation false-green happened, and it is
  written into the *Adding a command* procedure in `docs-tech/protocol.md`.
- **`check:ui` drives a whole window**: start an apply, read the countdown falling,
  roll back, assert the rules returned. The mock's timer is real, so this is a
  real window and not a fixture.
- **An integration test**, because this changes the apply path: the ordering fix
  and the rollback both touch what reaches the kernel, and the unit tests mock it.
- **Screenshots.** `apply-{dark,light}.png` show the idle state; the window has
  never been pictured in the documentation, though it is the product's thesis. Two
  new files, `apply-window-{dark,light}.png`. The two captures will read different
  remaining times — that is honest, not a defect.
- **The guard tests that already exist keep working**: `AllCommandTypes` grows by
  one. Six test files across all three packages assert over that list — twenty-seven
  references — including the one that checks the documentation's own count.

## Risks

| | |
|---|---|
| **The ordering fix touches the apply path** | The most safety-critical function in the product. It ships against a test that fails without it, plus the integration harness. If the shutdown hang cannot be reproduced, the move still stands on `Start`'s own documented contract — but the claim in this spec is corrected rather than left standing |
| **The window grows by the kernel write** | Milliseconds on a fast host, possibly a second or two on an SD card. Deliberate, argued above, and it shortens no operator's *usable* time — it lengthens the period during which the rollback is armed |
| **A rollback button is a new way to change the firewall from the network** | It restores a previously confirmed set and grants nothing a 120-second wait does not. Written into the threat model rather than assumed |
| **The topbar chip depends on a fast `GET_STATUS`** | Which is why the TTL cache is in scope and not deferred |

## Not in this release

- A countdown on the dashboard's status panel. The topbar carries every page,
  including that one; a second one on the same screen is the two-clocks problem.
- Any change to what the window *does*. The duration, the rollback target and the
  panic interaction are all untouched.
- The audit log's `boot_enforce_failed` and `rollback_skipped` wording, carried
  forward from 2.7. Related, but a different release's sentence.
