# 2.20 — When something happens, you hear about it

A webhook or an ntfy push when the firewall rolls back, when an apply is
confirmed, when panic mode is engaged, and when somebody keeps failing to log
in. The core still never opens a connection outward.

## 0 · The roadmap entry's mechanism does not survive reading the code

The entry says: *"the web process polls the audit log and sends the
notification."* Four facts, each checked in the tree rather than assumed, say
that is the weakest of the three ways to do it.

| Fact | Where | Consequence |
|---|---|---|
| `GET_LOG` returns the last 200 entries. No cursor, no `since`, no count | `shared.CmdGetLog`, `docs-tech/protocol.md:20` | A poller must diff against what it has already sent |
| `AuditLogEntry.Time` is RFC3339 at **second** granularity, and there is no sequence number | `shared/models.go:775` | Two identical entries in one second are indistinguishable. Deduplication is guesswork |
| The audit log is `0600`, owned by root. The web process **never opens the file** — it asks over the socket | `core/rules.go:384`, the comment on `WriteAuditLog` | "Polls the audit log" means "asks the core every *n* seconds", with a 200-entry ceiling on each answer |
| `FirewallStatus` already carries `Acceptance`, `AcceptanceReason`, `Panic` and `LastApply` | `shared/models.go:794` | Three of the four triggers are readable from the status, with the outcome already distinguished |

A log is a record. A queue is a queue. Reading the first as the second is what
forces the deduplication problem, and the deduplication problem is the one that
cannot be solved cleanly without changing the audit line format.

**So the mechanism changes, and the roadmap entry is amended openly.** Not
deviated from quietly: the entry's sentence is wrong after this spec, and a
roadmap that is corrected when something changes rather than quietly ageing is
what its own first paragraph promises.

## 1 · Where the events come from

Two sources. The audit log is not one of them.

```
                    ┌───────────────────────────────┐
  easywall-core ───▶│ GET_STATUS, every 15 s        │──┐
  (opens nothing)   │ Acceptance · Panic · LastApply │  │   ┌──────────┐
                    └───────────────────────────────┘  ├──▶│ notifier │──▶ HTTP POST
                    ┌───────────────────────────────┐  │   └──────────┘
  auditEvents ─────▶│ login_failed · login_2fa_faile │──┘
  (the web process  │ d · login_ratelimited          │
   raises these)    └───────────────────────────────┘
```

### The status side

`AcceptanceStatus` has four values, and two of them — `accepted` and
`rolled_back` — are **terminal states that persist** rather than instants that
pass. There is no race against a 120-second window: a poller that wakes up
after the window closed still finds the outcome sitting in the status.

The identity of one apply cycle is the pair `(LastApply, Acceptance)`. When that
pair differs from the last one the notifier acted on, it is a new outcome.
`AcceptanceReason` carries *why*, and it already distinguishes the two cases
that matter — the window expired, or an operator ended it by hand. It exists
because the interface once told an operator "the window closed without a
confirmation" on the screen whose whole argument is that it says what is true;
the notification inherits that distinction rather than flattening it again.

`Panic` is a boolean in the same status. It is carried there rather than read
from disk because only the core knows where its data directory is — so the
notifier sees panic mode engaged from `easywall-core panic` on the console,
which a web-originated view could not.

Two details that come from reading `server.go` and would otherwise be defects:

- **`cachedStatus()` returns `nil` on a socket error, not the previous value.**
  The notifier must treat `nil` as *unknown* and change nothing it remembers.
  Treating it as a state would make a core restart report a rollback that never
  happened.
- **The status cache has a 2-second TTL.** The notifier goes *through*
  `cachedStatus()` on a 15-second tick, so it adds no socket traffic of its own
  and cannot starve a page render behind a slow round trip.

### The self-raised side

Failed logins do not need to be read back from anywhere: the web process raises
them. `auditEvents.Record` is the single funnel every login event passes
through — `handler_login.go` and the rate limiter both reach the core that way —
so the notifier taps the funnel rather than the record.

The core already folds bursts (`loginEvents`, a 60-second window and a
1024-address ceiling, so that a script cannot erase the visible log). That
debounce is about *the record*. The notifier needs its own threshold about *the
phone*, because the question is different: "is this worth waking somebody up
for" is not "is this worth writing down".

## 2 · The four triggers

| Switch | Source | Sent when |
|---|---|---|
| **Rolled back** | `Acceptance == rolled_back` | `(LastApply, Acceptance)` is new — carrying `AcceptanceReason` |
| **Confirmed** | `Acceptance == accepted` | as above |
| **Panic mode** | `Panic` flips | on either edge, including when the CLI caused it |
| **Repeated failed logins** | `auditEvents.Record` | a threshold is crossed inside a window, then a quiet period before it can fire again |

Four switches, individually settable, all off by default — the same default
posture as telemetry, and for the same reason: a request that leaves the host is
asked for, never assumed.

## 3 · What goes out

One HTTP client, one `kind` switch, two body shapes.

| `kind` | Request |
|---|---|
| `webhook` | `POST`, `application/json`: `{event, severity, detail, host, version, time}` |
| `ntfy` | `POST`, `text/plain` body, with `Title`, `Priority` and `Tags` headers |

`shared.Reporter` is the shape this follows, and one of its decisions is carried
over verbatim: **redirects are refused.** The telemetry reporter's comment says
why — an endpoint that follows a redirect can be pointed at a third party by
whoever controls its DNS. That reasoning is stronger here, not weaker: the
destination is chosen by the operator and the body describes their firewall.

Timeout 10 s. One retry, then a `WARN` in the journal and a failure recorded for
the page to show.

**Private address ranges are not blocked.** A self-hosted ntfy on the LAN is the
normal case for this audience, not the attack. The operator configuring the URL
is the operator who owns the host; there is no lower-privileged party to defend
against here, and blocking RFC1918 would break the deployment this feature is
mostly for.

## 4 · Configuration

A new `[notifications]` table in `web.toml`.

```toml
[notifications]
kind = ""              # "webhook" | "ntfy" | "" (off)
url  = ""
on_rolled_back   = false
on_accepted      = false
on_panic         = false
on_failed_logins = false
```

It goes in `web.toml` rather than under `data_dir` for the reason `TOTPSecret`
gives in its own comment: an operator who has been told "edit `web.toml`" must
find everything that matters in the one file they were sent to. The file is
already `0600` and already holds `session_key`, the password hash and the TOTP
secret; an ntfy topic URL is a credential of the same kind and belongs with
them.

> **The trap this repeats.** A new top-level key written after a `[…]` heading
> lands inside that table. 2.12's reviews found seven tests that passed for the
> wrong reason, and one of them was exactly this — a key appended past a `[tls]`
> header into the wrong table, green the whole time.
> `[notifications]` is written **after** `[tls]`, the embedded default
> in `config/web.toml`, `shared.WebConfig` and `writeconfig.go` must agree, and
> a guard test proves the round trip — `-write-config` output parsed back must
> put every key in the table it was written under.

## 5 · The interface

Its own entry in the sidebar's SYSTEM group, not a section on *System*.

A URL field, four switches and a **Send a test** button is more than a section
carries, and the button is the reason the page exists in this shape. An operator
must be able to prove the notification arrives without waiting for a real
rollback to produce one. That is 2.17's position — *it proves what it says* —
pointed at this feature.

The page also shows **when something was last sent and whether it worked**. A
notification that fails silently is worse than no notification, because it is
believed.

## 6 · The demo

The public demo sends nothing. The page renders, the switches move, the test
button reports that a demonstration does not make outbound requests — the same
honesty `handleLogEvent` already applies to the address it declines to record.

## 8 · What is not promised

No queue, no delivery guarantee, no retry beyond the single attempt. If the host
has no route out when the rollback happens, the notification is gone — and the
page says so rather than implying otherwise. The audit log is the record; the
notification is a convenience, not a second record.

This is stated here so it is not discovered later as a defect. A feature that
quietly implies a guarantee it does not keep is the class of problem 2.17
exists to end.

## 9 · How it is proven

- An `httptest` server receives both body shapes. **Redirect refusal and the
  timeout are exercised, not read** — a test that asserts the `CheckRedirect`
  field is set proves nothing about behaviour.
- The state differ takes a table of `FirewallStatus` pairs, including the row
  where the second is `nil`, proving an unreachable core reports nothing.
- A guard test on the TOML table placement (§ 4).
- The failed-login threshold is proven by driving `auditEvents.Record`, not by
  reading the constant.
- `check:ui` drives the new page in both themes; the demo path asserts that
  nothing leaves the process.
- Every test above is verified by mutation: break the implementation, watch it
  go red. 2.12's reviews found seven tests that passed for the wrong reason;
  all seven were green, and all seven were found this way.

## 10 · Open questions for the plan

1. **The failed-login threshold and window.** The core uses 60 s. A phone is not
   a log; the numbers are probably not the same, and whether they are
   configurable at all is a decision the plan makes, not this spec.
2. **Whether `severity` is part of the webhook body or only of ntfy's
   `Priority`.** The two map onto each other but not one-to-one.
3. **Where the "last sent" state lives.** `data_dir`, beside `telemetry.json`,
   is the obvious answer; whether it survives a restart or starts empty is a
   choice with a visible consequence on the page.
