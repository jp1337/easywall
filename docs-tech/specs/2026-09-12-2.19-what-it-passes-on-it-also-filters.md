# 2.19 — What it passes on, it also filters

A port rule can name traffic this host **forwards** to a container, not only
traffic addressed to the host.

## 0 · What is actually broken, measured rather than read

root01xvp.wdkro.de runs ten Docker networks, twenty-three containers, a mail
server, nginx, a WireGuard hub and TeamSpeak. Its Hetzner Cloud firewall allows
fourteen ports. Measured with `ss -tulnpH`, which names the process:

| Port | Holder | Reaches easywall's `input` chain |
|---|---|---|
| 22 | `sshd` | yes |
| 80, 443 | `nginx` | yes |
| 51820/udp | WireGuard, in-kernel | yes |
| 25, 143, 465, 587, 993, 4190 | `dockerd` | **no** |
| 30033/tcp, 9731/udp, 8888/udp | `dockerd` | **no** |

**Four of fourteen.** The other ten are published container ports. Docker
publishes by writing a DNAT rule in `nat/PREROUTING`; the packet is then routed
rather than received, so it crosses `forward` and never `input`.

`iptables-save` on the same host, confirming it rather than inferring it:

```
-A DOCKER -d 172.17.0.3/32 ! -i docker0 -o docker0 -p tcp --dport 25   -j ACCEPT
-A DOCKER -d 172.17.0.3/32 ! -i docker0 -o docker0 -p tcp --dport 143  -j ACCEPT
-A DOCKER -d 172.17.0.3/32 ! -i docker0 -o docker0 -p tcp --dport 465  -j ACCEPT
```

An operator on that host sees a dashboard reporting **Active**, four rules, and
no indication that ten more ports are open and filtered by somebody else. That
is 2.17's defect class — a surface asserting what it does not enforce — aimed at
a whole direction of traffic.

## 1 · The mechanism is already there

`internal/core/nftables.go:664` builds a `forward` chain at the forward hook,
in `table inet easywall`, with `policy drop` unless `routing.mode` is `open`.
The code says why that is enough:

> a drop in either beats an accept another table's forward chain has already made

So easywall's forward chain **sees every forwarded packet**, including one
already rewritten by Docker's DNAT to `172.17.0.3:25`, and a verdict there is
final. Nothing needs to be added to reach the traffic.

## 2 · What is missing is the vocabulary

Three ways exist to say something about that chain today, and none of them can
name a port:

| | Says | Granularity |
|---|---|---|
| `docker.allow_bridge_networks` | bridge CIDRs may cross | whole network |
| `routing.networks` | these CIDRs may cross, either direction | whole network |
| A custom rule | — | **cannot reach it**: `nftables.go:825` appends every custom rule to `input`, hard-coded |

`features/docker.md` offers a third arrangement — Docker with
`{"iptables": false}` — and measured it against Docker 29.7.2: the setting
removes Docker's NAT along with its filter rules, and easywall cannot supply the
replacement, because custom rules land in `input` and a masquerade needs a
`postrouting` chain in a table of its own. On a host with ten bridge networks
that means hand-written DNAT *and* NAT. It is not a path.

## 3 · The shape

A port rule gains a **scope**: where the rule is evaluated.

| Scope | Chain | Means |
|---|---|---|
| `host` | `input` | traffic addressed to this machine — today's behaviour, and the default |
| `forwarded` | `forward` | traffic this machine passes on |
| `both` | both | the same port, wherever it arrives |

`host` is the default so that every rules.json written before this release means
exactly what it meant before. A rule that gains no scope key is a `host` rule.

### Why a scope on the rule, and not a second list

A second list of "forwarded ports" would be a second place to look for the answer
to *is 25 open*, and the dashboard would have to add the two together to report a
count. One rule, one port, one row, one place — the scope is a column, the way
`ssh` is.

### What it does not do

**It does not manage `DOCKER-USER`, and it does not write outside
`table inet easywall`.** The whole design rests on easywall owning one table; a
release that starts writing into Docker's is a different product. The verdict is
taken in easywall's own forward chain, where it already wins.

**It does not replace `allow_bridge_networks`.** Container-to-container and
container-outbound traffic still crosses on the CIDR exemption. What changes is
that *inbound* traffic to a published port can now be denied by a rule, where
before the exemption accepted all of it.

## 3a · The switch, and why the feature is nothing without it

Found while reading `addForwardExceptions` for the plan, and it changes the
design rather than decorating it.

That function accepts any packet with a source **or** a destination inside an
allowed bridge CIDR. After Docker's DNAT an inbound packet to a published port
has destination `172.17.0.3` — inside the bridge range. **It is already
accepted.** A `forwarded` accept rule added beside it would therefore permit
what was permitted anyway, and deny nothing. The feature is meaningless without
a default-deny for inbound-to-container.

And a default-deny that arrives switched on is 2.5.0 again: every container host
that upgrades loses every published port at its next apply.

So the release carries one key, and it defaults to today:

```toml
[docker]
published_ports = "open"      # Docker decides who reaches a published port — today's behaviour
                              # "filtered": only a forwarded port rule lets anything in
```

Under `"filtered"`, and only then, the forward chain gains the rule that gives
the feature meaning:

```
forward:
  ct state established,related                      accept   ← already there
  <forwarded port rules>                            accept   ← new
  dst in bridge AND src NOT in bridge               drop     ← new: the default-deny
  <bridge / routing CIDR exceptions>                accept   ← already there
  policy                                            drop
```

The direction test is what keeps containers alive. A container's outbound
traffic has its **source** in the bridge range, so the drop does not match it.
Container-to-container has both ends inside, so it does not match either. Only
traffic arriving from outside for a container address matches — which is exactly
a published port, and exactly what the operator asked to filter.

`ct state new` is deliberately **not** part of the drop's match: established and
related are accepted at the top of the chain, so anything reaching this rule is
already new or invalid. A second state test would be a second place for the two
to disagree.

### IPv6, stated rather than implied

`detectDockerBridges` returns IPv4 CIDRs only, so neither the new drop nor the
existing exception ever matches an IPv6 packet. Inbound IPv6 to a published
container port already falls to `policy drop` today, before this release and
regardless of this key. That is a pre-existing hole with a documented workaround
(`custom_networks`), it is not made here, and section 5 is where it gets closed.

## 4 · The ordering problem inside the chain

The forward chain today is: established/related accept, then the CIDR
exemptions, then policy drop. A `forwarded` port rule that sits *after* the
bridge exemption can never deny anything — the exemption has already accepted
the packet.

So the chain order becomes:

The order is in section 3a. What matters here is where it is built:
`Apply` calls `addForwardExceptions` at `nftables.go:710`, and the port rules
are not added until `nftables.go:767`. Appending forwarded rules where the port
rules already live would put them **after** the exceptions, where they can never
deny anything.

**This is the part that has to be proven rather than reasoned about.** A
`forwarded` rule set that renders after the exemption is a rule set that reports
itself enforcing and enforces nothing — the exact failure 2.17 exists to catch,
reproduced by this release. It gets a `selftest` case of its own.

## 5 · IPv6 travels with it

`internal/core/docker.go:25` says it in its own comment:

> IPv4 only. A Docker network with IPv6 enabled is not detected, and has to go
> in `docker.custom_networks`

The table easywall writes is `inet`, so the forward chain's `policy drop`
applies to IPv6 all the same, while the exemption that rescues IPv4 bridge
traffic does not. Today that is latent — no measured host has an IPv6 Docker
network — and it stops being latent the moment this chain starts taking
verdicts. Detection learns IPv6, or this release ships a hole it opened.

## 6 · Acceptance, and why the window is not enough

The acceptance window proves **the operator's own connection**. Every defect
this release can cause is invisible to it: SSH runs over `input`, so a forward
chain that takes the whole host's container traffic offline leaves the window
perfectly happy while mail stops, the cluster tunnel drops and twenty-three
containers go dark.

The release therefore carries its own proof, in the shape 2.17 established:

| Depth | Proves |
|---|---|
| Unit | the rendered chain puts forwarded rules before the exemptions |
| `selftest` | in a private netns, a packet DNAT'd to a container address is dropped by a `forwarded` deny and accepted by a `forwarded` allow |
| Integration | with a real bridge and a real container, a published port answers with an allow rule and refuses without one |

## 7 · Open questions for the plan

1. **Does a `forwarded` rule need a destination?** On a host with one container
   per port, "port 25 forwarded" is unambiguous. On a host with two containers
   publishing 8080 on different addresses it is not. Proposal: no destination in
   2.19 — a port is a port — and the interface dimension that would express it
   is 2.28's, which is the entry that should carry it.
2. **What does the dashboard count?** A `both` rule is one rule and two
   verdicts. Proposal: count rules, not verdicts, and let the scope show in the
   row.
3. **Does `routing.mode = "open"` disable the feature?** Under `open` the
   forward policy is `accept` and `addForwardExceptions` is skipped entirely
   (`nftables.go:704`). **Resolved:** under `published_ports = "filtered"` the
   forwarded rules and their default-deny render anyway. A deny under an accept
   policy is meaningful, and a key that silently does nothing because another
   key is set is the failure mode this release exists to end. The combination
   gets a test of its own.

## 8 · What this unblocks

easywall becomes able to be the only firewall on a container host. That is not
an abstraction: it is the reason the entry exists, and the host in section 0 is
waiting on it.
