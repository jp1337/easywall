## A · `docker.enabled` default

**(a) Confirmed.**
- `config/easywall.toml:47` ships `enabled = false`.
- `handler_firstrun.go:253-260` preserves the Docker settings, and `handler_firstrun_test.go:226` pins that.
- With it off: `nftables.go:726-732` gives `dockerCIDRs` = nil. Under `routing.mode = "closed"` (easywall.toml:77) the forward chain gets policy drop (nftables.go:692-695) and no exceptions, and `buildForwardChain` returns early (nftables.go:2146-2148).
- Result: an empty base chain with policy drop, which is final whatever Docker's own chains accept (features/docker.md:37-42). The acceptance window cannot see it (easywall.toml:57-61; nftables.go:2154-2156). VERIFIED by code read; the outage was not reproduced live.

**Detection today**
- `detectDockerBridges` (docker.go:38-68): `net.Interfaces()`, then keep names with the prefix `docker` or `br-` (docker.go:72-75), then the IPv4 network of each address. IPv6 is skipped.
- It runs at apply (nftables.go:729). `reconcileDockerBridges` restores once more if a bridge appears after boot (dockerreconcile.go:72-88). It does nothing when the setting is off (dockerreconcile_test.go:41).

**What `enabled = true` accepts** (VERIFIED, nftables.go)

| Chain | Rule | Effect |
|---|---|---|
| input | `addCIDRAccept` for each bridge CIDR, matching the **source** (`:777-780`, `:2379-2409`, offset 12) | every container can reach **every host port** |
| forward | `forwardExceptionMatches`: source **or** destination in a bridge CIDR (`:2091-2101`), in every `routing.mode` except `open` (`:2129-2135`) | container outbound, container↔container, and the world→published ports that Docker DNATs; with `published_ports = "open"` Docker decides |
| bogon | bridge CIDRs exempted (`:751-753`) | — |

That is exactly the host's behaviour without easywall — docker.md's "Option 1 — recommended" (features/docker.md:55).
Cost of a false positive: any interface named `br-*` that is not Docker's, such as OpenWrt's `br-lan` (docker.go:34-37 says so), has its network trusted on input.
On a host with no bridges, detection returns nothing, `custom_networks` is empty, and no rule changes: identical to `false`.

**(b) Debian: yes.** A Debian host that runs Docker gets the same empty forward chain. `debian/rules:60` installs this same file as the template.

**(c) Options**

| | Fix | For | Against |
|---|---|---|---|
| A1 | Flip `config/easywall.toml:47` to `enabled = true`, both paths | one line; covers compose (including the git-checkout mount, see K), `docker run`, and a Debian host with Docker; no effect on a host with no bridges; new installs only, because postinst:70 and entrypoint.sh:32-36 never overwrite an existing file | a router with a non-Docker `br-*` bridge trusts that network. Unlikely on the supported distros (requirements.md:24-30), but it must be said in the key's comment |
| A2 | Image-only: rewrite the default in `/usr/share/easywall/config/easywall.toml` and `/etc/easywall/easywall.toml` at build time | Debian unchanged | **does not reach the documented path**: `./config` from git already holds the tracked `easywall.toml`, so the entrypoint's copy-if-absent (entrypoint.sh:32-36) never runs — it depends on K. Also a Debian+Docker host stays broken |
| A3 | First run asks ("this host runs containers"), pre-ticked when the web process sees `docker0`/`br-*` (`net.Interfaces` works unprivileged in the host namespace) | explicit | new UI, both locales, screenshots; the web process then writes Docker settings, which it deliberately does not today |
| — | A variable (`EASYWALL_CORE_DOCKER_ENABLED`) | — | **ruled out by an invariant**: the environment may not name a rule field (env.go:13-16, `TestNoEnvVarTargetsARuleField`) |

## B · The first-run claim race (headline)

### (a) Confirmed — there is no gate

- `config/web.toml:4` binds `0.0.0.0:12227`.
- Routing, server.go:509-545: `/firstrun` GET/POST and `/firstrun/confirm`, `/firstrun/recover` are public routes, registered while `cfg.IsFirstRun()` (server.go:534). The only middleware is `Recoverer`, `SecurityHeaders`, `MaxBodySize` and `CrossOriginProtection` (server.go:482-491). There is no rate limit (contrast `/login` at :511).
- `handleFirstRunPOST` (handler_firstrun.go:116-175) checks only `IsFirstRun`, the form fields and the password policy. It then hashes and creates the pending entry.
- The only serialisation is `SaveFirstRun`'s lock (config.go:581-587, `ErrAlreadySetUp`). It decides who wins; it does not decide who may play. `IsFirstRun` is `Password == ""` (config.go:234-238).
- Nothing is filtered yet: docker.md:32, and a fresh core has no rules. The GET /firstrun check in CI (build.yml:607-619) proves the page answers 200 to anyone.
- So on a public host, the first visitor to finish step 2 owns an interface that writes root nftables.

### (b) Debian: yes, the same exposure

- `debian/rules:61` installs the same `web.toml` as the template.
- postinst:89-94 enables and **starts** `easywall-web` immediately.
- **postinst prints nothing**: no URL, no hint (debian/postinst:1-98).
- The unit logs to the journal (systemd/easywall-web.service:21-23).

### How others gate it (source, pinned tags)

| Project @ tag | Gate | Evidence |
|---|---|---|
| Jupyter Server v2.21.1 | **random token, printed to the log, per start**, plus a **loopback default** | `binascii.hexlify(os.urandom(24))` = 192 bit (auth/identity.py:223-224); regenerated per process unless `JUPYTER_TOKEN`/`JUPYTER_TOKEN_FILE` (:210-217); logged with `log.critical` as a URL with `?token=` (serverapp.py:2381-2386, 3155-3175); default ip `localhost` (serverapp.py:1021-1036). Compares with plain `==` (identity.py:497, 592, 735), **not** constant-time |
| Portainer 2.45.1 | **no token — a 5-minute timeout**, after which the API refuses everything until a restart | `adminmonitor.New(5*time.Minute, …)` (api/http/server.go:143); `adminInitDisabled` (api/adminmonitor/admin_monitor.go:51-66, 106-115). The race is open for those 5 minutes |
| Grafana v13.2.2 | **no claim step — a well-known default credential** | `admin_user = admin`, `admin_password = admin` (conf/defaults.ini:471-474); `http_addr =` empty = all interfaces (:50) |
| Home Assistant 2026.9.3 | **first come, under a lock** — exactly easywall's model today | `UserOnboardingView`, `requires_auth = False`, `async with self._lock: if self._async_is_done(): 403` (components/onboarding/views.py:170-197) |
| Gitea v1.27.3 | **first come until `INSTALL_LOCK`** | `if setting.InstallLock` is the only check on GET and POST (routers/install/install.go:62-63, 183-184); routes are unauthenticated (routers/install/routes.go:30-31) |

Only Jupyter proves "whoever claims can read this host's output". Nextcloud proves "can write this host's filesystem". The other four are first-come.
easywall, whose interface writes root nftables on a machine exposed by definition, sits with the weakest group today.

### Proposed design

| Question | Decision | Why |
|---|---|---|
| Which process holds it | **easywall-web**, in memory | Account creation is already the web process's power alone: it writes `web.toml`, and the core never sees credentials ("the core never sees any of it", config.go:552-556). A web process compromised before setup can already create the account, so the token adds no privilege worth stealing there. Putting it in the core would add a 24th protocol command and give the root process an authentication duty it has none of today — the trust split argues **against** the core |
| Generated | once per process start, only `if cfg.IsFirstRun()`; never on disk | nothing to clean up, nothing to leak through a backup. A restart invalidates the old token and prints a new one, which is also the recovery path if the log line is lost |
| Entropy / format | **reuse `newTOTPSecret()`**: 20 bytes `crypto/rand`, 160 bit, base32 (totp.go:29, 137-143). Display it with `formatTOTPSecret` in groups of four (totp.go:160-168) | 160 bit is past Jupyter's 192-bit class for online guessing; the code already exists (ladder rung 2) |
| Compare | normalise with `decodeTOTPSecret` (strips spaces, dashes and `=`, upper-cases; totp.go:145-158), then `subtle.ConstantTimeCompare` on the decoded bytes | constant-time; tolerant of a pasted grouping |
| Printed | one `slog.Warn` at start: `first run: enter this setup token on https://<this host>:<port>/firstrun`, `token=XXXX XXXX …` | stdout → `docker logs` (supervisord.conf:61-64 sends web stdout to `/dev/fd/1`) and the journal (easywall-web.service:21-23). Commands to document: `docker compose logs easywall \| grep 'setup token'` and `journalctl -u easywall-web -g 'setup token'` |
| Where checked | at the **top** of `handleFirstRunPOST`, before `ParseForm`'s fields are used and before `HashPassword` | step 1 is the only way to mint a pending entry (handler_firstrun.go:313-319), and confirm/recover require one (:403-407, :522-526), so one check covers all three POSTs. Checking before Argon2 also closes **X1** (unauthenticated 64 MiB hashes) |
| Form | a required "Setup token" field on step 1, with the command to fetch it printed beside it | GET /firstrun stays 200, so CI's build.yml:607-619 check still holds |
| On a rejected submission | **not** stashed in `firstRunKey` (handler_firstrun.go:265-272), the same as the passwords | the session cookie is signed, not encrypted (threat-model.md:83) |
| Lifetime | until the account exists or the process exits; no timer | a Portainer-style timeout adds a restart and no security once a token exists |
| No env override | no `EASYWALL_WEB_SETUP_TOKEN` | secrets are deliberately absent from the environment layer (env.go:25-28). Automation (wdk-ansible) writes `password` directly, so `IsFirstRun` is false and no token is ever generated |
| `.deb` | same code. postinst gains one `echo` after the start (postinst:93): "open https://<host>:12227/firstrun — the setup token is in `journalctl -u easywall-web`". postinst cannot print the token itself: the web process generates it | — |
| Demo | **no exemption.** The public demo ships with a password set (server.go:540-541), so `IsFirstRun` is false and it is unaffected. A self-hosted demo with an empty password writes a real `web.toml` (threat-model.md:108-126), so it needs the gate like anything else | demo.md:33 must change (X4) |
| Rate limit | optional: `LoginRateLimit` on `POST /firstrun` | brute force against 160 bit is moot; it only bounds the pre-check request cost |

Residual risks, one line each:
- Anyone who can read the journal (`adm` or `systemd-journal` group on Debian) or `docker logs` (the `docker` group, which is root-equivalent anyway) can claim.
- A MITM on the first TLS visit, against a self-signed certificate, sees the token as it is typed. This is out of scope today as well.

### Loopback-only default instead?

Keeping the default is recommended; loopback is rejected.

- A loopback bind is safer by construction (Jupyter ships both).
- It breaks the operator's goal and the documented flow: docker.md:23 is "from your own machine, open `https://<server>:12227`". carried-forward.md:197 records rewriting exactly that away from `localhost`.
- It forces `ssh -L`, which item I shows fails under `AllowTcpForwarding no` with an error that reads like an easywall fault.
- The token keeps the remote-first flow at the cost of one copy-paste.
- Anyone who wants loopback already has `EASYWALL_WEB_BIND_ADDR` (env.go:120-122).

Test: `POST /firstrun` without or with a wrong token → re-render, no pending entry, **no `HashPassword` call**. Verify it by deleting the check.

## K · `config/` in the git checkout

**(a) Confirmed.**
- `git ls-files config/` lists `easywall.toml`, `embed.go` and `web.toml`: the **embedded source of truth** (config/embed.go:17-25) is the directory compose mounts (docker-compose.yml:54; docker.md:17-21).
- After the first start, entrypoint.sh:40-54 makes `config/` `root:easywall 0750`, `web.toml` `easywall 0600` and `easywall.toml` `root 0600`.
- The tracked `web.toml` then holds `session_key`, the password hash, `totp_secret` and the recovery hashes, and `easywall.toml` holds the operator's settings.
- Consequences, from code: `git pull` cannot write `config/` (not writable by the checkout's owner); `git stash` would stash secrets; `git checkout .` deletes the account; `git status` shows secrets as modified.
- `.gitignore:22` ignores `config/ssl/` only.
- Also: because tracked files exist, the entrypoint's seed-if-absent (entrypoint.sh:32-36) **never runs on the documented path**. That is why A2 fails.

**(b) Debian:** no.

**(c) Options**

| | Fix | For | Against |
|---|---|---|---|
| K1 | compose mounts a **gitignored** directory: `./easywall-config:/etc/easywall`, plus `/easywall-config/` in `.gitignore` | Docker creates it empty, and the existing entrypoint seeds it from `/usr/share/easywall/config` (Dockerfile:64; entrypoint.sh:32-36). **No `config.example/` needed**: the image already carries the template, so the report's suggestion is redundant | existing git-checkout installs move to a new empty dir on the next `up`, and first run appears again.
