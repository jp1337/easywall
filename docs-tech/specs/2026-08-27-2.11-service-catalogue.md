# 2.11 — A rule names a service and who may reach it

A port rule gains a **source restriction** and an optional **service label**, and
a curated catalogue fills both in one click. Tracing the design turned up a live
security hole in the SSH brute-force module, which ships in the same release
because the restriction would silently do nothing without it.

## 1 · Model — additive, no migration

```go
type PortRule struct {
    Port        string   `json:"port"`
    Description string   `json:"description"`
    SSH         bool     `json:"ssh"`
    Sources     []string `json:"sources,omitempty"` // empty = anywhere, today's behaviour
    Service     string   `json:"service,omitempty"` // catalogue id — a label, never a behaviour
}
```

`omitempty` keeps an untouched `rules.json` byte-identical. `Service` drives
nothing: an id the catalogue no longer knows renders no chip and the rule
is unchanged — a catalogue edit can never alter a live firewall. `Sources`
validates through `validateIPOrCIDR`, the path the whitelist already uses, with
comments and blanks skipped exactly as every other operator-written list is.

**Amended after implementation.** This section said an unknown id "renders as
plain text". It does not: `serviceName` (`internal/web/server.go:1167`) returns
`""` for an id `ServiceByID` cannot find, so no chip renders at all — the row
looks exactly like a rule that was never given a service. That is the better
behaviour, not a bug; the wording above now says what the code does.

## 2 · Kernel

`addPortAccept` emits one nft rule per source × port, source match first. Empty
`Sources` emits exactly today's single rule.

**Amended from the design.** No builder is factored out: `cidrMatch(entry,
posSrcAddr)` (`internal/core/nftables.go:1492`) already handles both families,
a bare address or a network, and returns `nil` for a comment. `addWhitelistRule`
and `addCIDRAccept` are the older duplicates of it; they are left alone, because
rewriting a working accept path is not what this release is for.

## 3 · The sshbrute hole, fixed in the same release

`sshbrute` ends in **accept**, and `Apply` adds it to the input chain *before*
the blacklist:

```
input: … → jump sshbrute (new conn, dport 22) → under rate → ACCEPT
        blacklist DROP        ← never reached
        whitelist              ← never reached
        port rules             ← never reached
```

Two consequences, both live today whenever the module is on:

1. **A blacklisted address can SSH in**, as long as it stays under the rate limit.
2. **Port 22 is open even when no rule opens it.** With no SSH-marked rule
   `sshPorts` falls back to `{"22"}` (`nftables.go:1104`), and the chain accepts
   it. `docs/_docs/features/ports.md` describes that fallback as protection; it
   is also an accept.

And a third, prospective: a `Sources` restriction on the SSH rule — the rule
people will restrict first — would do nothing.

**Fix:** the chain's trailing verdict becomes `return`. Under-rate traffic falls
back into the input chain and meets the blacklist, then the whitelist, then the
port rule. Over-rate still drops in `sshbrute-over`. For an unrestricted,
un-blacklisted connection to a port that *is* open, nothing changes.

This is a behaviour change and the changelog says so: a host relying on the
fallback to reach SSH on 22 with no port rule needs a port rule. First-run has
always written one.

## 4 · Reachability

`Reachable` step 9 counts a TCP rule only when its sources are empty or contain
the caller. New `ReasonPortSourceMismatch` → **blocked**. `AllReachReasons`
forces both strict locales to label it; `reach_integration_test.go` gets the veth
case, so a source rule in `Apply` without a branch here shows up as a
disagreement with a real kernel.

**Amended during implementation, twice.** This section first placed the blocked
verdict immediately after the port loop, above the custom-rules step. That is
wrong for the reason the pre-existing code already defers `ReasonNoRule` past it:
a custom rule is appended by the nft CLI after everything netlink wrote and can
accept. Demonstrated in the veth harness — a port restricted to `192.168.0.0/16`
plus a custom `tcp dport 12229 accept`, kernel accepting, verdict "blocked" — a
false lockout warning on the one screen that has to be believed. The order is
open → unknown (custom rules) → blocked by restriction → policy.

The label was also wrong. "The port is open, but not to your address" is false
when the source list holds only comments: the kernel emits no rule, so the port
is open to nobody. It named no port although the template already passes one and
both sibling strings use it, and the German switched to Sie in a file that
otherwise says Du. The shipped string is "Port {{.Port}} is open only to the
source addresses its rule names, and yours is not one of them" — true on both
paths, since a rule naming no usable address names none.

## 5 · Catalogue — `internal/shared/catalogue.go`

A Go slice, no `go:embed` (the tree has exactly one, and it is the config).

```go
type Service struct {
    ID      string        // "pihole" — stable, never reused
    Name    string        // "Pi-hole" — a proper noun, never translated
    Ports   []ServicePort // {Proto, Port, Description}
    Suggest Suggestion    // SuggestPrivate | SuggestAnywhere
}
```

Two suggestion constants, not per-entry CIDR literals: the reasoning text is
translatable and the private ranges live in one place.

**Amended from the design.** `PrivateRanges` is RFC 1918 **plus `fc00::/7`**. A
suggestion of RFC 1918 alone on a dual-stack host silently blocks the LAN over
IPv6. A LAN numbered out of global IPv6 space is still not covered — the picker
writes the sources into a visible, editable field, and the aside says what
"private" means.

Translation cost is near zero: service names and port descriptions ("DNS",
"HTTPS") are not translated. Only the two rationales and the picker chrome are.

Guard test: ids unique, every port passes `validatePortRule`, every suggestion
constant has both locale keys.

## 6 · UI — `/ports`

A **Sources** column (one comma-separated text input, plain HTML) and an **Add
from catalogue** button beside *Add rule*, opening a `<dialog>`. Picking an entry
appends its rows pre-filled. A rule with `Service` set shows the name as a chip.

The catalogue is progressive enhancement over the Sources column: without
JavaScript the button is not shown at all, rather than shown and inert.

**Amended during implementation — this section was wrong.** It claimed the
sources column "works with JavaScript off — the rule the language switcher set
in 2.9". It does not, and no part of this page ever has. Every row input in
`ports.html` carries a class and no `name`; the only named fields in the form are
the hidden `rules` JSON blob and `type`, and JavaScript is what fills the blob.
`forwarding.html` is built the same way. The list editors — blacklist, whitelist,
custom — are the ones that genuinely work without JavaScript, because a textarea
with a name submits on its own.

So the Sources field is exactly as scriptless-capable as the Port and Description
fields beside it: not at all. That is a pre-existing property of the rules editor,
not something this release introduced, and redesigning two editors is not this
release's theme. What changes here is that the documentation stops claiming
otherwise.
