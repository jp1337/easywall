# 2.29 — Which lists, and which country

/blocked filters by country. The feed catalogue stops recommending a list that
blocks search crawlers. A list that really shrank is taken after it has stayed
small for a day.

**Why now.** Three findings from one day:

1. **The catalogue recommends a list that blocks crawlers.** blocklist.de `all.txt` contained Googlebot, Bingbot, Applebot, StatusCake and 186 Cloudflare addresses in every sample since June. The research file has the numbers.
2. **/blocked shows a country but cannot filter by it.** 2.27 D7 deferred the filter. The reason was that the core has no country table and the web process only sees 200 rows.
3. **A list that shrinks for real is never taken.** Hagezi TIF dropped from 79 175 to 36 487 entries (−54 %). Every installation that holds the old copy refuses each refresh (*Refused: shrank*) and keeps that copy until the operator switches the feed off and on again.

## 0 · Decisions, and what decided them

| # | Decision | Evidence |
|---|---|---|
| D1 | **`blocklist-de` (all) becomes ✗ deliberate, false positives *yes*.** Its confirm text names search crawlers, uptime monitors and Cloudflare. | Research § Top findings 1–3. A single reporter is enough to list an address for 48 h. |
| D2 | **New ✓ recommended feed `blocklist-de-ssh`**: `https://lists.blocklist.de/lists/ssh.txt`, plain, every hour, false positives *some*. | 0 crawler, webhook or monitor hits in 11 samples from January to October; 4 078 entries; same provider, format and terms as `all.txt`. |
| D3 | **New • optional feed `blocklist-de-imap`**: `…/lists/imap.txt`, for mail hosts. | 0 hits in 12 samples. |
| D4 | **An installation that has `blocklist-de` on keeps it on.** A changed verdict switches nothing. /blocklist shows the ✗ and the reason beside a feed that is on. | A firewall that changes its own rules on upgrade breaks the apply model: only an apply changes what runs. |
| D5 | **A real shrink is taken after a day.** When the core refuses a shrink, it remembers when the first such refusal happened and how many followed in a row. The **third consecutive** refusal that comes **at least 24 h after the first** is stored instead of refused. It is audited as `feed_shrink_accepted` with the before and after counts. Any fetch the core takes without a shrink resets the count. | The guard exists against a truncated download (2.23 D5), and a truncation is one broken fetch, not a day of them. Hagezi refreshes daily; the web's failure backoff retries at +1, +3, +7, +15 and +31 h, so it is taken about 31 h after the first refusal (final review M8). An hourly list needs three refusals in a row across 24 h. |
| D6 | **The shrink state lives in the core's memory**, per feed: when the first refusal of the current run happened and how many followed. A restart forgets it, so the day starts again. *(Amended at planning: the first version kept it in `feeds.json`. `TestUpdateFeed_EveryRefusalLeavesThePreviousCopy` holds every refusal to a byte-identical file, and that invariant is worth more than surviving a restart, which only delays the acceptance.)* | Keeps the refusal path free of writes. |
| D7 | **The country filter is web-side, and exact.** The web process pages through the core's whole ring: `GET_PACKET_LOG` gains `before` (seq) next to the existing filters, with the limit at its maximum of 1000. The web process keeps the entries whose source address the country table places in the chosen country. It stops at 200 matches or at the end of the ring. | 2.27 D4 keeps the table in the web process and the core learns nothing about countries. 2.27 D7 forbade filtering a 200-row sample, so the whole ring is read. The ring is 20 000 entries by default, so at most 20 socket requests per page load. |
| D8 | **The live tail stays a delta, with no `after` in the core.** With a country set, a poll asks for the newest 1 000 entries instead of 200 and keeps those newer than the page's newest that match the country. *(Amended at planning: the first version added `after` to the protocol. It is not needed — more than 1 000 refusals in five seconds is already outside what the 200-row tail shows — and a core `after` would also hide a ring that went backwards, which 2.25.2 D3 detects from the newest seq.)* | One request per poll, as now. |
| D9 | **A core without `before`/`after` is detected, not looped on.** If an answer holds a seq at or above `before`, the web process stops paging and shows a one-line notice that the core needs the same version. | Web and core can be upgraded minutes apart (`Health` in `handler_dashboard.go` already allows for this). |

## 1 · Core

- `PacketLogFilter` gains `Before uint64` (`json:"before,omitempty"`); `Matcher` keeps `e.Seq < Before` when `Before` > 0. It also gains `Country string` with `json:"-"`: the web process's own filter, never sent, checked against `shared.CountryCodes` by `Validate`.
- `Firewall` keeps the shrink state in memory (D6). `UpdateFeed` step 6 applies D5. The audit event `feed_shrink_accepted` takes the detail `"<after> entries replace <before> after <n> refusals since <time>"`.
- `docs-tech/protocol.md` documents `before`.

## 2 · Web

- `FeedCatalogue`: D1, D2, D3, in this order: `spamhaus-drop`, `dshield`, `blocklist-de-ssh`, `blocklist-de-imap`, `cins`, `et-compromised`, `blocklist-de`, `ipsum-3`, `hagezi-tif`, `tor-exits`.
- `/blocked` and `/blocked/rows` read `country`. With it set, `countryPage(f, cc)` pages as D7 describes and the tail follows D8. The country table's lookup already exists (2.27).
- The filter bar's *Country* select, and the popover link (D10).
- Locale keys in en and de (fr may have gaps): `blocked_filter_country`, `blocked_only_country`, `blocked_country_core_old`; the audit label `audit_feed_shrink_accepted`. The new feeds' keys follow the existing pattern (`feed_blocklist_de_ssh_fp_why`, …). `feed_blocklist_de_fp_why` and a new `feed_blocklist_de_confirm`, like `feed_hagezi_tif_confirm`, name crawlers, monitors and Cloudflare.

## 4 · Proof

Every test is seen red by breaking the code it covers.

| Test | Proves |
|---|---|
| unit, core | `before` bounds the answer; 0 means no bound; `country` never reaches the wire |
| unit, core | a shrink is refused the first and second time; the third, 24 h after the first, is stored and audited; a third inside 24 h is refused; a normal fetch between two refusals resets the count; a feed not in Current takes any size as before |
| unit, web | a country filter over a ring of 2 500 entries finds matches past the first 1 000 and stops at 200; the count covers the whole ring; an unknown code is a field error; with the lookup off the parameter is ignored and the select is absent |
| unit, web | a core that ignores `before` (it returns the same page again) ends the paging after one request and shows the notice |
| unit, web | a poll with a country set renders only new matching rows; with none it answers 204; a ring that went backwards gets the whole view |
| unit, catalogue | the order, verdicts and URLs of D1–D3; `blocklist-de` now needs the ✗ confirmation before it is staged |
| integration | an existing state with `blocklist-de` on still loads it after the upgrade (D4) |
| `check:ui` | the select filters the demo's rows to one country and the count says *of M*; the popover link sets the filter; the new feeds are listed in order |
| Chrome | /blocked with a country set, /blocklist, both themes, 1600 / 900 / 390 |

## 5 · Out of scope

- Filtering by several countries at once.
- A country filter on the audit log.
- Switching a feed off on upgrade (D4).
- The other blocklist.de service lists (`ftp`, `sip`, `strongips`): they are tiny, and an own feed can add them.
