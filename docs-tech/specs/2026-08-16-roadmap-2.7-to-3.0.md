## The situation

easywall 2.6.0 shipped today. The audience it is written for — someone running a
Raspberry Pi at home or a rented VPS, who does not know Linux well — appears
nowhere in the roadmap that ships with it. Both published roadmaps list
maintainer and operator work: integration tests, a protocol field, a REST API, an
installation count.

Two problems, and the first one is a security finding.

### The firewall is off after every reboot

`nft.Apply` is called from exactly two places: `internal/core/firewall.go:193`
(apply) and `:253` (rollback). Neither `NewFirewall`, nor `Daemon.Start`, nor
`cmd/easywall-core/main.go` puts the stored `current` rule set into the kernel at
startup. nftables rules do not survive a reboot.

So after a restart the machine is unfiltered until a human opens the web
interface and presses Apply. `Status()` reports it correctly —
`nftables.go:183 Enforcing()` asks the kernel rather than assuming — but only to
somebody who is looking. Nothing in `docs/` mentions it. The original Python
easywall had the same gap, reported as issue #22.

For a product whose first sentence is a safety promise, this outranks everything
else on either roadmap.

### The published roadmap describes work that is already done

Delivered in 2.6 |

## Decisions

| Question | Decision |
|---|---|
| Ordering principle | By exposure. The two holes an attacker actually walks through come first, then comprehension, then reach |
| Release size | One theme per release, sayable in one sentence |
| Model changes | Each travels with the feature that justifies it. Never twice, never speculatively |
| Reach of the product | It grows past a rule editor: counters, a drop stream, self-blocking, curated feeds, country blocks, egress control |
| Outbound traffic | Every source is switched on individually and is off by default. `docs/security.md` is rewritten in the same change that makes its current sentence false |
| Interface strategy | A service catalogue with folded depth. No simple/expert switch, and no page added to the sidebar by any of the twelve releases |
| Log parsing as root | Declined. See 2.17 |
| Passkeys | Moved behind 3.0. See 2.8 |
| Spec location | `docs-tech/specs/`, never `docs/` |
| Where this roadmap is published | `docs/roadmap.md` is rewritten from it; `README.md` carries the four nearest themes and links there. The two stop disagreeing |

## Principles

1. **One theme per release**, sayable in one sentence. The changelog heading then
   writes itself.
2. **A model change travels with the feature that justifies it.** `Blacklist
   []string` becomes objects exactly when comments and expiry arrive — not
   earlier as an end in itself, and not twice.
3. **A risky change brings its proof.** The veth harness in
   `nftables_forward_test.go` exists; every release that touches the packet path
   extends it instead of counting rules.
4. **Nothing produces outbound traffic unless somebody switches it on.** Feeds
   and country blocks are enabled one at a time, never as a group, never by
   default.
5. **Every new capability has to fit, folded, onto a page that already exists.**
   The sidebar carries twelve entries today (`web/templates/base.html:74-152`) and
   this roadmap adds none: egress becomes a third tab beside TCP and UDP, feeds
   and auto-blocking fold into the blacklist page, accounts grow out of the
   password page. Something that genuinely needs a thirteenth entry is not a
   feature any more; it is a second product.
6. **No feature lengthens the way back.** Whatever helps in an emergency has to be
   reachable without the web interface.
7. **The privileged process never opens a connection to the internet.** Established
   in 2.15, applied in 2.18, written into `docs-tech/threat-model.md`.

## 2.7 — The firewall survives a reboot

**The sentence:** after a restart the rules that were last confirmed are in force
again.

### What changes

The core puts `current` into the kernel before the socket accepts connections,
**with no acceptance window**. The reasoning belongs in the code, because it
looks like a breach of the central promise and is not one: `current` is by
definition a rule set that has already survived an acceptance window. Restoring
it is not a change — refusing to restore it is.

A window here would also be meaningless. Nobody is present to confirm, so it
would expire, and the rollback would land on `backup`, which nobody confirmed
either. A loop with no exit.

### What it costs, and what replaces it

Today a reboot is the accidental escape route: nftables is empty and the machine
is reachable again. This removes it. The replacement is a console tool —
principle 6:

```
easywall-core status    # Is the firewall enforcing? Which set? Since when?
easywall-core panic     # Flush table inet easywall. Unprotected, but reachable.
easywall-core resume    # Leave panic mode, put current back.
```

`panic` writes a marker (`/var/lib/easywall/panic`) that suppresses the
apply-at-start, because otherwise the next reboot locks the same person out
again. The interface shows the state as a loud banner with a control that ends
it.

One writer stays one writer: the CLI talks to the daemon over the socket. Only
when the socket is dead — so the daemon is not running — does it touch the table
directly.

That makes 2.7, not 2.8, the release that adds to the protocol: `PANIC` and
`RESUME` are the sixteenth and seventeenth commands, and three places currently
say fifteen — `docs-tech/protocol.md`, `docs/architecture.md:65`, and the
count assertion in `daemon_dispatch_test.go:371`. The test is the reason this
cannot be forgotten.

### Open, for the release spec

Docker. At boot `docker.service` may not be up, the bridges do not exist yet, and
the coexistence rules refer to interface names. Either a drop-in dependency when
`docker.enabled` is set, or a reconciliation once the bridge appears. Both have
sharp edges; that decision belongs in the release spec, not here.

### Proof

The veth harness is extended: flush the table (the reboot), start the daemon,
send a packet the restored set must drop. Plus the `panic`/`resume` round trip
and evidence that the marker survives a restart.

## 2.8 — A second factor

**The sentence:** a stolen password alone no longer opens the firewall.

### What is in it

TOTP for the single account, eight one-time recovery codes (argon2-hashed, shown
once), and — because it falls out here anyway — **login events in the audit
log**. Today there are none at all: a successful login, a failed one, a
rate-limited one and a logout leave no trace.

That needs a path the web process does not have. `WriteAuditLog` lives in
`internal/core/rules.go:317` and only the core calls it. A new, narrow socket
command that accepts a **fixed set of event types** and no free text is the right
shape; a general "append this line" command would let the network-facing process
write arbitrary history into the record.

It is the eighteenth command, after the two 2.7 adds, and
`TestDaemonDispatch_HandlesEveryDeclaredCommand` makes shipping it without a
handler impossible.

### The way back does not get longer

`docs/security.md` states it today: no mail, no outside service, the way back is
editing `web.toml` on the host. That stays exactly as it is — `totp_secret` is
one line in the same file, removed the same way. A second factor that needs a
second emergency exit is not one.

### Passkeys are deliberately not here

WebAuthn requires an RP ID that is a registrable domain suffix of the origin. A
bare `https://192.168.1.50:12227` does not qualify — Chrome and Safari reject IP
addresses as an RP ID. That is precisely how the target user reaches the device:
by address, with a self-signed certificate. Passkeys would be unavailable on the
majority of installations.

They move behind the release that gives the machine a name and a real
certificate — 3.0. Before that they would be a control that stays greyed out for
most people.

### Proof

Flow tests across the login path: correct password without a code, wrong code,
expired window, code replay, a recovery code consuming itself. Plus the existing
rule — the rate limit applies to the second step as well, or it is a six-digit
brute force.

## 2.10 — What changes is on the screen

**The sentence:** before applying, you see what happens — and whether it hits you.

### What changes

`/apply` gains the difference between `staged` and `current`, grouped by rule
type. No protocol work: `CoreClient.GetRules` (`internal/web/client.go:103`)
already returns `*shared.RulesState` with all three states, so the comparison
happens in the web process.

Two levels, because two audiences look at it:

```
┌─ This apply changes ──────────────────────────────┐
│                                                    │
│  3 ports open, 1 closes,                           │
│  12 addresses join the blacklist.                  │
│                                                    │
│  ⚠  Port 12227 closes — you are connected          │
│     through that port right now.                   │
│                                                    │
│  ▸ In detail                                       │
│      + tcp  8080        Nextcloud                  │
│      + tcp  443         HTTPS                      │
│      − tcp  12227       easywall web interface     │
│      + blacklist  45.9.12.0/24  … and 11 more      │
└────────────────────────────────────────────────────┘
```

The warning is the real gain. The web process knows `r.RemoteAddr` and its own
port (`handler_firstrun.go:73 webPort()`), so it can say *this cuts you off*
instead of demonstrating it 120 seconds later. The same holds for the port
carrying `SSH: true`.

### Proof

The comparison is a pure function: table tests for empty/empty, all new, all
gone, order changed, description changed. The interface goes through the rule in
`CLAUDE.md` — rendered, both themes, 1600/900/390, both languages, screenshots
retaken in the same change.

## 2.11 — A rule names a service and who may reach it

**The sentence:** you pick "Pi-hole", not "53/udp".

### Why the catalogue and the source restriction are one release

A catalogue entry without a source is wrong for the interesting cases: "Pi-hole"
means "from my network", not "from the internet". Shipped apart, every entry
created in the first would be rewritten in the second — exactly what principle 2
prevent.

### Model

`shared.PortRule` gains `Source []string` (empty = anywhere). The validation
exists: the same IP/CIDR checks the blacklist and whitelist use. Additive in
JSON, so an older export without `source` loads as "anywhere".

### Kernel

An `ip saddr` / `ip6 saddr` match against an anonymous set, before the `dport`
match. The order is assertable and is asserted.

### Catalogue

A curated table in the repository — **nothing is downloaded**, principle 4.
Around twenty entries, each with a reason to be there: SSH, HTTP/S, WireGuard,
Pi-hole, Nextcloud, Home Assistant, Jellyfin, Samba, Syncthing, Vaultwarden,
Minecraft. Each names ports, protocol, one sentence of explanation and a
**suggested reach** — SSH suggests "only my current address", Pi-hole "only my
network", HTTPS "anywhere".

"My network" is not a new invention: the single network definition shared by the
editor, the core and the demo since 2.6 gets used a third time rather than
written a first time.

The free path stays — the folded "individual ports and ranges" section. Someone
who wants to type port numbers types port numbers.

### The point where the catalogue tips over

It must not become a swamp. The rule for the release spec: an entry goes in
because it is common on a Raspberry Pi or a beginner's VPS, not because somebody
asked for it. The i18n parity tests that already exist apply to every catalogue
entry in both languages.

### Proof

veth: a packet from inside the permitted source range arrives, one from beside it
does not, with the rule otherwise identical. Plus catalogue tests — every entry
has valid ports and both translations.

## 2.14 — You can see it working

**The sentence:** every rule shows how often it fired.

Smaller than the outline first suggested. "You can see it working" held two
things — counters and a list of blocked connections. The list needs an event
stream out of the kernel, and 2.17 needs that stream anyway. It gets built once,
where it is unavoidable. This release is the counters.

### What changes

A `counter` on the rules, `Rule.UserData` as the label so a line read back can be
matched to its rule again. `GET_COUNTERS` is the nineteenth command.

### Where it shows

No new page. A column on the ports page, a number on each dashboard tile, "times
blocked" on the blacklist. The real gain for the target user is the inversion:

> *Port 8080 — no connection at all since the last apply. Do you still need it?*

An open port nobody uses is the most common avoidable exposure on a hobby server,
and nobody finds it because nobody goes looking. A counter reading zero finds it.

### The honesty requirement

The table is rebuilt on every apply, so the counters restart at zero. It has to
say "since the last apply", or the number lies. Do not compute across the
rebuild: a summed number that looks measured is worse than a reset.

## 2.15 — When something happens, you hear about it

**The sentence:** a rollback reaches the phone, not only the journal.

**Events:** apply rolled back · apply confirmed · panic mode active · repeated
failed logins.

**Channels:** a generic webhook, and ntfy. No SMTP — credentials in `web.toml`,
foreign mail servers, deliverability; that is a barrel, and for this audience a
push to the phone is closer to hand than an email anyway.

### The architectural decision this fixes in place

The events originate in the core, which runs as root. It does **not** send them.
Instead the web process polls for new audit entries in the background — `GET_LOG`
with a `since` — and turns them into notifications. So the rule holds: *the
privileged process never opens a connection to the outside.* That is the same
separation as the rest of the product and belongs in
`docs-tech/threat-model.md`.

### What the message contains

Event type and timestamp. **No rule contents.** A webhook goes to a third party;
your own whitelist is not something that belongs there. The destination is named
in the interface, the way the telemetry line on `/system` already does it.

### Proof

A test server as the far end: exact payload, a disabled channel sends nothing, a
failure does not stall the loop, and a test that fails as soon as an address from
the rule set appears in a payload.

## 2.16 — Every entry has a why and an until

**The sentence:** blacklist entries carry a comment and an expiry.

### Model

`Blacklist []string` → `[]ListEntry{Address, Comment, Expires}`. Those two fields
and no others — no stock kept for 2.17 and 2.18. An extra JSON field later is
cheap; a second migration of the same entries is not.

A custom `UnmarshalJSON` accepts both shapes so `rules.json` and every older
export still load. That is the actual work of this release, not the interface.

### Expiry needs a trigger

An expired entry does not leave the kernel by itself. The core gets a timer on
the next due expiry and re-applies then — **with no acceptance window**, on the
same reasoning as the boot apply: removing a block cannot lock anyone out.

That does **not** hold for the whitelist, where an expiry removes a permission and
very much can lock someone out. The warning from 2.10 therefore fires at save
time: *this entry expires on 3 September and describes the address you are
connected from.*

### Interface

The textarea becomes a table, the way the ports page already is: address,
comment, expiry as chips (1 hour · 1 day · 1 week · never). The textarea survives,
folded, as "paste a list" — people copy address lists out of forums, and that has
to keep working in one go. `POST /iplist/validate` changes shape with it.

## 2.17 — Whoever knocks gets locked out

**The sentence:** repeated knocking on closed doors blocks itself, in the kernel.

### This substitutes for log parsing, deliberately

The brainstorm asked for a core that reads journald/auth.log. This proposes
something else that reaches the same outcome without turning the root process
into a log parser. **The decision is open to reversal**; if log parsing is wanted
anyway it becomes its own release after 2.17, with its own attack-surface review.

### What it is instead

nftables has dynamic sets with timeouts: a rule may execute
`add @blocked { ip saddr timeout 1h }` when it matches. Someone hitting closed
ports three hundred times in four minutes locks themselves out **with no
userspace involved at all**. No journal, no root-side parser, and it behaves the
same in a container as on a Pi.

### The credential case goes the other way round

A reimplemented fail2ban would be a root log parser and a permanent building site
of regexes for other people's services. Instead easywall exposes a **named,
documented set that fail2ban and CrowdSec can write into** — both drive nftables
sets, and both are already installed on plenty of machines in this audience. A
dozen lines of documentation instead of a subsystem, and someone running neither
loses nothing: the knock protection above covers the common case.

### So it is not a black box

The view deferred from 2.14 arrives here. The core subscribes to the netlink log
group (NFLOG) and keeps the last 500 rejections in memory, bounded. The interface
can then answer *why* an address is blocked — 312 attempts on port 22 in four
minutes — instead of only *that* it is.

## 2.18 — Other people's lists, and countries

**The sentence:** curated blocklists and country blocks, each switched on
individually, all off by default.

### Who downloads

The web process — never the core. Same separation as the notifications, which
turns it from a one-off into a rule. The web process fetches, validates, bounds
and hands the result over the socket.

### Geo without an account

MaxMind wants an account and a licence key: a hurdle for a beginner and a
dependency on somebody else's terms for us. Country zones derived from the RIR
delegation files instead — free, no key, and the derivation is checkable.

### The finding that shapes this release most

`nftables_semantics_test.go` locks in that the **blacklist is evaluated before the
whitelist**. That is right for a list you wrote yourself — but it means a feed
that happens to contain your own address locks you out **even though it is
whitelisted**. With ten thousand entries from someone else's hand that is not an
edge case.

Therefore: **feed sets are consulted after the whitelist, unlike the manual
blacklist.** You wrote your own blacklist; you did not write the feed. The
difference is surprising and so it has to appear in the interface, not only in the
code.

### Distrust of the source, as hard conditions

A ceiling on size and on entry count · refusal when the new version differs from
the previous by more than 30 per cent, so an emptied or poisoned list cannot pass
quietly — the figure is a starting value the release spec may revise against real
feeds, but there is a figure and it is enforced · a feed may **only block, never
permit** · a failed fetch keeps the previous version rather than emptying the set.

### Documentation that must change with it

`docs/security.md` states the update check is the only outbound request easywall
makes. That sentence becomes false here and is rewritten in the same change.

## 2.19 — Outbound traffic

**The sentence:** what the server may send out becomes configurable.

The output chain is created at `internal/core/nftables.go:311` with policy
`ACCEPT` and **not one rule** — the name "output" appears nowhere else in the
file. Outbound traffic is today neither filtered nor configurable.

`output.mode`: `open` (the default, as today) or `allowlist`. Presets are not a
convenience here but a precondition — DNS, NTP, HTTP/S, the distribution's
package sources.

### Two rules that cannot be switched off

First, `ct state established,related accept` in output. Without it the SSH session
being used to configure this dies, because the replies to an inbound connection
leave through the output hook.

Second, whatever easywall itself needs outbound — update check, telemetry,
notifications, feeds — is permitted automatically for as long as that feature is
on. A firewall that blocks its own feed refresh is an error message nobody can
interpret.

This is the release with the highest lockout risk on the list. It gets the
acceptance window, the diff from 2.10 and a round of its own on the veth harness.

## 2.20 — More than one account

**The sentence:** more than one person, and the record says which one.

The `user` field in the socket protocol — the item that has been on the roadmap
since 2.5. `WriteAuditLog` already takes a `user` argument; the protocol does not
carry one, so `internal/core/daemon.go` passes the literal `"web"` in six places
(lines 230, 260, 287, 304, 321, 365). Afterwards it says who.

Two roles, no more: **administrator** and **observer**. The observer may see
everything and apply nothing — for the housemate who wants to know whether the
server is up, and for oneself when checking from a machine one does not trust. A
five-tier role model on a one-person Pi would be a parody.

`web.toml` gains an `[[account]]` array. The way back is unchanged: edit the file
on the console.

## 3.0 — Reachable from outside

A REST API with token authentication, built on the accounts from 2.20 · ACME as an
alternative to a reverse proxy · a **list** of trusted proxy addresses whose
`X-Forwarded-For` is believed, never a switch — the boolean is the vulnerability
in GHSA-3fxj-6jh8-hvhx, GHSA-rjr7-jggh-pgcp and GHSA-9g5q-2w5x-hmxf, which
`internal/web/server.go:226` already cites · and **now the passkeys**, because from
here there is a hostname and a real certificate, without which WebAuthn is not
selectable on most installations.

A major version, because an API is a second public interface and a compatibility
promise easywall has not made before.

## Deliberately excluded

| | |
|---|---|
| SMTP notifications | Credentials in `web.toml`, foreign mail servers, deliverability. ntfy reaches the same phone without any of it |
| A reimplemented fail2ban | Replaced by the set the real one can write into |
| Zones, on the firewalld model | easywall runs on hosts with one uplink; what zones would be for is covered by `routing.mode` |
| Rule schedules | "Open this port between 08:00 and 18:00" sounds useful and is a state machine nobody can debug once it is in the wrong state |
| IDS/IPS, deep packet inspection, QoS | Different products. easywall filters packets |
| Managing several hosts from one interface | The API in 3.0 makes Ansible possible. A fleet interface is a second product |

## Risks

1. **Twelve releases is more than a year.** The roadmap says "planned in this
   order", not "promised" — and it gets corrected when something changes rather
   than quietly ageing. That is exactly the failure the current one demonstrates.
2. **2.7 removes the reboot escape route.** `easywall-core panic` has to be
   documented *before* 2.7 ships — in the release notes, on the site and in the
   man page. Not afterwards.
3. **The catalogue in 2.11 grows without end** if the admission rule is soft.
4. **2.18 makes a sentence in `docs/security.md` false.** It is rewritten in the
   same change, or the documentation lies about a security property.
5. **2.19 carries the highest lockout risk** of anything on this list.

## What happens to the published roadmaps

`docs/roadmap.md` is rewritten from this document: the delivered items move into a
"Done in 2.6" section, the duplicate 2.9 goes, and the twelve themes above take
their place. `README.md` keeps the four nearest ones and links there instead of
maintaining a second, diverging copy. The contradiction at `CHANGELOG.md:231`
and `:235` is resolved in favour of what the code does, and the second `### Added`
block in 2.5.0 is merged into the first.

## What has happened since

**2.7 shipped** on 2026-08-18 as described, plus two findings the work turned up:
every timestamp in the interface was converted in the stored zone rather than the
viewer's, and the container image had no `tzdata`. `PANIC` and `RESUME` are the
sixteenth and seventeenth commands, and the three places that said fifteen now
hang off `shared.AllCommandTypes` with four guards instead of three hand-kept
mirrors.

**2.8 is designed** — see `2026-08-19-2.8-second-factor-design.md`. It follows
the outline above (TOTP, eight recovery codes, login events in the audit log) and
adds two riders: the running version is displayed nowhere in the interface
(`web/templates/base.html` carries the literal `v2`), and credential-writing
routes do not check for demo mode, so a visitor to the public demo can change the
password and lock everyone else out. `LOG_EVENT` is the eighteenth command, as
predicted.

## The order changes: two new items

Requested during the 2.8 brainstorm — more languages than English and German,
for coverage outside the two countries the project currently speaks to.

The cost lands in an awkward place. `locales/{en,de}.json` hold 404 keys each and
the coverage tests enforce **exact parity**: a missing key fails the build. With
eight languages that is a brake on every feature from here on — 2.9 through 2.17
each add strings, and each would be blocked until all eight translations exist,
or the rule becomes a sham because somebody copies the English text in to make
the test green. A French interface displaying English while the project claims to
support French is worse than no translation, for the same reason a stale
screenshot is worse than none.

So the work splits, and the split is dictated by principle 2. A fallback
mechanism with no third language is stock: while only `en` and `de` exist it
changes nothing, and a guard relaxed before anybody needs the relaxation is a
guard nobody will notice later. **French therefore travels with the mechanism.**

### 2.9 — The interface speaks French, and the next language need not come from us

**The sentence:** a third language can arrive without us writing it.

- Parity becomes **fallback** for everything except `en` and `de`, which keep the
  hard rule. A missing key renders the English string and is *reported*, not
  hidden.
- A coverage report per language, and a state a language can be in: present but
  not reviewed by a human.
- A guide in `CONTRIBUTING.md`.
- `fr.json`, drafted in-house and shipped **visibly marked as unreviewed** — in
  the switcher and in the report. The roughly thirty security-bearing sentences
  (evaluation order, what a block does, what an acceptance window promises) are
  collected in a list a reviewer reads first, rather than starting them at key 1
  of 404.
- **The language switcher is rebuilt.** Two chip buttons in a `--sidebar-width`
  of 240 px do not hold eleven languages: `.lang-options` wraps, and the
  endonyms of the languages on this roadmap come to roughly 720 px, so the switch
  becomes a four- to five-row block at the foot of a sidebar that then scrolls —
  in order to let somebody who cannot read the interface change its language.
  It becomes a `<select>` plus a submit button, progressively enhanced: without
  JavaScript both are visible and work, with JavaScript the form submits on
  `change` and the button is hidden. The "JavaScript is present" flag is set in
  the existing nonced head script that already sets `data-theme`, **not** in
  `app.js` — that file loads at the end of `<body>`, so the button would appear
  and then vanish. The `<select>` also gives the native OS picker at 390 px,
  which is the best mobile behaviour available and costs nothing to build.
  Four include sites: `base.html`, `login.html`, `firstrun.html`, and
  `login_verify.html` once 2.8 has added it.

The no-JavaScript requirement is not negotiable and is already written down above
`{{define "langswitch"}}`: *an operator who cannot read the interface should not
also need JavaScript to fix that.*

### 2.19 — Nine languages

**The sentence:** the interface speaks the languages this audience actually uses.

Spanish, Portuguese (Brazil), Italian, Dutch, Polish, Russian, Chinese
(Simplified), Japanese. Chosen for self-hosting and Raspberry Pi communities
rather than for global speaker counts. One pass over a string set that has
stopped moving, instead of nine passes over a growing one.

**No right-to-left.** Arabic and Hebrew are not a translation but a design-system
change — every `margin-left`, every directional icon, the whole sidebar. That is
its own item or none, and it must not slip into a list as "one more language".
