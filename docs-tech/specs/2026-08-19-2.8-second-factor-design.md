## Decisions

Each row was decided in brainstorming; the reasoning is in the section named.

| Question | Decision | Why, in one line |
|---|---|---|
| Shape of the login | **Two steps.** `/login` unchanged, then `/login/verify` | The second step gets its own bound without spending password attempts |
| Login events → audit log | **`LOG_EVENT`, fixed enum, debounced in the core** | A failed login is unauthenticated input reaching the root process's log |
| TOTP implementation | **Hand-written against RFC 6238 vectors; one dependency for the QR image** | The RFC ships its own test vectors; a QR encoder is Reed–Solomon and not our craft |
| Hash algorithm | **SHA-1, fixed, not configurable** | See *Why SHA-1* |
| Where state lives | **Secret and codes in `web.toml`; last accepted step in `data_dir`** | `web.toml` is not rewritten non-atomically once per login |
| Second-step limiting | **Attempt counter inside the pending cookie, three tries, then it dies** | Binds code attempts to the already-limited password rate |
| Language switcher rebuild | **Deferred to 2.9** | It breaks with the third language, so it travels with the third language |

## Why SHA-1

Cryptographically this is not a compromise. HMAC's security rests on preimage
resistance and the PRF property, not on collision resistance, so the SHA-1
collision attacks do not reach HMAC-SHA1. NIST SP 800-131A Rev. 1 permits SHA-1
for HMAC, KDFs and random bit generation and forbids it only for digital
signatures and timestamps. The Rev. 3 draft deprecates SHA-1 through 31 December
2030 and disallows it after — a date to know, not a date that is now.

Interoperability is the actual constraint, in the opposite direction. Google
Authenticator has supported SHA-256/512 since 2014, but a substantial share of
apps silently ignore the `algorithm=` field of an `otpauth://` URI, and Microsoft
Authenticator is effectively SHA-1 only. The failure mode is the wrong one for
this audience: the app shows six digits, the digits do not match, and nothing
distinguishes a mistyped key from a wrong clock from an unhonoured algorithm
parameter. A silent failure while enrolling a second factor is a lockout.

So: the internal function takes the hash constructor as a parameter, because the
RFC's own vectors cover all three and testing all three is therefore free. The
URI and the enrolment path hard-code SHA-1. **No switch in the interface and no
key in `web.toml`.** The code comment names the 2030 date and the interop reason,
so the next reader does not mistake it for negligence.

### The new dependency

`github.com/boombuler/barcode` v1.1.0 (22 July 2025), MIT, standard library
only, no transitive modules. Verified before adoption: the objection to
`skip2/go-qrcode` is that it has been archived since 2021, which makes it a
dependency Renovate can never move.

### Two states, two different decisions

**The login's intermediate state is a cookie.** Own name (`easywall_pending`),
own short expiry, `Path=/login` so it is not sent anywhere else, signed with the
same session key. It carries username, credential fingerprint, attempt counter
and issued-at. `sessionUser()` never looks at it — the reason not to add a field
to the existing session is the bug `middleware.go` already documents above
`sessionUser`: two places answering "signed in" differently produced a redirect
loop that ended in `ERR_TOO_MANY_REDIRECTS`. A cookie that is not a session
cookie cannot answer that question wrongly.

It is a cookie rather than a server-side table because **unauthenticated**
requests create it: a map any stranger can fill is memory any stranger occupies.

**Implementation note that has already cost one release:** build its store with
`store.MaxAge(180)`, never `Options.MaxAge`. `auth.go`'s comment on
`newSessionStore` records why — assigning a fresh `Options` struct leaves the
codec's own thirty-day max age in place, which is how a logged-out cookie stayed
valid to the server for a month.

**The enrolment's pending secret lives in memory.** A small table on the pattern
of `revokedSessions`, keyed by session ID, with an expiry. The reasoning
inverts: enrolment is **authenticated**, there is exactly one account, so the
table never holds more than a handful of entries and no stranger reaches it. In
exchange, an unconfirmed secret never enters a cookie — `gorilla/sessions` with
only a hash key **signs but does not encrypt**, so a cookie value is readable
plaintext. It would be on screen as a QR code anyway, so this is not a breach;
it is merely unnecessary. A restart mid-enrolment then means "start again"
rather than "an unconfirmed secret is sitting in a browser store".

## Data flow

### The login

```
GET /login
  IsFirstRun? -> /firstrun
  valid session? -> /dashboard
  else: the form

POST /login  [LoginRateLimit: 5 / 10 min / IP]
  | argon2 and the name comparison both always run (unchanged)
  |
  +- wrong ---------------> flash, /login              => login_failed
  |
  +- right, no factor ----> session, /dashboard        => login_ok
  |
  +- right, factor set ---> set easywall_pending, 303 -> /login/verify
                            { user, credfp, attempts=0, iat }, MaxAge 180s
                            NO session. Nothing sessionUser() reads.

GET  /login/verify   missing / expired / foreign cookie -> /login
POST /login/verify   [no IP limit of its own — see below]
  | one field; the shape decides
  |
  +- six digits ---------> TOTP, window +/-1 step
  |                        AND step > last accepted step (replay)
  |                        ok -> store step, delete pending, session
  |                                                     => login_ok
  |
  +- recovery shape -----> against the eight argon2 hashes, all eight, no early exit
  |                        ok -> remove that hash from web.toml, session
  |                        flash: "7 recovery codes left"
  |                                                     => login_recovery_used
  |
  +- otherwise ----------> attempts++                   => login_2fa_failed
                           attempts >= 3 -> delete pending, /login
```

**Why `/login/verify` has no IP limit of its own**, as arithmetic: one
intermediate state allows 3 code attempts; a new intermediate state costs one
password round; those are capped at 5 per 10 minutes per address
(`middleware.go:141`, `rate.Every(2*time.Minute)` with burst 5). That is **15
code attempts per 10 minutes per address** against a target that rotates every
30 seconds. Without a valid cookie the route is a redirect and costs nothing.
The only amplifier is recovery-shaped input, which runs eight argon2
verifications (~300 ms), bounded by the same 3 attempts per state.

Consuming a recovery code does write `web.toml`, and that is not a contradiction
of the decision above: it happens at most eight times in the life of an
enrolment, not once per login. The rejected shape was a rewrite of the credential
file on *every* successful sign-in.

**Replay, precisely:** store the step that *matched*, not the current step.
Otherwise a code accepted at `N-1` also burns the still-valid step `N`, locking
the operator out for 30 seconds immediately after a successful login.

All eight recovery hashes are checked with **no early exit on match** — the same
stance `handler_login.go` already writes out for not short-circuiting argon2
against the name comparison.

### Enrolment

```
/password shows: "Second factor: off"  [Set up]

POST /password/2fa/begin      current password required
  -> generate secret, into the in-memory table (session ID -> {secret, iat})
  -> page with QR (data: URI), the key in plain text, the server time, one code field

POST /password/2fa/confirm
  +- code hits at +/-1 --> web.toml: totp_secret + 8 argon2 hashes, ONE write
  |                        fingerprint changes -> every other session ends
  |                        re-stamp our own
  |                        show the eight codes ONCE       => totp_enabled
  |
  +- code hits at +/-10 -> "The code is right, but this server's clock is about
  |                         4 minutes behind." Nothing stored.
  |
  +- no hit -------------> "Wrong code." Nothing stored.

POST /password/2fa/disable    current password required   => totp_disabled
POST /password/2fa/recovery   current password required   => recovery_codes_regenerated
```

Four routes, all `POST`, all inside the authenticated group and therefore under
the existing `http.NewCrossOriginProtection`. The page shown after `begin` is
not a `GET` with its own URL: it is rendered as the response to the `POST`, so a
reload cannot mint a second secret and the page cannot be bookmarked.

**Enabling and disabling both require the current password** — the same rule the
page already applies to changing it. No additional code prompt on disable:
whoever is at that form already holds a session that came through the second
factor, and a further code would only create a new lockout case (phone gone
*and* codes gone = cannot even switch it off) against no attacker it stops.

**`credentialFingerprint` covers the TOTP state.** It hashes the password hash
today; it hashes hash **and** secret from here. Enabling or disabling therefore
ends every other session at that moment, and the acting one is re-stamped
exactly as `handler_password.go` already does after a password change. A second
factor that lets previously open sessions run on protects from the next login,
not from now.

### The eighteenth command

```go
type LoginEvent string   // internal/shared/protocol.go

const (
    EvLoginOK         LoginEvent = "login_ok"
    EvLoginFailed     LoginEvent = "login_failed"
    Ev2FAFailed       LoginEvent = "login_2fa_failed"
    EvRecoveryUsed    LoginEvent = "login_recovery_used"
    EvRateLimited     LoginEvent = "login_ratelimited"
    EvLogout          LoginEvent = "logout"
    EvTOTPEnabled     LoginEvent = "totp_enabled"
    EvTOTPDisabled    LoginEvent = "totp_disabled"
    EvRecoveryRenewed LoginEvent = "recovery_codes_regenerated"
)

var AllLoginEvents = []LoginEvent{ /* all nine */ }

type LogEventPayload struct {
    Event LoginEvent `json:"event"`
    Addr  string     `json:"addr"`   // netip.ParseAddr'd in the core
    Left  int        `json:"left"`   // login_recovery_used only
}
```

No free text. An event not in `AllLoginEvents` is refused and **nothing is
written** — the web process cannot invent a line. `Addr` goes through
`netip.ParseAddr` and is normalised in the core; if that fails the entry is
written **without** an address rather than dropped, because the entry is the
record and the address is the annotation. `Left` is an integer and can smuggle
nothing.

Guard tests hang off `AllLoginEvents` the way four of them hang off
`AllCommandTypes` after 2.7: dispatch knows each, `audit-log.md` documents each,
both locales label each.

### Getting there must never delay a login

The event is a side effect, not a precondition. `internal/web/auditevents.go`
holds a buffered channel (64) and **one** sender goroutine. The handler drops
its event and moves on. When the buffer is full the event is discarded and a
counter goes to the journal — more honest than throwing unbounded goroutines at
a socket that is not answering. When the core is unreachable the line goes to
the journal and the login proceeds: a crashed core must not take the firewall's
interface with it. That is 2.7's principle, inverted.

`login_ratelimited` originates in middleware, which must not know `CoreClient`.
`LoginRateLimit` therefore gains `onBlocked func(ip string)`, supplied by the
server when it builds the router — testable, and `middleware.go` stays free of
the client.

### The debouncer, in the core

The finding that forces it: `GET_LOG` hands the web process the **last 200
lines** (`daemon.go`, `readAuditLog(..., 200)`) and `debian/easywall.logrotate`
rotates daily with no size ceiling. A failed login is an **unauthenticated**
operation. Roughly forty addresses at five attempts per ten minutes each fill
those 200 visible entries within an hour and push an `apply_rolledback` out of
view. The log does not fill; the page that shows it becomes useless — and that
page is what 2.12 will build notifications on.

`internal/core/loginevents.go`. Debounced: **only** `login_failed`,
`login_2fa_failed` and `login_ratelimited` — the three a stranger can trigger.
Successes, logout and the three enrolment events are rare and operator-caused,
and are written immediately.

```
window 60s, key (event, address)

first in window   -> write immediately    detail: "from 203.0.113.7"
subsequent        -> count only
window closes     -> if count > 1:        detail: "from 203.0.113.7, 13 more within 60s"
```

Two lines per burst, never more. The first immediately, so an operator who is
watching sees it; the summary afterwards, so a scanner cannot fill the 200.

**And a ceiling, because this runs in the root process on input from outside:**
the table holds at most 1024 addresses. Beyond that, further addresses fold into
one aggregate bucket (`detail: "from 1731 addresses, 40219 within 60s"`) so the
record still shows the volume while the memory does not hang off a number a
stranger chooses.

### None of the nine gets a colour

The colour table in `server.go` states its rule: colour describes **what the
firewall is doing**, not whether a human meant it. That is why
`apply_refused_panic` and `rollback_skipped` are deliberately absent. A failed
login does not change what the firewall is doing; it is read, not signalled. All
nine are uncoloured, with a comment pointing at that rule. That 2.12 will push
on `login_failed` is not a contradiction: a notification is not a colour.

`user` stays `"web"` for all nine, as every existing call site passes it. The
submitted username is **not** echoed: that would be foreign text in the record,
and with exactly one account it says nothing. The field becomes real in 2.17
(then 2.18 — see *Roadmap change*), and a half-true field now would collide with
that release.

## The version

`web/templates/base.html:68` is `<span class="brand-version">v2</span>` — a
literal, and not even the version but the major. It would have read `v2` in 2.5
and will read it in 2.19. `shared.CurrentVersion` reaches the templates by two
paths and neither shows it: `server.go:420` uses it as an asset cache-buster,
and `dashboard.html:11` wraps `.Version` in `{{if .Version.UpdateAvailable}}`,
which names the **new** version and never the installed one. Whoever is current
sees nothing; whoever is not learns where to go but not where they are.

This is the class of defect `CLAUDE.md` already records under "`-ldflags -X`
writes to a `var`": the release machinery was never the problem, the displaying
was. The first question on any bug report is the installed version, and today
the operator has to SSH in and run `easywall-web --version` — on a product whose
purpose is that they do not have to.

**Two places.** The sidebar chip becomes the real version. `.brand-version`
(`app.css:322`) is a mono chip with `margin-left: auto`, so it grows leftward
into the brand block; `-ldflags -X` can also write `2.8.0-3-gabc1234` there, so
it gets a width ceiling with an ellipsis and the full string in `title`. That is
verified in a screenshot at 390 px with a long value, not in a diff — it is the
clipped-port-number class from `CLAUDE.md`.

The dashboard says the version in **both** cases. The reason not to leave it at
the chip: at 390 px the sidebar is a drawer behind the menu button, and the
first question in every bug report must not sit behind an interaction.

`PageData` gains a `Version` field even though `Asset` holds the same value
today. Two names because two reasons: `Asset` hangs off asset URLs and may
become a build hash tomorrow without anyone thinking about it; `Version` is what
an operator reads. Displaying it through `Asset` is the coupling that produces
"easywall v3f9a1c" on the first build hash.

A guard test scans `web/templates/*.html` for a version literal and fails on
one. That is the half that keeps it from coming back.

**The consequence, which is large:** the chip is on every screenshot.
`docs/assets/img/screens/` holds 22 files, 20 of which show the sidebar (only
`login-{light,dark}` do not). All 20 say `v2` today and must be retaken — not
because the page changed, but because the documentation would otherwise show an
interface that no longer exists. The rule that demands it is the rule that
justifies it.

## The demo finding

`grep -n "IsDemo\|DemoMode" internal/web/*.go` returns six occurrences and
**none of them is in a handler**: `client.go:31-32` (the predicate),
`config.go:76` (validation), `server.go:98` (swap the client), `:118` (disable
telemetry), `:415` (the banner flag).

`POST /password` does not test for demo mode. `handlePasswordPOST` calls
`s.cfg.SaveCredentials(...)`, which writes `web.toml`. So on the public demo any
visitor can **today** change the password and lock everybody else out until the
process restarts. That is a pre-existing defect, not one 2.8 introduces — but
2.8 makes it considerably worse: whoever enrols TOTP on the demo walks away with
the QR code and leaves a demo nobody can enter, not even with the published demo
password.

The fix belongs in this release because this release touches the credential
surface. In demo mode, `POST /password` and all four 2FA routes **show**
everything and **write** nothing:

- `POST /password` refuses with a flash. There is nothing to demonstrate past the form.
- The 2FA routes run the whole flow — a real QR code, a real code check, real
  recovery codes on screen — and discard the final write, saying so plainly.
  The visitor sees the entire feature; nobody is locked out.

Plus a guard test that enumerates the credential-writing routes and asserts each
refuses to persist in demo mode. A new route of that kind has to enter the list.

**Open:** how the public demo is actually deployed. If its `web.toml` is
read-only, today's effect is an `internal_error` rather than a lockout. That does
not excuse the code; it explains why nobody noticed.

describes the way back as editing `web.toml` on the host, and from this release
that describes half of it. The `totp_secret` line has to be named, in both

to the text this fix makes wrong.

### The verify page

`login_verify.html`, built like `login.html` — centred, no sidebar, no topbar,
because nobody is signed in yet.

```
        easywall

  Code from your app, or a
  recovery code

  [ ______________________ ]   autofocus, inputmode="numeric",
                               autocomplete="one-time-code"
```

`type="text"`, not `type="number"`: a recovery code has letters, and

`firstrun.html:145`. Whoever is standing at the second step must be able to
change language.

### The eight codes, once

Shown after `confirm` as a mono grid with a **copy** button. No download route:
a URL that serves the codes turns "shown once" into "retrievable at any time",
and a `blob:` download would run into `default-src 'self'`. The clipboard API
needs no CSP change. Below them, unambiguously: *these codes will not be shown
again.*

### Recovery code format

Five plus five characters from the Crockford base32 alphabet (no I, L, O, U), 50
bits per code, printed as `XXXXX-XXXXX`. Not confusable with six digits, so one
input field can take either. The length is a starting value the implementation
may revise; the requirement is that the shape is unambiguous and that the
alphabet excludes what people mistype.

## Error cases

| Case | Behaviour | Why |
|---|---|---|
| Core unreachable | Login works; the event goes to the journal | A crashed core must not take the interface with it — 2.7, inverted |
| `web.toml` unwritable at `confirm` | Nothing enabled, message shown, **pending secret stays in memory** | Otherwise the operator re-pairs their app because the disk was briefly full |
| Server clock wrong | The +/-10 diagnosis at enrolment, with signed magnitude | The fault is on the server; the message must not point at the human |
| Password changed while a pending state is open | The intermediate state is refused | It carries the fingerprint; a password change ends half-logins too |
| Recovery code hits but consuming it fails | **The session is granted**, `crit` to the journal, warning in the interface | The code is in the operator's hands, not an attacker's. "Full disk locks you out of your firewall" is the worse outcome — the same weighing as "refusing to restore is worse" in 2.7 |
| Three wrong codes | Pending deleted, `/login`, "Please sign in again" | Does not reveal which factor failed |
| Session key rotated | Every cookie including the pending one becomes invalid | Correct and intended |

## Proof

### RFC 6238, Appendix B

The vectors for SHA-1, SHA-256 and SHA-512 across the six T values from 59 to
20000000000. The point where hand-written TOTP usually goes wrong, and the
reason the test covers all three: the RFC uses **seeds of different lengths**
per algorithm (20/32/64 bytes), not one shared seed. Feeding the 20-byte seed to
SHA-256 produces numbers that look plausible and are wrong. The vectors are
eight digits; the six-digit assertion is derived (`mod 10^6`) and checked too.

### The bound the roadmap asks for

The roadmap requires "the rate limit applies to the second step as well, or it is
a six-digit brute force". It is proved in the form chosen in brainstorming rather
than as a second bucket: a test drives five password rounds of three code
attempts each from one address and asserts that the **sixteenth** code attempt
within ten minutes does not get through. The arithmetic in this document is then
an executable claim rather than a paragraph.

| Area | Assertion |
|---|---|
| Replay | the same code twice, second refused; accepted at `N-1` leaves `N` valid; the stored step survives a restart |
| Window | +/-1 accepted, +/-2 refused; +/-10 only at enrolment, with correct magnitude and sign |
| Pending | authenticates nothing (`/dashboard` with only that cookie -> `/login`); a forged counter is invalid; expired after 180 s; refused after a password change |
| Recovery codes | eight, pairwise distinct, correct shape; consuming one leaves seven; a consumed one no longer matches; regenerating invalidates all eight old ones |
| Fingerprint | enabling and disabling end other sessions, the acting one survives |
| Debouncer | 14 failures in 60 s produce **exactly two** lines with the right numbers, the first immediately; an unknown event is refused and **nothing** written; an unparseable address yields an entry without an address, not a drop; the 1025th address lands in the aggregate bucket and memory stops growing |
| Guards | the four `AllCommandTypes` guards at **18**; `AllLoginEvents` across dispatch, `audit-log.md` and both locales; the demo client answers `LOG_EVENT` |
| Config | both new keys survive the save round trip with comments intact (`render()`); a `web.toml` without them loads; `config_docs_test.go` and `config_schema_test.go` know them |
| Version | no version literal in `web/templates/*.html`; `PageData.Version` equals `CurrentVersion`; the dashboard names it with no update available |
| Demo | every credential-writing route refuses to persist, enumerated in a list a new route must join |

**No kernel integration tests.** This release does not touch the packet path;
the veth harness is untouched. That is not an omission but the answer to "a risky
change brings its proof": this release's risk is in the login path, and that is
where the tests are.

### The browser

`ui-check.mjs` gets two runs instead of one.

**Run 1, against the demo** (as today): `/password` with the new card joins
`PAGES`; then `begin` -> the QR appears -> the script turns the displayed key
into a code with `node:crypto` -> `confirm` -> the eight codes appear -> the
"nothing is saved in the demo" notice is present. That exercises the TOTP maths
end to end through the browser with no dependency in the script.

**Run 2, a second instance with prepared state.** The verify page is
unreachable in the demo, because no secret is ever stored there — and it is the
page a half-locked-out human meets first. So the script writes a `web.toml` with
a known password hash and a known `totp_secret`, starts `easywall-web` with it
(the socket path points nowhere; the login path does not need the core, and the
dashboard then shows its `CoreErr` banner) and drives: password ->
`/login/verify` -> computed code -> `/dashboard`; plus three wrong codes ->
back to `/login`.

This is also the only way to take `two-factor-verify-{light,dark}` at all. The
scaffolding is required either way; here it merely gets a name.

## Roadmap change

The i18n item from brainstorming, resolved against principle 2 (*a model change
travels with the feature that justifies it, never earlier as an end in itself*).
A fallback mechanism with no third language is stock: while only `en` and `de`
exist it changes nothing, and a guard relaxed before anyone needs the relaxation
is a guard nobody will notice later. **French travels with the mechanism**, which
gives it its justification and brings the language that was asked for forward by
about a year.

```
2.9  (new)   The interface speaks French — and the next language need not come from us
             - parity becomes fallback for everything except en/de, which stay hard
             - a coverage report per language, shown rather than hidden
             - a guide in CONTRIBUTING.md
             - the language switcher rebuilt: <select> + submit, progressively enhanced
             - fr.json as the proof the mechanism carries, shipped marked as unreviewed

2.10 … 2.18  today's 2.9 … 2.17, shifted by one

2.19 (new)   Nine languages — Spanish, Portuguese (BR), Italian, Dutch, Polish,
             Russian, Chinese (Simplified), Japanese. One pass, once the string
             set is stable. No RTL: that is a design-system change, not translation

3.0          unchanged
```

French is drafted in-house and ships **visibly marked as unreviewed**, in the
switcher and in the coverage report — the mechanism has to be able to express
"present, but not checked by a human" anyway, or a contributed language cannot
be either. The roughly thirty security-bearing sentences are collected in a list
a reviewer reads first, rather than starting them at key 1 of 404.

Renumbering costs the table and the code block in `docs/_docs/roadmap.md` and
the four nearest themes in `README.md`. The roadmap document says of itself that
it gets corrected rather than quietly ageing; this is the first occasion to show
that.

## Risks

1. **The clock.** The largest support risk and no security risk. Hence the
   server time permanently on the enrolment page rather than only in an error.
2. **The way back must be documented before the release**, not after. See
   *Documentation*.
3. **Twenty screenshots**, hanging off one changed line in `base.html`.
4. **The eight codes are shown once.** Whoever clicks past them does not have
   them. The card therefore always shows how many are left, with "new codes" one
   click away.
5. **The demo fix has to be verified against the real demo**, not only against a
   test. Whether that deployment has a read-only `web.toml` is still open.

## Open for the implementation plan

- The debounce window (60 s), the address ceiling (1024) and the pending
  lifetime (180 s) are starting values. Each is a number in one place and each is
  asserted by a test, so revising one is a revision, not a hunt.
- Recovery code length: 5+5 Crockford base32 characters, revisable upward.
- How the public demo is deployed (`web.toml` permissions).
- The reviewer list of security-bearing French sentences — produced in 2.9, not
  here.
